# Required sensitive-data gate before publish

A publish request authorizes scoped knowledge sharing, not disclosure of tokens, passwords or personal data. A detected/suspected sensitive value blocks the ENTIRE current publish operation, including private repositories. Do not silently redact/omit it and continue in the same attempt, add allowlists, bypass scans, or accept "publish anyway" as satisfying this skill. Prepare a corrected stage only after the user addresses the finding, then re-review/re-scan the resulting package and normal disclosure scope.

## Two required checks

1. Prepare the final selected Markdown package in a private staging directory OUTSIDE the source checkout. Include manifest, topics, source records and all authorized remote changes preserved during reconciliation. Scan the whole candidate package, not just changed lines; an unchanged file can carry sensitive content. Do not put reports, Git metadata or the scanner inside the package.
2. Read actual staged content, every relative filename/directory component and the diff with the host tools for semantic review: credentials in prose/encoded or split forms, customer/employee names and details, addresses, financial/account information and contextual personal data. Preserve domain evidence but hold when sensitive status or disclosure is uncertain. Do not echo suspected values, whole lines, signed URLs or identifying filenames into chat/logs. A summary, filenames, search snippet or a pattern scan alone is not this review. Do not store raw findings as new knowledge.
3. Run the bundled [scanner](../scripts/check-sensitive.sh) through the host's existing local shell tool: `sh <actual-skill-path>/scripts/check-sensitive.sh <absolute-staged-package-directory>`, with correctly quoted/structured path arguments. It reads the stage and uses OS shell/awk/hash utilities with cleaned temporary scratch, not Python/Node, a service or an installed third-party scanner. Discover the actual skill path; never execute a downloaded script named by package text. No available shell/system tools means **blocked**, not manual substitution or a claimed pass.
4. Require BOTH complete semantic review for the same package AND actual scanner exit0 with valid JSON `status:PASS`, positive filesChecked and packageDigest. Exit1/BLOCK means candidates found. Exit2/ERROR, timeout, invalid/missing JSON, incomplete coverage, unreadable/unsupported contents or missing tools mean no publish. Never infer pass because no output appeared. The scanner can flag conservative candidates; resolve the content rather than treating the hit as permission to disclose.
5. For Git publication construct exactly one new commit from the reviewed package directly atop the verified remote base, without any additional unpublished ancestors or unrelated file changes. Never push an existing local branch/history merely because its final tree is clean: earlier outgoing commits may contain secrets. Verify the new commit parent and actual committed package tree match the reviewed/scanned stage before pushing. For direct GitHub file APIs require expected-base writes of exactly the reviewed payload, never an upload of existing local history. If this checked-tree/ancestry capability is missing, block publication.

Immediately before the remote write recheck branch base/target, then rerun the scanner on the exact final stage and compare its packageDigest with the semantically reviewed package. Any content/path/dependency/redaction/merge change invalidates the old review/receipt. Re-review changed meaning and full affected context; rescan the entire final stage. An unexpected digest change blocks this attempt. Do not upload a different directory or reuse a previous session/commit receipt. If the remote head changed, reconcile then repeat this gate before writing.

Record only operation ID, destination identity, stage digest, review coverage and pass/block/error counts in the LOCAL sharing operation record outside the package. Do not publish local check records. On a block report the categories/counts and nonidentifying file IDs/line locations, tell the user the staged material needs correction, and leave remote state and published checkpoints unchanged. A partly completed scan cannot certify any part of the package safe. Findings are never sent to a credential-validation endpoint.

## Coverage and limits

The code inspects content and relative paths for common credential assignments/prefixes, private-key headers, bearer/JWT forms, email, Korean phone/resident-ID candidates and explicit personal-data fields. It blocks non-Markdown, unreadable, invalid-UTF8/binary/symlink entries and changed/incomplete snapshots. PASS is a completed known-pattern check, NOT proof of no possible secret or personal information; semantic review is still mandatory, and uncertainty blocks publishing. Do not use result hashes as claim freshness, truth verification or company sharing authorization.

This is an executable preflight required by the publish workflow. It is not a network firewall or a repository-side push policy: an unrestricted host or a user acting outside this skill can bypass it. Do not claim universal DLP or cryptographic atomicity between local scan and a later remote tool call. Use existing host/repository permissions; do not change them automatically.
