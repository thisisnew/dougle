# 업무 건수 조회 정의

봇은 “입하 이슈 몇 건?” 같은 업무 질문을 실제 테이블·필터·기간에 연결한 **검토된 조회 정의**가 있을 때 자동으로 건수를 답합니다. 숫자는 매 문의의 성공한 현재 SQL 결과에서 가져옵니다. 모델이 출력한 `verified=true`, 과거 답변, 조회 시각, 단순 테이블 존재만으로 정의를 승인하지 않습니다.

## 회사 호스트에서 준비

사용자가 해당 업무 조회의 자동화를 요청한 범위에서만 작성합니다. 원본 코드·문서·DB는 읽기 전용입니다. 회사의 실제 자료·스키마를 확인해 업무 용어, 대상 테이블, 조건·제외 조건, 기간·시간대, 허용 Slack 채널이 일치하는지 검토합니다. 의미가 불명확하면 질문하거나 확인 요청을 유지합니다. 이름이 비슷하다는 이유로 다른 테이블을 연결하지 않습니다. 이 문서의 synthetic 예시는 실제 회사 지식이 아닙니다.

원본의 위치·revision·관측 시각, 스키마, 업무 정의와 SQL의 대응·필터·기간 검토 내용을 공통 지식의 `sources/<id>.md`에 보존합니다. 의미 검토는 호스트가 수행하며 해시 검사가 이를 대신하지 않습니다. 기존 소스 기록과 관측 이력을 지우지 않습니다. 해당 파일의 최종 바이트 SHA256을 계산합니다. 관련 원본이 변경되면 이 증거 파일도 갱신하고 조회 정의를 다시 검토해야 합니다. 변하지 않은 로컬 해시가 원격 업무 규칙의 영구 유효성을 뜻하지 않습니다.

백업·동시 변경 확인 후 `~/.dougle/registries/query-plans.json`에 선택한 정의를 추가합니다. 기존 정의·다른 프로젝트를 덮어쓰지 않습니다. 봇의 문의 처리에서는 이 파일과 sources를 수정할 수 없습니다. 플러그인 업데이트만으로 조회 정의가 자동 생성되지 않습니다.

```json
{
  "version": 1,
  "plans": [{
    "id": "receiving-open-count",
    "questions": ["현재 입하 이슈는 몇 건인가요?", "입하 이슈 몇 건?"],
    "channel_ids": ["CTEST"],
    "tool": "mcp__claude_ai_Google_Cloud_BigQuery__execute_sql_readonly",
    "relation": "synthetic.replica.receiving_issues",
    "sql": "SELECT COUNT(*) AS count FROM synthetic.replica.receiving_issues WHERE status = 'OPEN'",
    "scope": "미해결 입하 이슈(전체 기간)",
    "evidence": [{"path": "sources/receiving-count.md", "sha256": "<실제 파일의 SHA256 64자리>"}]
  }]
}
```

questions는 조건과 의미가 같은 **완전한 질문 문장** 목록입니다. 질문 앞뒤 공백만 제거하며 내부 표현을 임의 정규화하거나 비슷한 질문으로 확장하지 않습니다. 같은 채널·질문이 두 정의에 겹치면 사용하지 않습니다. 회사·센터 등 범위가 다르면 채널과 질문·SQL 모두 분리합니다. “입하 이슈 말한 거야” 같은 문맥 의존 후속 질문, 추가 스레드 문맥이나 이미지가 있는 문의는 이 자동 건수 경로를 적용하지 않습니다.

현재 범위는 단일 물리 테이블의 `SELECT COUNT(*) AS count FROM ...`와 선택적 WHERE입니다. JOIN·하위 SELECT·GROUP·다중 문장·다른 집계는 지원하지 않습니다. 기간별 질문은 별도 정의로 등록합니다. 예를 들어 “최근 7일에 등록된 미해결 입하 이슈”는 실제 timestamp 의미·시간대를 검토한 뒤 WHERE에 정확한 기간 조건을 포함합니다. “이번 주”, “최근 7일”, “현재 미해결”을 같은 의미로 연결하지 않습니다. SQL은 바깥 공백을 제외한 정확한 문자열로 대조하므로 필터·날짜·문자열 대소문자·문자열 내부 공백을 바꾸면 불일치입니다.

## 확인과 동작

설치된 스킬의 `scripts/bot.sh query-plans-check`를 실행합니다. `ready`는 형식·허용 도구·증거 파일 해시가 맞다는 뜻이며 업무 의미를 자동 인증하는 결과가 아닙니다. 명령은 모델·SQL·Slack을 호출하거나 파일을 변경하지 않습니다. `invalid_query_plan`이면 JSON 필드, 중복 질문, 허용 채널/도구, 원본 증거 경로·SHA256과 지원 SQL 형태를 확인합니다.

선택된 정의만 엔진에 전달합니다. 일반 문의에 전체 조회 정의나 추가 정책을 넣지 않습니다. 실제 실행한 도구·SQL 해시·테이블·현재 호출 receipt와 결과를 대조합니다. COUNT는 데이터가 없어도 한 행의 count=0을 반환해야 합니다. 성공·완료 표시(jobComplete 또는 job_complete=true)가 있고 오류·다음 페이지가 없는 단일 count 행만 인정합니다. `rows=[]`, 완료 표시 없음, 페이지 누락, 403/404는 0건이 아닙니다. 커넥터가 지원 형식의 완료 결과를 주지 않으면 형식을 확인하고 보류하며 완료 표시를 모델이 만들어 넣으면 안 됩니다.

0건이면 “이번 BigQuery 조회에서는 결과가 없습니다. 잠시 후 다시 문의해 주세요.”를 보냅니다. 1건 이상이면 검토된 범위와 실제 건수로 문장을 만듭니다. 모델이 7건을 보고 0건이라고 쓰더라도 런타임은 검증한 7건으로 렌더링합니다. BigQuery 조회 결과를 실제 운영 전체의 무지연 상태라고 주장하지 않습니다.

조회 정의의 fingerprint를 답변과 같은 DB 트랜잭션에 기록합니다. 조사 도중, 저장 전, 게시 직전에 정의·증거가 변경/삭제되면 해당 답변은 게시하지 않습니다. 사용자 설정·도구·채널의 기존 제한도 유지합니다. 협조하지 않는 외부 작성자가 마지막 검사와 실제 전송 사이를 바꾸는 극히 짧은 경쟁 구간까지 원자적으로 잠그지는 못합니다.
