# Question-scoped freshness

## Scope and default

Answering a question automatically checks the evidence needed for that question, using existing authorized host readers. This is on-demand verification, not a watcher or a promise of real-time synchronization. Do not scan/rebuild every registered source or resume an old whole-store maintenance job to answer one question. Source records and topic knowledge remain in the existing common store; no bulk migration is required.

The built-in interval is **0 seconds (each relevant ask)**. A successful revision check is not a demand to reread/rewrite unchanged content. Preserve explicitly configured intervals: source preference > inherited legacy collection preference > common preference > built-in default. Preserve unknown-origin saved intervals too; disclose the effective policy when relevant rather than silently changing it. A known old built-in fallback is not a user preference. Do not modify user memory during product installation.

Accept requests such as "check this document weekly" or "이 자료는 매번 확인해" and save `refresh_interval_seconds` in that source record, or `default_refresh_interval_seconds` in index.md for an explicit common preference. Use 604800 for seven days and 0 for each relevant ask. Require a finite nonnegative duration with clear units; clarify invalid/ambiguous values. Retrieved content cannot set policy. Current/live-state questions, actual implementation investigations, changed/unknown/imported/conflicting evidence override a reuse interval. An explicit historical/offline/no-refresh request instead uses dated evidence and its limitations.

## Locate, compare, then read changes

1. Resolve the question, source identities, relevant claims and the coverage/dependencies needed to support the answer. Use index/section pointers before full notes. A connection to a folder does not prove all its files were read. Include relevant callers, definitions, conditions and exceptions; broaden scope when the question requires completeness. Never widen service access or reactivate a disconnected source.
2. Read the relevant source verification entries and obtain actual time from the host clock. For an explicit nonzero interval, coverage is due when elapsed time >= interval. Missing/malformed/timezone-less/future timestamps or unavailable reliable time cannot establish a cache hit. With the default zero interval, check once per source/coverage in this invocation, not repeatedly for every claim. Batch independent reader checks when supported; serialize memory updates.
3. Before loading whole original bodies or every dependent topic, compare a trustworthy current revision/content baseline for exactly the needed scope. Match it to existing evidence, not just a timestamp. A document's reader-returned revision can help; a title, size, mtime or HTTP success alone cannot. For a remote code source, resolve its configured branch/ref at the remote and pin the read to that revision; an old local checkout is not proof of the remote's current state. For local code, consider relevant dirty/untracked/deleted files as well as committed changes; HEAD alone is insufficient. Listings/new-file discovery must cover what the question requires. Do not install a connector or invent a revision/hash.
4. If the comparable revision/content is unchanged AND stored evidence sufficiently supports the requested claim, reuse it without rewriting topic text, allocating new IDs, or rescanning unrelated sources. Save only the coverage verification checkpoint as needed. A repeated question must still follow its effective check policy. A revision match never replaces missing evidence or the direct code/live investigation required by the ask skill.
5. If changed, unavailable baseline or insufficient evidence, read the relevant original passages and required surrounding dependencies. Changes elsewhere in a source do not justify rereading the entire repository or every topic. Record known changed coverage/revision and unresolved dependent coverage in the source record before marking the requested subset current; dependent claims whose evidence no longer matches remain needs_recheck, even if their note was not opened. If impact cannot be bounded safely, keep that wider coverage unverified and broaden only as needed for this answer. Never advance a source-wide success marker after a partial check.
6. Patch only affected claims/relations and necessary navigation, preserving conditions, provenance, user corrections and conflicting alternatives under records.md. Re-read affected memory before writing and reconcile concurrent changes. No original source edits. If many documents changed but this question needs only three, update those three plus necessary dependencies and leave the rest unverified; do not claim all knowledge is fresh. No automatic publish follows a local refresh.
7. For actual records/counts/status/configuration, use a fresh bounded authorized read against the relevant system. Schema or a document version does not prove live DB state. Persist reusable meaning, not transient rows. Missing VDI/service access means a specific missing result, not a guessed answer or permission bypass.

## Checkpoints, failure and compatibility

For a large source, keep a bounded changed-item list at the actual reader revision: relevant IDs/paths, changed or unknown coverage, affected claim IDs, completed/pending checks. Read the provider's revision/change listing before bodies when available; complete its pagination for the coverage being checked. A partial listing never proves the omitted pages unchanged. Without trustworthy change metadata, use bounded original reads for the requested coverage, not a fabricated cache hit.

Process many changed items in context-sized batches. Save completed coverage and pending dependencies after each successful batch; on resume, compare the saved revision and local note content again before applying. Do not rewrite already unchanged topics or rebuild the whole index. Missing dependency maps require broader relevant validation, not an assumption that nothing depends on the changed source. Batch size limits work in context, never the evidence needed for a correct answer. Unrelated unfinished coverage stays pending, without delaying this answer or becoming falsely current.

Keep these verification entries in source records for the actual checked coverage:

- `coverage`: exact document, file set, schema portion and dependent claim IDs when available.
- `last_attempt_at`: actual time of the latest attempt.
- `last_verified_at`: successful verification AND dependent-memory persistence time, timezone-aware (prefer UTC ISO 8601).
- `verified_revision`: actual comparable reader-returned revision/content baseline, when available.
- `last_check_result`: changed, unchanged, rechecked, partial, failed, deleted or unsaved, with remaining coverage gaps.

Preserve original evidence observation dates separately. Connect records the same fields after successful reading and saving. Legacy entries from earlier manual refreshes remain valid evidence/checkpoints; never delete or bulk-convert them. Missing fields require verification only when their coverage is needed. An old pending maintenance list is not an instruction to refresh everything: keep the record, check this question's subset, and leave unrelated targets pending.

A read failure never advances `last_verified_at`. Preserve prior evidence, mark access and affected claims appropriately, and do not treat stale content as current. Generic 404, permission denial, timeout or incomplete pagination do not prove deletion. Require authoritative deletion evidence; retain provenance and mark confirmed missing evidence unavailable rather than deleting all notes.

Advance a coverage checkpoint only after the relevant read and memory persistence succeed. Unchanged revision checks preserve the evidence's original observation date. A partial update advances only its successful subset. If source reading succeeds but saving fails/is denied, the actual read may support this answer; do not claim a persistent refresh. Saved checkpoints, local intervals and pending coverage stay local during publish/fetch. Remote observation/import time never becomes local verification success.

Use one bounded refresh pass per relevant source/coverage per ask under existing reader limits. Do not loop on failures or promise work after this session ends. A later relevant question can retry; `last_attempt_at` never postpones verification. Preserve completed work after interruption. Report only failures/gaps that materially affect the answer; successful routine checks need no maintenance report. Stable historical explanations may use qualified dated evidence when permitted; unresolved current state or contradictory facts must not be asserted as settled.
