# dougle-bot 실행 계약

기본은 검증한 답변의 자동 게시입니다. 개발자 확인·운영 조회·내부 오류가 필요할 때만 담당자에게 DM을 보내며, 결과를 받아 원래 스레드에 답변을 이어갑니다. 사용 안내는 [README](README.md), 문의별 흐름은 [자동 답변과 개발자 확인](../docs/dougle-bot/internal-handoff.md)을 참고하세요.

`[slack] require_approval = true`를 지정한 경우에만 검토 모드로 동작합니다. 기존 승인 대기 답변은 자동 게시하지 않습니다. [이전 시험 설계](../docs/dougle-bot/TEST_PLAN.md)의 가정을 현재 구현 완료 사항으로 간주하지 않습니다.

## 접수와 게시

| 단계 | 현재 계약 |
|---|---|
| 접수 | 허용 채널의 사람 메시지 중 봇을 직접 부른 `app_mention`만 받습니다. |
| 조사 | 질문에 필요한 자료를 읽고 이번 호출의 필수 스킬과 근거 실행 기록을 확인합니다. |
| 자동 답변 | 게시 조건을 통과한 답변을 원래 스레드에 보냅니다. 일반 문의에는 DM을 만들지 않습니다. |
| 개발자 확인 | `needs_lookup`·`failed`를 담당자 DM으로 알립니다. 전송 성공 후 고정 대기 안내를 문의당 한 번 시도합니다. |
| 결과 반영 | 해당 DM 카드에서 받은 결과로 같은 문의를 이어가고 검증한 답변을 같은 스레드에 게시합니다. |
| 전송 불명 | `post_unknown`으로 남기고 자동 재전송하지 않습니다. |

대기 안내는 자동 모드에서만 다음 문구를 보냅니다.

> 추가 확인이 필요해 담당 개발자에게 요청했습니다. 확인되면 이 스레드에 이어서 답변드리겠습니다.

DM 전송이 확인되지 않으면 안내를 보내지 않습니다. 안내에 SQL·내부 오류를 포함하지 않으며 최종 답변의 전송 기록과 분리합니다. 안내 전송 실패·불명확한 결과·재시작 후에도 다시 보내지 않습니다. 담당자 결과로 답변을 이어가는 경로는 유지합니다.

## 답변과 권한

답변은 비개발자가 이해할 업무 설명을 기본으로 하며 질문에 필요한 조건·예외·불확실성을 남깁니다. 구현 상세는 질문에 필요할 때 포함합니다. 공개 본문에는 출처 목록·인용 번호·서명을 붙이지 않고 근거는 로컬 기록과 필요한 내부 DM에 보존합니다. 일반 `dougle-ask`는 출처를 표시합니다.

엔진은 허용된 자료를 읽고 `~/.dougle` 내부 지식만 수정할 수 있습니다. Slack 전송은 봇 런타임이 맡습니다. 원본 코드·문서·DB를 바꾸거나 개발자에게 요청한 SQL을 런타임에서 실행하지 않습니다. 허용 도구의 실제 이름과 회사의 읽기 전용 계정·자료 공유 범위는 운영 환경에서 확인해야 합니다.

<summary>입력·저장·재시작</summary>

- 실제 설치 워크스페이스, 허용 채널, 사람 메시지, timestamp, 본인 멘션을 확인합니다. 이벤트 키는 `channel:ts`입니다. 이벤트·스레드·문의·작업을 SQLite 한 트랜잭션에 저장한 뒤 ack하며 Bolt의 `process_before_response=True`를 사용합니다.
- 실행 시작 시 접수 기준 시각을 기록합니다. 중지 중이거나 시작 기준보다 오래된 멘션은 받지 않으며 과거 이력을 문의 큐로 가져오지 않습니다.
- WAL·FK, `user_version=2`, 프로세스 flock과 전체 worker 하나를 사용합니다. 스키마 정본은 [store.py](src/dougle_bot/store.py)입니다. 문의·답변·스레드·엔진 실행 외에 control·jobs·deliveries·audit를 보관합니다.
- 답변 저장, 작업 완료, 자동 게시 준비 표식을 같은 트랜잭션에 기록합니다. 저장 직후 종료돼도 완성된 답변을 다시 생성하지 않습니다. 저장 전 종료에는 이 보장이 적용되지 않습니다.
- 재시작 시 미완료 조사 작업은 다시 대기시킵니다. 게시 도중 중단한 작업과 전송 여부가 불명확한 카드는 보류합니다. 취소한 작업은 복구하지 않습니다.
- 자동 게시 시도는 먼저 기록하며 감사 동작은 `auto_post`입니다. 이전 승인 대기 답변에는 자동 게시 준비 표식이 없으므로 업데이트만으로 게시하지 않습니다.
- 대기 안내는 `handoff_notice_intent`를 트랜잭션으로 선점하고 별도 `post-intents.log`에 전달 ID를 기록한 후 전송합니다. 중복·동시 호출·재시작은 같은 안내를 재전송하지 않습니다. DB만 과거로 복원해 전달 기록이 사라지면 검토를 요구합니다.

<details>
<summary>엔진·근거 확인·도구 제한</summary>

`claude -p`를 고정 cwd에서 실행하고 질문은 stdin으로 전달합니다. 회사 별칭은 zsh 로그인·대화형 초기화를 거친 고정 명령 이름으로 실행하며 질문을 셸 코드에 넣지 않습니다. stream-json 최종 `result.structured_output`을 답변 후보로 사용합니다.

매 호출의 Skill 요청과 성공 응답을 연결해 `dougle-ask`·`i-have-adhd`·`plain-language` 실행을 확인합니다. 출력 계약은 [prompts.py](src/dougle_bot/prompts.py)의 `OUTPUT_SCHEMA`이며 `answered`·`cannot_answer`·`needs_lookup`, 본문, 출처, 조회 요청, 검증 정보를 검사합니다. [근거 확인 문서](../docs/dougle-bot/research-verification.md)에 읽기 기록과 필수 근거 계약을 정리했습니다.

세션이 없으면 새 세션으로 한 번 재시도합니다. 스키마·말투·스킬·근거 검증 실패는 한 번의 보완 예산을 공유합니다. 각 실행은 예산을 따로 예약하며 인증·네트워크 실패를 세션 없음으로 취급하지 않습니다. 이미 선언한 조사 요구는 스킬 확인 실패나 개발자 결과 반영 후에도 유지합니다.

같은 문의의 직전 시도에서 스키마·근거·필수 스킬이 모두 검증되고 표현만 실패했다면 본문만 고치는 보완에서 근거를 재사용할 수 있습니다. `sources`·`status`·`lookup`·`verification`은 같아야 하고 세 필수 스킬은 다시 성공해야 합니다. 운영 현재값·누락 근거·다른 문의·세션 복원에는 적용하지 않습니다. 문장의 의미가 같다는 보장은 아닙니다.

성공한 답변을 저장할 때만 세션과 `last_seen`을 갱신합니다. 후속 질문은 같은 스레드 세션과 이후 메시지를 사용하며 새 최상위 문의는 별도 세션입니다. 세션 복원 시 읽은 전체 스레드로 재시작하고, 이력 한도를 넘으면 조용히 잘라내지 않고 중단합니다.

Bash·Agent·Task를 차단하고 PreToolUse hook으로 허용 도구와 실제 파일 쓰기 경로를 검사합니다. Write/Edit는 `~/.dougle` 내부만 허용하며 symlink 탈출을 막습니다. StructuredOutput·ToolSearch는 결과 반환·도구 발견에 허용하되 발견한 도구 실행에도 같은 권한 정책을 적용합니다. OS 전체 샌드박스나 MCP 서버 구현의 안전성을 보장하지는 않습니다. 봇 밖의 Claude 작업과 지식 쓰기까지 직렬화하지 않습니다.

제한 시간은 문의 처리 시작부터 누적하며 보완·세션 복원 때 초기화하지 않습니다. 시간 초과나 중단 시 소유한 프로세스 그룹만 종료합니다. 이미 수행한 원격 읽기는 되돌리지 않습니다. 출력 총량은 4MB로 제한하고 원시 stdout/stderr는 보관하지 않습니다.

</details>

<details>
<summary>개발자 결과·게시·검토 모드</summary>

결과 입력은 담당자 ID, 워크스페이스, 문의, 실제 카드 channel/ts, 최신 답변 또는 실패 작업을 확인합니다. 중복 제출은 작업 하나만 만듭니다. 일반 DM 텍스트·이미지는 임의 문의에 연결하지 않습니다.

확인 결과는 요청한 미확인 `code`·`live`·`knowledge` 종류에만 보고 근거로 사용합니다. 이미지 확인을 대신하지 않습니다. 처리 결과의 `evidence_kinds`는 비어 있으며 필요한 자료를 다시 읽습니다. 시간 입력은 요구하지 않고 제출 시각을 실제 조회 시각으로 표시하지 않습니다. 예전에 제공된 조회 시각은 보존합니다.

조회 요청은 대상·막힌 이유·확인할 내용·필요한 결과를 담습니다. 검증하지 못한 SQL은 표시하지 않되 확인 요청은 유지합니다. 운영 조회는 허용된 BigQuery 읽기 도구를 먼저 탐색하고 스키마와 데이터 최신성을 확인하도록 지시합니다. 복제 데이터가 현재 운영 상태를 증명한다고 단정하지 않습니다.

게시 직전 최신 답변·허용 채널·스키마·민감정보·말투·스레드 변경 여부를 확인합니다. 자동 모드에서 작성 중 스레드가 바뀌면 내부 확인으로 넘깁니다. 원본 Confluence·DB를 런타임이 직접 재조회하지는 않으며 자료 최신성 판단은 `dougle-ask`가 맡습니다. Slack 조회와 게시 사이의 원격 변경을 원자적으로 잠글 수는 없습니다.

`awaiting_approval`에서 `posting`으로 조건부 전환한 뒤 조각별 전달 ID·시도·결과를 기록합니다. 내부 상태 이름이 `awaiting_approval`이어도 자동 게시 준비 표식이 있으면 자동 모드로 처리합니다. 첫 조각이 확실히 전송되지 않은 오류는 자동 모드에서 `failed`, 검토 모드에서 재승인 가능한 상태로 돌아갑니다. 응답 유실·부분 성공·전송 도중 종료는 `post_unknown`으로 남깁니다. reconcile은 본문·전달 ID가 맞는 단일 봇 메시지를 확인한 경우에만 전송 완료로 복구합니다.

검토 모드는 승인자·워크스페이스·문의·최신 답변·실제 카드·미리보기 해시를 확인한 뒤 게시합니다. 직접 수정은 새 revision, 조회 결과 반영과 내부 재검증은 새 job입니다. 스레드나 게시 형식이 바뀌면 다시 생성·검토하며 옛 전달 본문을 재사용하지 않습니다. `needs_lookup`에는 게시 버튼이 없습니다.

거절은 검증 후 즉시 상태를 저장하고 ack한 뒤 카드를 갱신합니다. 거절 사유 모달과 수동 다시 생성은 제공하지 않습니다. 예전 거절 모달은 빈 사유로 완료할 수 있지만 예전 다시 생성 버튼·모달은 새 AI 작업을 만들지 않습니다. 내부 재검증은 별도로 유지합니다.

렌더러는 사실을 요약하지 않고 제한된 서식과 등록된 인용 표시만 변환합니다. 코드·인용은 보존합니다. 수동 수정은 승인자의 수정이며 수정 문장 전체를 AI가 재검증했다는 뜻은 아닙니다.

</details>

<details>
<summary>이미지 입력</summary>

Slack files 객체와 `files.info`로 권한 있는 직접 업로드 PNG/JPEG를 확인합니다. `files:read`가 필요하며 스레드당 최대 4장, 장당 5MiB, 합계 12MiB를 검사합니다. 일부 이미지를 조용히 생략하지 않습니다. 최초 이벤트의 첨부가 history에서 보이지 않아도 중단합니다.

다운로드는 `files.slack.com`의 HTTPS `/files-pri/`만 허용하고 리다이렉트는 따르지 않습니다. 크기·시간·MIME·기본 파일 구조를 검사하지만 완전한 이미지 디코더는 아닙니다. 다운로드 오류나 CLI의 알려진 이미지 처리 오류는 실패로 처리합니다.

이미지는 메모리에서 base64 image content로 만들어 Claude의 stream-json stdin에 전달합니다. 키체인 값·다운로드 URL·이미지 본문을 프롬프트 텍스트나 DB·audit에 저장하지 않습니다. 이미지 자체는 AI 제공자에게 전달되며 Claude 세션 보관 정책은 별개입니다.

수집 오류는 모델 호출 전에 중단하고 담당자 DM에 알립니다. 첨부 변경·삭제는 history hash에 반영해 게시 전 검증합니다. 이미지 해석 정확도와 이미지 속 민감정보의 완전한 탐지는 별도 검증 대상입니다.

</details>

<details>
<summary>운영·진행 표시·중단</summary>

메뉴는 시작·상태 확인·중지·채널 추가입니다. 설정이 없으면 설치·키체인·담당자·채널 안내를 먼저 합니다. 같은 Slack 앱의 채널 추가는 토큰을 재사용하며 설정 변경 전 실행을 중지합니다. 채널 등록만으로 자동 재시작하지 않습니다.

토큰은 macOS Keychain에서만 읽습니다. 저장할 때는 `security` 명령의 값 없는 마지막 `-w`와 사용자 터미널 입력을 사용합니다. 환경변수·설정·CLI 인자로 토큰을 받지 않습니다. 실행 환경은 M Mac, Python 3.12+, uv, slack-bolt와 표준 sqlite3입니다.

실행 버전은 daemon 시작 audit로 확인합니다. 스킬이나 CLI 파일의 버전이 실행 중인 프로세스의 버전을 대신하지 않습니다. [README의 상태 확인](README.md#대화에서-진행-상황-보기)과 [진행 로그](README.md#터미널에서-진행-상황-보기)로 관측한 단계를 확인합니다.

문의 리액션은 `dougle`과 상태 이모지를 함께 사용합니다. 처리 중은 loadingg, 조회 결과 대기는 말풍선, 완료는 처리완료, 오류·전송 불명은 경고, 거절·취소는 금지 표시입니다. 리액션 실패는 답변을 막지 않으며 heartbeat를 대신하지 않습니다. 적용 전 시도 목록을 audit에 남겨 재시작 후 이전 표시를 정리합니다. `dougle`이 `invalid_name`이면 상태 이모지만 사용합니다. loadingg/처리완료가 없으면 각각 모래시계/체크로 대체하고, 권한·네트워크 실패에는 다른 이모지로 재시도하지 않습니다. 명시적 빈 설정은 표시를 끕니다.

DM이 있는 문의는 같은 카드를 갱신합니다. queued/drafting 카드의 중단 버튼은 담당자·워크스페이스·카드·최신 job을 확인하고 문의와 작업을 함께 `cancelled`로 바꿉니다. 늦은 결과 저장과 세션 갱신을 막으며 전체 봇 중지와 구분합니다.

진행 DM은 약 30초마다 제한된 작업 단계·도구 응답 수·경과·무신호 시간을 갱신합니다. 원문·도구 인자·경로·토큰은 넣지 않으며 도구 응답 수를 성공한 근거 수로 표시하지 않습니다. `answer_timing`에는 큐 대기·처리·관측 단계 시간, 재시도 종류, 입출력 문자 수를 남깁니다. `recent_timings`는 최근 10개 중 유효한 숫자 항목을 반환합니다. 단계 시간은 CLI 이벤트 사이 관측값이며 순수 추론 시간이나 병렬 도구별 실행 시간이 아닙니다. 계측 실패는 답변을 실패시키지 않습니다.

</details>

## 검증 범위

자동 검사는 가짜 서비스와 임시 데이터로 파서·권한 검사·큐·SQLite·게시·복구 경계를 확인합니다. 합성 자료를 사용한 실제 모델 평가는 별도 기록이며, 실제 회사 연결·응답 품질·공유 가능 범위는 [회사 수용 검증](../docs/dougle-bot/company-acceptance.md) 대상입니다. 자동 테스트 통과만으로 회사 사용 검증을 마쳤다고 표시하지 않습니다.

## 개발자 결과 접수와 직접 응대 (0.1.14)

- 진행 상태는 loadingg, 게시 완료는 처리완료 사용자 이모지입니다. invalid_name일 때만 각각 hourglass_flowing_sand/white_check_mark로 대체하며 dougle 정체성은 유지합니다. 빈 ack_reaction은 전체 표시를 끕니다.
- needs_lookup/failed 카드에는 직접 응대할게요(take_over)를 제공합니다. 사용자·워크스페이스·카드·draft/job·현재 상태를 확인하고 트랜잭션으로 cancelled와 developer_takeover 기록을 저장합니다. 기존 결과 제출이나 최종 자동 게시를 허용하지 않습니다.
- 결과 제출은 작업 등록과 developer_result_received를 같은 트랜잭션에 저장합니다. 자동 모드에서 고객에게 접수 안내를 보낸 뒤 조사·검증을 이어갑니다. 새 작업 ID가 아닌 과거 이벤트로 안내하지 않습니다.
- 직접 응대 안내와 결과 접수 안내는 이벤트별 감사 선점 및 post-intents.log를 사용합니다. 중복 시도와 성공 불명 재시도를 막고, 중지·허용 채널·작업 상태를 전송 전에 다시 확인합니다. 이미 시작한 원격 전송의 회수나 분산 exactly-once를 보장하지 않습니다.
