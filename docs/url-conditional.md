# URL 재수집 — 바뀌었는지 먼저 묻기

웹 서버가 ETag 또는 Last-Modified를 제공하면 다음 동기화 때 그 값을 함께 보냅니다.
서버가 **304(변경 없음)**를 보내면 이전 원본을 그대로 사용합니다. 본문을 다시 분석하지 않습니다.
사용자가 따로 켤 옵션은 없습니다. 수동 동기화와 ON으로 설정한 자동 갱신에 적용합니다.

`첫 수집(200) → 원본 + 확인표 보관 → 다음 요청에 확인표 첨부 → 304면 재사용 / 200이면 새 본문 검사`

## 안전 규칙

- 확인표가 없으면 기존처럼 본문을 수집합니다. 서버가 지원하지 않아도 사용할 수 있습니다.
- 확인표는 **처음 수집한 최종 URL과 정확히 같은 URL**에만 보냅니다. 다른 호스트나 다른 경로로 전달하지 않습니다.
- 리다이렉트의 모든 목적지에 기존 공개 HTTPS/SSRF 제한을 적용합니다.
- 조건부 요청 없이 받은 304나 이전 원본과 주소가 맞지 않는 304는 오류입니다.
- 새 본문 수집·분석·저장이 성공해야 확인표도 교체합니다. 실패하면 이전 원본과 확인표를 유지합니다.
- 새 200 응답에 확인표가 없으면 예전 값을 지웁니다. 304가 새 값을 주면 갱신하고 없으면 유지합니다.
- 제어 문자 또는 1024자를 넘는 확인표는 사용하지 않습니다.
- 404/네트워크 오류는 Source 오류로 표시하고 이전 복사본을 남깁니다. 원격 삭제가 로컬 자료 삭제로 이어지지 않습니다.

**304는 웹 서버의 변경 없음 응답일 뿐 사실 검증이 아닙니다.** 오래된 서버 캐시나 잘못된 ETag까지 판단할 수는 없습니다.
지식 편집·AI 호출·게시를 자동 실행하지 않습니다.

## 모델과 실제 구현

| 모델 | 실제 코드 |
|---|---|
| Source별 확인표 | SQLite v20 `source_http_cache(source_id, uri, etag, last_modified)`, Source 삭제 시 cascade |
| 수집 결과 | `CollectedSnapshot.validators`, 도메인 `HttpValidators` |
| 조건부 HTTP | `PublicHttpReader`: If-None-Match / If-Modified-Since, 304 분리 처리 |
| 이전 원본 재사용 | `UrlCollector.collect(location, previous)` |
| 원본·확인표 동시 반영 | `JdbcSourceStore.publish`의 같은 트랜잭션 |

API/화면 계약은 바꾸지 않습니다. Source의 마지막 반영 revision·시각·오류에서 결과를 확인합니다.
v19→v20 이관은 기존 원본을 유지하고 빈 캐시 테이블만 추가합니다. 이전 앱으로 DB를 다운그레이드하지 마세요.
