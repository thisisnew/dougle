# 업무 건수 자동 답변과 기대 실패 2건 수정

스킬 0.8.30 / 봇 0.1.27. 2026-11-10 사용자가 기존 기대 실패 두 건의 수정을 요청했습니다.

## 무엇이 문제였나

기존 테스트는 “현재 입하 이슈는 몇 건인가요?”라고 묻고 관계가 입증되지 않은 centers 테이블을 조회했습니다. 첫 테스트는 COUNT 쿼리에 빈 rows 배열까지 주었는데, 정상적인 COUNT(*) 0건은 count=0인 한 행이어야 합니다. 두 테스트는 posted를 기대했지만 런타임은 확인 요청으로 전환했습니다. 일반 업무 용어와 실제 조회의 검증된 연결이 없어 자동 답변을 완료하지 못했습니다.

## 구현

호스트가 실제 업무 원문과 스키마를 검토한 조회 정의를 공통 지식의 보호된 registries/query-plans.json에 등록합니다. 질문 전체 문장·채널·도구·테이블·정확한 SQL·답변 범위·원본 증거 파일 해시를 연결합니다. 봇의 문의 처리로 이 정의나 증거를 작성/수정할 수 없습니다. 모델이 “검증됨”이라고 말하는 것으로 등록하지 않습니다.

런타임은 선택된 정의만 프롬프트에 전달합니다. 일반 질문의 고정 정책은 그대로이며 새 모델 단계·전체 레지스트리 주입은 없습니다. 실제 도구 호출의 SQL 해시, 테이블, 현재 호출의 receipt, 오류/완료/페이지 상태, 단일 count 행을 대조합니다. 0건은 동일한 무결과 안내를 보내고, 1건 이상은 검토된 범위와 실제 숫자로 문장을 만듭니다. 모델 본문이 0건이라고 써도 실제 완료 결과가 7건이면 7건으로 렌더링합니다.

조회마다 새 성공 결과가 필요합니다. 직전 0건 답변·receipt를 다음 문의의 결과로 재사용하지 않습니다. 조회 정의 fingerprint를 초안·job 완료와 같은 트랜잭션에 저장하며 저장 전·게시 직전에 증거/정의 변경·삭제를 다시 검사합니다. 기존 자동 모드/승인 모드·등록 도구·채널 제한을 보존합니다.

## 검사

기존 기대 실패 표시 두 개를 제거하고, 실제 입하 이슈 테이블·필터와 연결된 합성 정의 및 완료된 COUNT 결과로 바꿨습니다. 이제 반복 0건 게시와 0→1 변경을 정상 테스트로 검증합니다. 관련 신규 검사는 다음을 포함합니다.

- 잘못된 테이블·필터·기간·질문·채널, 미등록 정의, 여러 운영 조회를 섞은 답변은 자동 게시하지 않습니다.
- 빈 count rows·미완료·도구 오류는 0건으로 처리하지 않습니다.
- 기간 조건이 있는 정확한 SQL과 7건 결과를 받아 모델의 틀린 숫자를 교정합니다.
- 모호한/중복 정의·지원하지 않는 SQL·누락/변경된 원본 증거·symlink를 거부합니다.
- 조사 도중 및 저장 후 게시 전에 정의가 바뀌면 게시를 중단합니다.
- query-plans-check는 읽기 전용이며 SQL·모델을 호출하지 않습니다.

개발 시험은 임시 자료와 fake 엔진/Slack/SQLite를 사용합니다. 회사 데이터·실제 Slack·키체인은 변경하지 않았습니다. 전체 로컬 pytest 1,736개 통과, 실패·기대 실패 0개입니다. Ruff, 스킬 구조·공유/게시·민감정보·플러그인 검사와 wheel 소스/사본/ZIP/격리 설치를 확인했습니다. CI와 공개 다운로드 결과는 최종 릴리스 검증 기록에 남깁니다.

## 회사에서 적용

1. 0.8.30 플러그인과 0.1.27 런타임을 준비하고 기존 봇 정상 중지 후 새 버전으로 시작합니다. 사용자 설정·키체인·지식은 보존합니다.
2. [조회 정의 안내](../../skills/dougle-bot/references/query-plans.md)를 읽고, 회사 자료에서 입하 이슈의 실제 테이블·필터·기간·시간대·채널을 확인합니다. 합성 예제의 테이블이나 CTEST를 그대로 등록하지 않습니다.
3. 기존 지식과 등록 파일을 백업하고 승인된 범위의 정의만 추가합니다. 질문별로 조건을 명확히 구분하며 기존 정의를 덮어쓰지 않습니다.
4. 설치 스킬의 scripts/bot.sh query-plans-check에서 ready를 확인합니다. 이는 형식/증거 해시 검사이며 의미 검토를 대신하지 않습니다.
5. 등록한 같은 질문을 3회 묻고, 실제 조회 결과와 답변 숫자를 비교합니다. 실제 데이터가 바뀌었을 때 다음 문의도 새 값인지 확인합니다. 원본 업무 DB에 테스트 데이터를 쓰지 않습니다. 안전한 0건/변경 사례가 없으면 해당 실제 시험은 미실행으로 표시합니다.
6. 등록하지 않은 기간·다른 채널의 질문을 임의의 같은 조회로 처리하지 않는지 확인합니다. 403/404/완료 표시 없는 결과가 무결과 안내로 바뀌면 결함으로 보고합니다.

현재 자동 범위는 등록된 완전한 질문과 단일 테이블 COUNT(+WHERE)입니다. JOIN·그룹 집계·임의 표현의 모든 자연어 질문·추가 스레드 문맥·이미지 질문은 자동으로 추측해 처리하지 않습니다. 회사별 조회 정의는 실제 자료로 등록해야 하므로 업데이트만으로 모든 업무 질문이 자동 답변되는 것은 아닙니다. BigQuery 조회 결과를 운영 전체의 무지연 사실이라고 보장하지 않습니다.

## 실패했을 때

invalid_query_plan은 형식·중복 질문·허용 도구·증거 경로/해시·SQL 형태를 확인합니다. query_plan_changed는 조사/게시 사이 정의나 증거가 바뀐 것으로, 원문 재검토 후 새 문의로 다시 조회합니다. 결과에 jobComplete=true 또는 job_complete=true가 없다면 커넥터의 실제 반환 형식을 확인합니다. 완료 표시를 모델이 만들어 붙이거나 검증을 끄지 않습니다.

회사 Claude는 설치/실행 버전, 정의 ID와 검토한 범위, 질문별 실제 결과·최종 답변·재시도와 오류 코드·사용량을 보고해 주세요. 인증정보·개인정보·원시 업무 행은 보고서에 넣지 않습니다.
