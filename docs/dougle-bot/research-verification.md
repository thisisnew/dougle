# 답변에 필요한 근거 확인

짧은 답변이라도 필요한 조사는 마쳐야 합니다. 먼저 질문에 필요한 자료를 확인하고, 근거가 충분한지 검사한 뒤 쉬운 말로 답합니다.

| 질문 | 필요한 확인 |
|---|---|
| “이 화면에 상태가 뭐라고 쓰여 있나요?” | 첨부 이미지의 실제 표시 내용 |
| “왜 이 버튼이 안 보이나요?” | 원본 코드의 표시 조건·호출 경로와 관련 설정·문서 |
| “이 주문은 실제로 처리됐나요?” | 해당 환경·대상의 최신 읽기 전용 조회 또는 개발자 조회 결과 |
| “조건은 맞는데 이 건만 왜 실패했나요?” | 관련 구현과 원인을 가릴 수 있는 실제 상태 |
| “회송이 무슨 뜻인가요?” | 최신성 정책을 만족하는 업무 지식. 매번 코드·DB 조회를 요구하지는 않습니다. |

비개발자에게 코드 이름을 보여주지 않아도 필요한 코드 확인은 수행합니다. “코드로 확인하지 않았습니다”라는 문구로 조사를 대신할 수 없습니다.

## 실행 기록과 답변 대조

모델은 질문 유형, 필요한 근거 종류, 성공한 읽기 도구 호출 ID와 출처, 아직 확인하지 못한 종류를 제출합니다. 런타임은 이를 이번 호출의 실행·응답 기록과 대조합니다. 검토 정보는 고객에게 게시하는 본문에 붙이지 않습니다.

스킬 실행이나 파일 이름 검색, 토픽 요약만으로 원본 코드 확인을 대신하지 않습니다. DB 스키마를 읽은 기록도 실제 데이터 조회로 인정하지 않습니다. 첨부 이미지는 이번 호출에 전달한 파일만 인정합니다.

필요한 확인이 빠지면 정해진 예산 안에서 한 번 보완합니다. 재시도에서 조사 요구를 삭제해 통과할 수는 없습니다. 직접 확인할 수 없으면 개발자 확인을 요청하거나 확인하지 못한 범위를 답합니다. 미검증 사실 답변을 `answered`로 제출하면 게시 가능한 답변으로 저장하지 않습니다.

## 개발자 결과 사용

[개발자 확인 DM](internal-handoff.md)의 결과는 해당 문의에서 요청한 미확인 근거 종류와 범위에만 사용합니다. 개발자 보고를 봇이 직접 조회한 결과로 표시하거나 이미지 확인의 근거로 대체하지 않습니다. 환경 복구 보고는 실제 자료를 다시 읽어야 한다는 뜻입니다.

시간 입력은 요구하지 않습니다. 제출 시각을 실제 조회 시각으로 바꾸지 않으며, 예전에 입력한 조회 시각이 있으면 보존합니다. 내용이 오래되었거나 범위가 맞지 않으면 필요한 결과를 다시 요청합니다. SQL·운영 행·토큰은 고객 답변에 전달하지 않습니다.

`verification`은 `question_kind`, `required`, `checks`, `missing`으로 구성합니다. 각 `check`는 근거 종류, 읽기 호출 ID(`receipt`), 출처 인덱스(`source_index`)를 연결합니다. `answered`는 모든 필수 근거를 충족하고 `missing`이 비어 있어야 합니다.

| 근거 종류 | 인정하는 실행 기록 |
|---|---|
| `knowledge` | 지원하는 자료 내용 읽기 |
| `code` | 소스 확장자 파일의 `Read`, 단일 소스 파일 내용 `Grep`, 원본 코드 URL의 `WebFetch` |
| `live` | 허용된 `execute_sql_readonly`의 실제 조회 |
| `image` | 이번 호출에 전달한 `image:<file_id>` |
| 개발자 보고 | `developer_report`와 요청된 `evidence_kinds`. 예전 보고는 `live`로 해석합니다. |

`PostToolUse`는 성공한 읽기의 정확한 ID와 지원 근거 종류를 모델에 알려줍니다. 경로·결과 원문·DB 행을 알림에 복제하지 않습니다. 검증의 기준은 실제 stream 기록이며 모델이 적은 ID나 알림만으로 성공을 인정하지 않습니다. 인식하지 못하는 도구·형식은 지원하는 읽기 방법이나 개발자 결과로 보완합니다. 이 절차가 도구 권한을 추가하지는 않습니다.

같은 문의의 직전 시도에서 스키마·필수 스킬·근거 검증이 모두 끝나고 표현만 실패했다면, 본문만 고치는 한 번의 보완에서 근거를 재사용할 수 있습니다. `status`·`sources`·`lookup`·`verification`은 같아야 하고 세 필수 스킬도 다시 성공해야 합니다. 운영 현재값, 누락 근거, 다른 문의, 세션 복원에는 적용하지 않습니다.

검증 기록은 `drafts.verification_json`에 저장하며 DB는 `user_version=2`로 이행합니다. 기존 문의·세션·게시 이력을 보존합니다. 검증 기록이 없는 이전 미게시 답변은 게시·직접 수정 전에 다시 조사합니다. 자동 게시 준비 표식이 없는 예전 승인 대기 답변은 업데이트만으로 게시하지 않습니다. 검토 모드에서는 새 답변을 승인해야 합니다. 이미 게시한 메시지는 바꾸지 않습니다. 검토 모드의 수동 수정은 승인자의 수정이며 모든 수정 문장을 AI가 재검증했다는 뜻은 아닙니다.

## 검증의 한계

실행 기록은 자료를 읽었다는 사실을 검사합니다. 질문에 어떤 근거가 필요한지, 읽은 코드가 주장·환경에 맞는지, 결과를 제대로 해석했는지는 여전히 모델 판단입니다. 구현 질문을 화면 설명으로 잘못 분류하는 오류까지 막았다고 주장하지 않습니다.

가짜 모델·Slack 응답과 실제 파서·큐·SQLite를 쓰는 자동 검사는 누락·오류·재시도·업데이트 경계를 확인합니다. 합성 자료의 실제 모델 평가와 회사 수용 검증은 별도입니다. 현재 실행 결과는 [검증 기록](implementation-verification.json)의 빌드와 범위를 확인하고, 회사 질문의 분류·검색 품질과 실제 CLI 호환성은 [회사 수용 검증](company-acceptance.md)으로 확인하세요.
