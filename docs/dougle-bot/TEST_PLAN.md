## 목표와 완료의 의미

모든 환경에서 장애가 전혀 없음을 보장할 수는 없습니다. 이 계획은 장애가 나더라도 **승인 없는 게시·중복 재게시·다른 문의와의 혼합·비밀 유출·조용한 문의 유실**을 방지하고, 남은 상태와 재개 방법을 확인하는 것을 목표로 합니다.

케이스 목록의 `NOT_IMPLEMENTED`·`NOT_RUN`은 최초 계획의 상태입니다. 현재 테스트와 개별 ID의 대응은 아직 전부 정리되지 않았으므로 실제 실행 기록을 별도로 확인하세요. 문서/JSON의 형식 검사를 통과해도 제품 테스트는 통과한 것이 아닙니다. 테스트 개수는 독립된 시나리오 ID 수이며, 반복 횟수나 조합 수를 별도 기능 테스트처럼 부풀리지 않습니다.

## 최초 설계에서 검토한 동작

| 결정 | 보완할 명세 | 검증 기준 |
|---|---|---|
| 빠른 영속 접수 후 ack | §6.1의 즉시 ack와 저장 전 종료의 유실 문제 | 최소 접수를 로컬에 영속화한 뒤 ack하고 무거운 처리는 worker에서 수행합니다. Slack 응답 기한 내 저장이 불가능하면 성공 접수로 ack하지 않습니다. 실제 SDK가 자동 ack하는 위치도 확인합니다. |
| 전송 여부 불명 보존 | §6.4의 모든 실패를 승인 대기로 복귀시키는 규칙 | 명확한 미전송만 재승인 가능하게 합니다. timeout/연결 종료/불명 오류/중간 종료는 post_unknown으로 두고 확인 전 재게시하지 않습니다. |
| 조각별 전송 기록 | §7의 단일 posted_ts만으로는 부분 게시 복구 불가 | 전송 시도와 조각 번호·본문 식별·응답 ts·결과를 영속 기록합니다. 추가 테이블/필드는 구현 명세에 반영합니다. |
| 승인과 초안 일치 | §6.3–6.4 | 사용자·workspace·문의·최신 revision·카드·목적지·최종 표시 본문을 묶고, 변경 시 재승인합니다. |

| 실제 도구 제한 | §5의 광범위 git/gh 허용 | 읽기 전용 도구·인증·쓰기 경로 제한을 검증합니다. 프롬프트 지시나 allowedTools 목록만으로 강제됐다고 보고하지 않습니다. |
| 비용 예약과 미확인 비용 | §6.2의 오늘 합계 확인 | 실제 호출 전에 예약하고 retry에도 적용합니다. 비용 누락/timeout은 0원으로 처리하지 않습니다. CLI 추정액을 확정 청구액으로 보장하지 않습니다. |
| 유실 맥락·조회 결과 구분 | §6.2/6.5 | 실제 게시본·중요한 정정·미해결 사항을 복원합니다. 개발자 결과는 시각/대상과 함께 보고된 근거로 다룹니다. |
| 원본과 출력 보호 | §5/§9 보완 | Slack 입력·자료는 비신뢰 데이터입니다. 최소 조회 결과만 처리하고 토큰/개인정보를 로그·카드·공유 지식에 복사하지 않습니다. |

위 항목은 최초 설계의 제안입니다. 구현 여부는 현재 코드·자동 검사 기록을, 회사 환경 확인 여부는 별도 체크리스트를 참고하세요.

## 테스트 환경

Python 3.12+, pytest, ruff와 표준 라이브러리로 구성합니다. 제품 의존성은 별도 bot 프로젝트에서 관리합니다. 테스트 계획 때문에 기존 스킬 사용자에게 런타임을 설치시키지 않습니다.

- `FakeSlack`: 채널/스레드/DM/메시지 저장소, 호출 trace, cursor, 권한, rate limit, 카드/모달, 쓰기 전 실패와 **쓰기 후 응답 유실**을 따로 구현합니다.
- `FakeEngine`: 결정된 결과/오류/비용/세션 ID를 반환합니다. 명령 실행·결과 파싱을 검증하는 테스트에는 임시 가짜 CLI 프로세스를 사용하며 실제 `claude`는 절대 호출하지 않습니다.
- `FakeSecretStore`와 `FakeSecurityRunner`: 키체인 내용을 메모리에서만 관리하고 인자·환경·터미널 연결을 관찰합니다. security 호출을 실제 OS로 전달하지 않습니다.
- `FakeClock`/명시적 barrier: 자정·역행·타임아웃·경합을 재현합니다. 우연히 맞을 때까지 sleep하거나 wall-clock에 의존하지 않습니다.
- SQLite: 테스트별 임시 실제 DB를 사용합니다. DB를 통째로 mock하지 않아 UNIQUE/FK/트랜잭션/WAL/재시작 동작을 놓치지 않습니다. 손상 fixture도 임시 DB에서만 만듭니다.
- 모든 ID/토큰/조회 결과는 합성 자료입니다. 실제 Slack 사용자/채널 ID와 회사 결과는 커밋하지 않습니다. 가상 비밀 sentinel은 실행 중 생성하며 검사 보고서에는 값 자체를 남기지 않습니다.
- 테스트 fixture는 실제 홈·`~/.dougle`·키체인·네트워크·실제 CLI로 나가는 호출을 기본 거부합니다. subprocess 테스트는 해당 임시 가짜 실행 파일만 허용합니다.

Fake의 결과만 믿지 않고 실제 호출 인자/응답 해석/DB 변화까지 확인합니다. FakeSlack이 항상 성공하는 테스트만으로 완료 판정을 내리지 않습니다. 실제 SDK handler와 adapter도 가짜 transport에 연결하여 ack·retry·예외 변환을 검사해야 합니다.

## 공통 준비와 케이스 사용법

자동 케이스의 기본 fixture는 허용 채널 A/B, 비허용 채널 X, 승인자 U1, 비승인자 U2, 봇 B1, 서로 다른 두 스레드, 새 임시 DB, 가상 시계, 비밀을 모사한 FakeSecretStore입니다. 정상 문서는 가상 입하/반품 업무 자료이며 공개 가능한 시험 내용만 사용합니다.

각 케이스의 `condition_and_action`이 기본 fixture를 변경하고, `expected`가 독립 판정 기준이 됩니다. 구현 시 반드시 **실제 입력·순서·fault 지점·관측 상태·금지된 부수효과**를 pytest assertion으로 옮깁니다. 기대 결과를 production 함수에서 계산해 서로 같은 버그를 공유하지 않습니다.

각 실행 결과에는 케이스 ID, 구현 커밋, Python/SDK 버전, test node ID, 결과, 가상 seed/전송 trace/DB 검증 증거를 남깁니다. 모델 의미 평가와 Fake 결과 검증은 합산하지 않습니다.

## 경계값과 조합 검증

독립 시나리오를 먼저 구현한 다음 각 케이스의 의미 있는 입력 변형을 `pytest.mark.parametrize`로 실행합니다.

| 축 | 변형 |
|---|---|
| 길이 | 0, 1, 한도-1, 한도, 한도+1, 다중 조각; 한국어/emoji/결합문자/코드/URL |
| 상태 | queued, drafting, awaiting_approval, needs_lookup, posting, posted, rejected, failed, post_unknown |
| 승인 동작 | 게시, 수정 제출, 재생성 제출, 조회 결과 제출, 거절 |
| 식별 | 승인자/비승인자/누락; 최신/과거/다른 문의/없는 draft; 정상/다른 workspace·카드·목적지 |
| API 결과 | 성공, 확실한 미전송, 저장 후 timeout, 응답 유실, malformed 결과, 권한 거부, rate limit |
| 시간 | 한도 직전/동일/직후, 자정, 시간대, 시계 역행, 잘못된/미래 조회 시각 |
| 경합 | 이벤트 재전송, 게시×게시, 게시×수정, 수정×수정, 재생성×거절, 종료×복구 |
| 프로세스 | 정상 종료, timeout, SIGTERM, SIGKILL, 자식 잔존, 버퍼 초과, 비정상 인코딩 |

상태×동작×승인자×초안 관계는 작은 독립 reference model로 전수 생성합니다. 허용 조건은 production 분기 복사가 아니라 위 승인 계약에서 정의합니다. 특히 모든 비승인 조합에서 채널 전송/상태 변경이 0인지 확인합니다. 모든 축의 무의미한 곱을 테스트 수로 제시하지 않습니다.

## 중단 주입 지점

다음 지점 각각의 **직전/직후**를 프로세스 종료 또는 가짜 예외로 재현합니다. 네트워크가 섞인 지점은 원격 효과 발생 여부를 독립적으로 설정합니다.

1. 수신 후 최소 접수 저장 시작/commit/ack.
2. 문의 선점, 예산 예약 commit, 엔진 시작.
3. 엔진 응답 수신, 비용/세션 저장, 초안 저장/최신 포인터 commit.
4. DM 카드 생성 요청, 원격 저장, 응답 수신, 카드 식별자 저장.
5. 수정/조회 결과 제출 검증, 새 작업 등록, 새 revision commit.
6. 게시 선점, 전송 intent commit, 네트워크 요청.
7. 각 조각의 Slack 저장, 응답 수신, 해당 ts 저장.
8. 최종 posted commit, permalink 조회, 카드 갱신.
9. 복구 작업 선점, 원격 대조, 복구 결과 commit.
10. 마이그레이션 시작/각 단계/user_version 변경/commit.

호출 횟수만 확인하지 않고 **종료 후 새 프로세스로 같은 DB를 열었을 때의 결과**를 확인합니다. 전달 불명인 경우 게시를 멈추는 것이 통과 조건이며, 무조건 자동 완주를 요구하지 않습니다.

## 오류가 실제로 잡히는지 확인

대표 P0 경로는 개발용 임시 변경으로 결함을 심어 해당 테스트가 실패하는지 확인합니다. 추가 mutation 패키지는 필요하지 않습니다.

- 승인자 검사 제거 → AUTH 테스트 실패.
- 최신 draft 조건 제거 → 오래된 카드/모달 테스트 실패.
- 이벤트 UNIQUE 또는 원자적 접수 제거 → 중복/유실 테스트 실패.
- timeout을 승인 대기로 복귀 → 쓰기 후 응답 유실 테스트 실패.
- 실제 게시본 대신 최초 초안 사용 → 후속 맥락 테스트 실패.
- 비용 누락을 0으로 처리 → 예산 우회 테스트 실패.
- raw exception 기록 → 비밀 sentinel 검사 실패.

이 작업은 임시 복사본에서만 수행하고 제품 커밋에 결함을 남기지 않습니다. 아직 mutation 검사를 실행한 것은 아닙니다.

## 실행 단계와 배포 기준

| 단계 | 통과 조건 |
|---|---|
| 명세/설계 | 상태·ack·부분 게시·권한·비용·크기 한도를 확정하고 케이스와 연결 |
| 단위/계약 | 설정·비밀·프롬프트·카드·결과 검증·권한 경계의 실제 assertion 통과 |
| 저장/프로세스 | 실제 임시 SQLite와 가짜 CLI로 commit/rollback/timeout/종료/복구 통과 |
| 통합 | FakeSlack + FakeEngine + SQLite로 전체 사용자 흐름과 경합/응답 유실 통과 |
| 내부 시험 배포 | 지원 범위의 모든 P0/P1 자동 케이스 통과, 실패·skip·xfail을 성공으로 세지 않음 |
| 회사 사용 확인 | 별도 회사 체크리스트 수행, 실제 CLI/스킬/MCP/Slack 권한·답변 품질 확인 |
| 팀 공개 | 회사 검증과 자료 공유 범위 확인까지 완료 |

ruff/형식 검사는 별도 수행합니다. 코드 coverage는 미검증 분기를 찾는 보조 자료이며 승인/전송/복구/권한의 실패 분기 누락을 허용하지 않습니다. 테스트 수/coverage 수치 하나로 제품을 완료 처리하지 않습니다.

현재는 봇 구현이 없으므로 자동 케이스는 전부 미구현이고 회사 확인도 전부 미실행입니다. 문서에 있는 테스트를 실행한 테스트처럼 보고하지 않습니다. 실제 회사 확인을 하지 못하면 그 상태를 그대로 남기고 확인된 범위만 보고합니다.

## 공식 계약 확인 자료

- [Slack conversations.replies](https://docs.slack.dev/reference/methods/conversations.replies/): cursor 페이지를 읽어야 하며 첫 페이지를 최신 전체 이력으로 간주하지 않습니다.
- [Slack chat.postMessage](https://docs.slack.dev/reference/methods/chat.postMessage/): 일부 오류도 원격 효과가 발생했을 수 있으므로 불명 전송을 구분합니다.
- [Slack section block](https://docs.slack.dev/reference/block-kit/blocks/section-block/): section text 최대 3000자, 갱신 시 block_id를 구분합니다.
- [Slack plain-text input](https://docs.slack.dev/reference/block-kit/block-elements/plain-text-input-element/): max_length 범위는 1–3000입니다.
- [Claude CLI](https://code.claude.com/docs/en/cli-reference): allowedTools는 자동 승인 규칙이며 tools는 내장 도구 노출, MCP는 별도 정책이 필요합니다. 비용 제한은 추정 사용량 기반입니다.
