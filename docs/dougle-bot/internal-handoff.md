# 자동 답변과 개발자 확인

봇은 등록된 채널의 멘션을 받아 필요한 근거를 확인하고 원래 스레드에 답합니다. 일반 문의에는 승인 DM을 보내지 않습니다. 운영 조회·코드 확인·개발자 도움·내부 오류가 있을 때만 `approver_user_id`로 지정한 담당자에게 DM을 보냅니다.

## 문의별 동작

| 상황 | 고객 스레드 | 담당자 DM |
|---|---|---|
| 확인한 답변 | 간결한 존댓말로 답변합니다. | 보내지 않습니다. |
| 질문이 모호함 | 필요한 정보를 묻습니다. | 보내지 않습니다. |
| 관련 자료 없음 | 확인한 범위에서 찾지 못한 내용을 알립니다. | 개발자 확인으로 해결할 수 있으면 요청합니다. |
| 운영·코드 확인 필요 | DM 전송 성공 후 대기 안내를 보냅니다. | 확인 대상·항목·필요한 결과를 요청합니다. |
| 내부 오류·시간 초과 | DM 전송 성공 후 대기 안내를 보냅니다. | 점검 사항과 처리 결과 입력을 표시합니다. |
| 최종 답변 전송 여부 불명 | 자동 재전송하지 않습니다. | 전송 여부 확인을 요청합니다. |

대기 안내는 자동 모드에서 문의당 한 번만 시도하며 다음 문구를 사용합니다.

> 추가 확인이 필요해 담당 개발자에게 요청했습니다. 확인되면 이 스레드에 이어서 답변드리겠습니다.

DM 전송이 실패하거나 성공 여부가 불분명하면 안내를 보내지 않습니다. 안내에는 SQL·내부 오류·완료 시각을 넣지 않으며, 최종 답변을 게시한 것으로 처리하지 않습니다. 담당자가 결과를 제출하면 같은 문의의 검증을 이어가고 원래 스레드에 답합니다. 결과가 부족하면 남은 확인만 요청하며 대기 안내를 반복하지 않습니다.

## 담당자 입력

DM 카드의 **확인 결과 입력**에는 요청한 코드·운영 상태·업무 자료의 비민감 요약을 넣습니다. **처리 결과 입력**에는 연결이나 실행 환경을 고친 내용을 넣습니다. 일반 DM 텍스트나 이미지는 문의에 자동 연결하지 않습니다.

시간을 따로 입력할 필요는 없습니다. 제출 시각은 내부에 기록하며 실제 조회 시각으로 간주하지 않습니다. 개발자 보고와 AI의 직접 조회를 구분하고, 환경 복구 보고를 원본 확인의 근거로 사용하지 않습니다. 필요한 자료는 다시 읽습니다.

운영 조회는 설정된 BigQuery 읽기 도구를 먼저 찾아 대상·스키마·최신성을 확인하도록 지시합니다. 접근 불가나 데이터 지연이 확인되면 부족한 운영 조회만 요청합니다. DM에는 막힌 이유·확인할 내용·필요한 결과를 구분하고, 검증하지 못한 SQL은 제외합니다. 조회 요청 SQL을 런타임이 실행하지는 않습니다.

<details>
<summary>개발자용 상태·중복·복구 계약</summary>

- 내부 요청은 `needs_lookup`, 처리 오류는 `failed`, 최종 답변 전송 여부 불명은 `post_unknown`입니다. 대기 안내는 DM 전송이 확인된 `needs_lookup`·`failed`에만 적용합니다.
- 대기 안내 전에 SQLite에 `handoff_notice_intent`를 선점하고 별도 `post-intents.log`에도 전달 ID를 기록합니다. 중복 호출·동시 작업·재시작은 같은 안내를 재전송하지 않습니다. 전송 실패나 불명확한 결과도 자동 재시도하지 않으며 최종 답변 처리를 막지 않습니다.
- 안내 직전에 실행 상태, 허용 채널, 문의·답변·실패 작업의 일치 여부를 다시 확인합니다. 안내 시도 전 중지·채널 제거·결과 제출로 상태가 바뀌면 보내지 않습니다. 원격 Slack 전송까지 원자적으로 잠그는 보장은 아닙니다.
- 결과 입력은 담당자·워크스페이스·문의·카드·최신 답변 또는 실패 작업을 확인합니다. 중복 제출은 작업 하나만 만듭니다. 개발자 보고는 이 문의가 요청한 미확인 `code`·`live`·`knowledge`에만 사용하며 이미지 근거를 대신하지 않습니다.
- 답변·엔진 작업 완료·자동 게시 준비 표식을 한 트랜잭션에 저장합니다. 저장 직후 종료되면 모델을 다시 호출하지 않고 저장된 답변의 게시를 진행합니다. 자동 게시 시도도 먼저 기록합니다.
- 게시 전 최신 답변·허용 채널·스레드 변경·민감정보·말투를 검사합니다. 전송 도중 종료되거나 일부 조각만 성공하면 무조건 다시 보내지 않습니다. `post_unknown`은 본문과 전달 ID가 맞는 봇 메시지의 긍정적인 증거로만 복구합니다.
- 안내와 최종 답변의 전송 기록은 분리합니다. DB만 과거로 되돌려 이미 시도한 전송 기록이 사라지면 별도 전달 기록과 대조해 검토를 요구합니다.
- 정상 자동 게시의 감사 기록은 `auto_post`입니다. 엔진에는 Slack 쓰기 도구를 허용하지 않으며 런타임이 전송합니다.

## 설정과 업데이트

`require_approval`이 없는 기존 설정도 자동 모드입니다. 새 실행 환경을 준비한 뒤 중지·시작해야 적용됩니다. `reply_mode`는 설정값이므로 `running_version`과 `update_required`도 함께 확인하세요. 토큰·Slack scope 변경은 필요하지 않습니다.

`[slack] require_approval = true`를 지정하면 검토 모드를 유지합니다. 이 모드에서는 최신 답변을 승인한 뒤 게시하며 자동 대기 안내를 보내지 않습니다. 예전 승인 대기 답변은 업데이트만으로 자동 게시하지 않습니다. 기존 지식·설정·세션·문의 기록은 보존합니다.

## 검증 범위

[자동 테스트 기록](implementation-verification.json)은 기록된 빌드와 실행 범위에 한정합니다. 현재 대기 안내의 회귀 검사는 [test_handoff_notice.py](../../dougle-bot/tests/test_handoff_notice.py)에 있습니다. 가짜 Slack·엔진과 실제 SQLite로 DM 성공·실패, 안내 중복, 재시작, 담당자 결과와 최종 답변을 검사합니다.

회사 연결과 실제 답변 품질은 [회사 수용 검증](company-acceptance.md)으로 따로 확인합니다. 실행 기록 검사만으로 질문 분류나 개발자 보고의 해석이 항상 정확하다고 보장하지 않습니다. 민감정보 검사는 패턴 검사이며 회사 자료의 공유 권한은 운영자가 정합니다.

## 개발자 응답과 직접 응대

자동 모드에서 확인·처리 결과가 저장되면 고객 스레드에 결과 접수 안내를 한 번 보낸 뒤 검증과 답변을 이어갑니다. 각 제출은 해당 작업 ID에 연결됩니다. 직접 응대 버튼은 조회 대기·실패 카드에 표시되며, 누르면 사유 입력 없이 해당 문의를 종료하고 고객에게 개발자가 직접 답변할 예정임을 알립니다. 다른 문의와 새 멘션은 계속 처리합니다.

중복 클릭·제출과 오래된 카드/모달은 다시 처리하지 않습니다. 안내 시도는 독립 게시 기록에 남기고, 전송 실패·성공 불명·시도 중 중단은 자동 재전송하지 않습니다. 안내 실패가 최종 답변 검증을 생략하거나 직접 응대를 취소하지 않습니다. 명시적 승인 모드는 자동 고객 안내를 보내지 않습니다.
