# 문맥을 이어 질문하기

이제 선택한 이전 질문·답변을 새 요청에 포함할 수 있습니다.
현재 코딩 세션을 이어 쓰는 것이 아니라 **매번 승인한 내용으로 별도 CLI 요청**을 보냅니다.

## 사용 순서

1. 새 질문을 검색하고 새 근거 묶음을 저장합니다.
2. 답변 이력의 보관함에서 **이전 문맥 선택**을 엽니다.
3. 새 묶음과 이전 답변 1~5개, 제공자·모델을 선택해 미리봅니다.
4. 전문을 확인하고 **이 문맥 고정 저장**을 누릅니다. 아직 전송하지 않습니다.
5. 승인 상태 확인 → 동의 → 승인 저장 → 별도 실제 전송 버튼 순서로 실행합니다.
6. 근거가 먼저 표시되고 임시 출력/완료 답변이 이어집니다. 중단은 기존 답변 작업 버튼을 사용합니다.
7. 성공하면 보관함에 새 답변이 자동 연결됩니다. 보관함을 새로고침하면 다음 문맥에 선택할 수 있습니다.

이미 승인/작업이 있는 묶음은 문맥을 바꿀 수 없습니다. 새 묶음을 만드세요.
문맥을 고정하면 해당 묶음의 제공자·모델·이전 답변도 고정됩니다.
빈 모델 값은 CLI 기본값입니다. 실제 실행 모델을 검증했다는 뜻은 아닙니다.

## 모델과 코드 대조

```text
conversation_request (v18, 불변 JSON)
  ├ 새 질문 bundle_id (유일)
  ├ 보관함 ID / 당시 revision
  ├ 선택한 이전 작업·질문·답변·묶음 해시
  └ 제공자 / 모델 / 요청 전문 / digest
        → answer_approval (기존 건별 승인)
        → answer_job (기존 생성·SSE·취소)
        → 완료 답변 + conversation_turn 자동 연결 (같은 트랜잭션)
```

- `ConversationRequestService`: 확인한 미리보기 해시와 실제 재검증 결과가 같을 때만 저장. 같은 요청 재시도는 기존 값 반환.
- `ConversationHistoryService`: 선택 소속/순서, 완료 작업, 과거 근거 최신성을 검사.
- `StoredAnswerContext → AnswerContextProvider`: 저장된 문맥과 현재 값을 비교. 원본 변경·작업 삭제·보관함 삭제/추가 시 사용 차단.
- `EvidenceAnswerPreview`: 문맥 없는 기존 요청은 그대로 유지. 고정 문맥은 전용 해시/모델로 구성.
- `AnswerJobService`: 접수·전송 직전·결과 저장 직전에 재검증. 이전 문맥은 사실 근거가 아니며 현재 근거 번호만 답변 검증에 허용.
- `ConversationCompletion`: 성공 답변과 보관함 연결을 원자적으로 저장. 실패/취소 시 새 턴 연결 없음.

저장 전 미리보기 해시는 기존 승인 API에서 거절됩니다. 고정 저장 후에만 해당 묶음의 승인 경로가 문맥을 포함합니다.
승인은 10분/1회이고, 저장만으로 승인하거나 생성하지 않습니다. 모델 호출 중 DB 연결을 잡지 않습니다.
요청문은 JSON 포함 20,000 UTF-16 코드 단위 한도이며 토큰 수가 아닙니다.

## API

`POST /api/workspaces/{workspaceId}/conversations/{id}/requests`

```json
{
  "selection": {
    "bundleId": "새 묶음 ID",
    "expectedRevision": 1,
    "jobIds": ["이전 완료 작업 ID"],
    "provider": "CODEX",
    "requestedModel": "선택한 모델"
  },
  "digest": "확인한 미리보기 해시"
}
```

응답은 고정 요청의 ID·범위·문맥·전문·해시입니다. 승인/작업 API는 기존 묶음 경로를 재사용합니다.
기존 `answer-preview`에 `contextRequestId`가 추가됩니다. 문맥이 없으면 null입니다.

## 삭제·한계

- 보관함 삭제는 이미 끝난 답변/근거/고정 요청을 지우지 않습니다. 고정 요청은 감사용 복사본으로 남지만 재사용은 차단됩니다.
- 새 질문의 근거 묶음 삭제는 고정 요청·연결된 승인/작업도 삭제합니다. Workspace 삭제는 모두 삭제합니다.
- 이전 작업/원본을 삭제해도 고정 문맥 복사본은 남습니다. 민감 자료 삭제 시 새 묶음도 함께 확인하세요.
- 생성 도중 문맥이 바뀌면 최종 답변을 버립니다. 이 변경을 즉시 원격 중단하는 감시는 아직 없으며 명시적 중단 버튼을 사용할 수 있습니다.
- 성공 후 보관함 revision이 증가하므로 과거 고정 요청을 새 요청처럼 재사용하지 않습니다. 다음 질문은 새 묶음으로 준비합니다.
- 자동 사실 검증은 아닙니다. 이전 답변을 원본 근거로 승격하지 않습니다.

## 검증

- 고정 저장/재시도, 변경·기존 승인/작업 차단, 제공자/모델 바인딩, 삭제 무효화.
- 승인한 전문만 모델에 전달, 완료 답변·연결 원자성, 전송 전 삭제 차단, 생성 중 삭제 시 늦은 답변 폐기.
- v17 → v18 기존 보관함 보존과 고정 요청 재시작 보존.
- UI는 명시적 고정 저장 후에만 별도 승인 화면을 노출하고 선택을 잠급니다.
- 초기 삭제 무효화 조회에서 내부 읽기 예외가 트랜잭션을 rollback-only로 만들었습니다. 읽기 검증의 예상 오류 정책을 수정하고 관련 50개 테스트가 통과했습니다.
- 전체 빌드: UI 185개, 백엔드 316개 통과 + 실제 AI opt-in 1개 미실행.
- 실제 JAR smoke 통과: 고정 요청 재시작 보존 → 별도 승인/전송 → 가상 CLI 근거 우선 SSE → 완료 턴 자동 연결. 외부 AI 호출은 없습니다.
- 실제 브라우저도 명시적 선택·고정·별도 승인·가상 CLI 전송·SSE 완료 답변·2번 턴 연결까지 통과했습니다. 근거 없는 검색 묶음은 오류로 차단했습니다.
- 네이티브 병렬 컴파일 중 브라우저 CDP가 시간 초과되어 빌드 부하를 줄인 뒤 같은 QA 공간에서 복구했습니다. 이후 빌드 작업 수 기본값은 2입니다.
- 가상 100파일 순차 검색 p95 31.24 ms, 목록 p95 10.17 ms. 동시 부하/AI 성능이 아닙니다. [측정 원본](performance-phase3-foundation.json).
