# 대화 보관함 — 완료 답변 정리

**답변 이력 → 대화 보관함 관리**에서 완료 답변을 원하는 순서로 묶습니다.
보관함 자체는 정리 기능입니다. 이전 대화를 이어 질문하려면 별도 [문맥 선택·고정·승인](context-requests.md)을 사용합니다.

## 사용법

1. 보관함 이름을 입력하고 **보관함 만들기**를 누릅니다.
2. 답변 이력 목록에서 완료 답변을 선택합니다.
3. 보관함에서 **현재 완료 답변 추가**를 누릅니다.
4. 보관함의 번호를 누르면 당시 근거와 답변을 다시 봅니다.
5. 보관함 삭제는 재확인 후 실행합니다. 답변·근거 원본은 남습니다.

생성·추가·삭제는 로컬 DB 작업입니다. AI 호출·외부 전송·새 승인·지식 생성은 하지 않습니다.
같은 답변을 같은 보관함에 다시 추가해도 중복되지 않습니다. 여러 보관함에 연결하는 것은 가능합니다.
이 순서는 **사용자가 정리한 순서**이지 실제 AI가 이전 턴을 읽었다는 뜻이 아닙니다.

## 실제 모델과 동작

```text
Workspace
  └ conversation: 이름, revision, 생성 시각
      └ conversation_turn: position, job_id, 추가 시각
          └ answer_job → evidence_bundle: 기존 완료 답변과 당시 근거

AnswerHistoryPanel → ConversationShelf
  → ConversationController → ConversationService → ConversationStore
      → JdbcConversationStore → SQLite v17
```

| 규칙 | 실제 구현 |
|---|---|
| 이름 | 제어 문자 없는 1~120자, 앞뒤 공백 제거 |
| 수량 | Workspace당 보관함 100개, 보관함당 연결 100개 |
| 순서 | 추가할 때 revision 증가, 그 값을 position으로 저장 |
| 동시 추가 | 조회한 expectedRevision 비교. 먼저 추가한 요청만 성공, 나머지 409 |
| 재시도 | 같은 보관함/작업은 기존 연결 반환. 새 승인이나 생성 없음 |
| 연결 대상 | 같은 Workspace의 SUCCEEDED + 답변이 있는 작업만 |
| 격리 | 서비스의 Workspace 검사와 두 복합 외래 키로 교차 연결 차단 |
| 저장 | 답변/근거를 복제하지 않고 job ID만 연결 |

트랜잭션과 기존 단일 연결 풀로 로컬 쓰기를 직렬화합니다.
삭제된 연결의 번호는 재사용하지 않아 번호가 비어 있을 수 있습니다.
이름 변경·순서 변경·연결만 제거·실시간 목록 동기화는 아직 없습니다.
다른 화면에서 변경했다면 새로고침 후 보관함을 다시 선택하세요.
닫기는 브라우저 요청 관측만 중단합니다. 이미 서버에 도착한 로컬 변경을 되돌리는 기능은 아닙니다.
생성 요청 자체에는 멱등 키가 없으므로 응답이 끊기면 목록부터 새로고침하세요.

## 삭제와 업그레이드

- 보관함 삭제: 보관함과 연결만 제거. 답변/근거/승인과 실행 중 작업은 유지.
- 근거 묶음 삭제: 기존 정책대로 답변 작업 삭제, 연결도 함께 제거. 빈 보관함은 유지.
- Workspace 삭제: 해당 보관함·연결·기존 자료 전체 제거.
- 원본 파일만 삭제: 보관한 답변/근거는 남음. 민감 자료 완전 삭제와 혼동하지 마세요.
- v16 → v17: 기존 자료 보존, 빈 보관함 테이블 추가. 과거 답변을 자동 분류하지 않음.
- 업데이트 전 앱 종료 후 데이터 디렉터리 백업. v17 DB를 구버전 앱으로 열지 마세요.

## API

기본 경로: `/api/workspaces/{workspaceId}/conversations`

| 요청 | 입력 / 결과 |
|---|---|
| GET 기본 경로 | 보관함 목록 |
| POST 기본 경로 | `{"title":"관측 기록"}` → 201 보관함 |
| GET `/{id}` | `{conversation, turns}` (position 순서) |
| POST `/{id}/turns` | `{"jobId":"…","expectedRevision":0}` → 갱신된 상세 |
| DELETE `/{id}` | 204, 보관함과 연결만 삭제 |

변경 요청은 기존 `X-Forge-Client: 1` 헤더가 필요합니다.
400은 입력 오류, 404는 해당 Workspace의 자료 없음, 409는 revision 충돌/한도/완료되지 않은 답변입니다.
상세에는 답변 본문을 중복 반환하지 않습니다. 기존 작업/근거 상세 API를 사용합니다.

## 다음 구현 — 아직 미구현

읽기 전용 [이전 문맥 미리보기](conversation-context.md)는 추가했습니다. 아래 영속 요청·전용 승인·전송은 아직 미구현입니다.

실제 대화 턴은 보관함의 정리 순서와 구분해야 합니다.
다음 단계에서는 새 질문과 선택한 이전 문맥을 불변 요청으로 만들고,
포함된 이전 답변·근거·모델·토큰 예산을 미리보기에 표시한 후 새 승인을 받습니다.
이전 AI 답변은 사실 근거로 승격하지 않습니다. 기존 답변 요청 digest를 그대로 재사용하지 않습니다.
승인 후 문맥 변경/삭제 시 실행을 차단하고, 재연결은 관측만 해야 합니다.

## 검증

- 백엔드 통합 9개: 순서/재시도, 충돌/미완료 차단, Workspace·FK 격리, 삭제 보존, 번호 재사용 방지, 입력/한도, 동시 추가, 연결 한도, HTTP 경계.
- 마이그레이션 추가 1개: v16 자료 보존·자동 이관 없음·재시작 후 연결 보존. 기존 마이그레이션도 v17까지 검증.
- UI 6개: 명시적 조회/생성/추가, 삭제 재확인, 범위 검사, 닫기 시 늦은 응답 차단.
- 초기 FK 테스트는 실제 차단됐지만 SQLite의 예외 변환 타입을 잘못 예상해 실패했습니다. 실제 DataAccessException과 FOREIGNKEY 오류를 확인하도록 수정한 뒤 관련 26개 테스트가 통과했습니다.
- 2026-10-22 전체 빌드 성공: UI 155개, 백엔드 285개 통과 + 실제 AI opt-in 1개 미실행.
- 실제 JAR smoke 통과: 보관함 연결의 재시작 보존, 중복 추가 방지, 보관함 삭제 후 답변/근거 보존을 검증했습니다. 기존 SSE/중단/재시작도 통과했습니다.
- 실제 브라우저: 생성 → 완료 답변 추가 → 중복 추가해도 1개 → 중단 답변 추가 비활성 → 번호로 답변 열기 → 재확인 삭제 → 답변 재조회와 근거 우선 표시를 확인했습니다.
- 가상 자료·가상 CLI만 사용했고 실제 AI 전송은 하지 않았습니다. 브라우저 QA 공간과 임시 서버를 종료했습니다.
- 작은 가상 파일 100개 순차 검색 p95 16.96 ms. 부하/AI 성능은 아닙니다. [측정 원본](performance-phase3-foundation.json)
- 메인 JS 500.36 kB로 기존 Vite 500 kB 경고는 남습니다. 이력/보관함은 지연 로딩 청크 9.28 kB이며 빌드는 성공했습니다.
