# 대용량 추출·저장 수정 — 0.1.30

T0161–T0165의 100 MiB 텍스트 중간·끝 누락 원인은 `TikaJavaAnalyzer`의 32,000,000자 출력 제한과 추출문 전체를 하나의 String으로 전달하는 계약이었다. 이 작업은 제한값을 늘리지 않고 파트 저장으로 바꾼다. 2026-10-28 Intel0.1.30/DB v30 설치 검증을 완료했다. [검증 범위](evaluations/remaining-fixes-20261027.md)는 전체 인수와 구분한다.

## 저장 및 색인 계약

추출 저장 예산은 문서당 **512 MiB**다. 디스크 스풀의 UTF-8 본문과 파트별 4바이트 길이 헤더를 합산하여 쓰기 전에 검사한다. 인라인 본문도 UTF-8 바이트 예산을 검사한다. 압축 PDF/Office 입력이 이 예산보다 크게 펼쳐지면 임시 스풀을 닫고 `ERROR`와 문서 분할/축소 안내를 반환한다. 앞부분만 `PARTIAL`로 저장하지 않는다. 예산 아래에서는 전체 본문을 유지하며, 100 MiB 자료의 1/50/99 MiB 표식 인수 조건은 그대로다. 작은 예산을 주입하는 패키지 전용 생성자로 경계·UTF-8 바이트·파서 예외 전달·취소 우선순위를 검사하므로 예산 회귀에 512 MiB 입력이 필요하지 않다. Tika 파서 자체의 임시 자원 사용량 전체를 제한하는 예산은 아니다.

- 작은 추출문은 최대 2,000,000자까지 기존 `Analysis.text()` 계약을 유지한다. 더 큰 추출문은 임시 파일로 내려쓰고, 최대 65,536 UTF-16 코드 단위의 파트를 순차 조회한다. 전체 추출 길이에 비례하는 대형 String이나 byte 배열을 만들지 않는다. 파트 위치 목록은 파일 크기에 비례하는 작은 메타데이터다.
- CRLF/CR을 LF로 바꾸고 NUL을 제거한다. NFC 정규화 경계에서 결합 문자·한글 자모·서로게이트를 보존한다. 큰 문서의 앞뒤 공백은 보존한다. 하나의 결합 문자 연속 구간이 파트 창보다 길면 추출 오류로 종료하며 부분 성공으로 숨기지 않는다.
- 큰 문서의 `text()`는 첫 파트이고 `textTruncated=true`다. 내부 소비자는 `textParts()` 전체를 사용해야 한다. `parts`는 JSON에 노출하지 않는다. PDF 미리보기의 `reason`은 앞부분 미리보기임을 알린다. UI는 supported=true여도 reason을 표시한다.
- DB v30의 `extracted_text_part`와 `source_analysis_text_part`는 문서 및 체크포인트 파트를 저장한다. 본문 메타데이터·파트 교체·검색 큐는 같은 트랜잭션이다. 기존 문서/체크포인트 외래 키 삭제와 함께 파트도 삭제된다. 저장 성공·실패 시 임시 스풀을 닫는다. JVM 비정상 종료 시 남은 OS 임시 파일의 별도 회수 정책은 후속 과제다.
- 체크포인트 JSON에는 작은 메타데이터만 저장한다. 큰 본문을 JSON으로 합치지 않고 재시작 후 파트를 순서대로 읽는다. `save`/`checkpoint`는 전달된 임시 Analysis의 소유권을 소비한다. 저장 후 반환하는 수동 분석 결과는 영속 저장소에서 다시 조회한다.
- `SearchIndex.Document`의 기존 생성자는 유지한다. 큰 문서는 `textHash()`가 전체 파트의 UTF-8 SHA-256을 계산하고 `chunks()`가 저장 경계와 무관하게 연속 검색 창·전역 행/오프셋을 만든다.
- 검색 큐 소비는 `SearchCatalog.withDocument`의 읽기 트랜잭션 안에서 지연 파트를 읽는다. 색인 중 본문이 교체되어 서로 다른 버전의 파트가 섞이지 않게 한다. 파트 조회·해시·분할·저장은 인터럽트에 즉시 반응한다.

## 이전 자료와 소비자 감사

- v30은 기존 추출문과 불변 근거를 보존한다. 기존 32M 잘린 업로드는 수동 재분석 또는 재업로드해야 뒤쪽 본문을 복구할 수 있다. 스키마 변경이나 Lucene 재색인만으로 원래 없던 본문을 복구하지 않는다.
- 이전 `앞부분만 검색` 오류 체크포인트는 마이그레이션에서 제거한다. Source 비교 기준은 그 오류가 있는 파일을 변경 대상으로 처리하므로 다음 동기화에서 원본이 바뀌지 않았어도 다시 분석한다. 실패하면 이전 자료를 보존한다. 마이그레이션 자체는 외부 재수집을 실행하지 않는다.
- 답변 근거 작성·검증·원본 해시는 `EvidenceSourceStore`/`EvidenceMaterial`로 통합했다. 원본 BLOB은 8 MiB 단위 해시, 추출문은 전체 파트 해시와 제한된 원문 범위 검사를 사용한다. 읽기 트랜잭션의 callback 안에서 동일 스냅샷을 유지한다. 100 MiB 뒤쪽 인용·오래된 원문 거부·단일 연결 풀·동시 교체 회귀가 통과했다.
- 제한형 기존 아카이브는 원본당 1 MiB 한도를 유지한다. 압축 PDF 등에서 추출문이 스풀 크기가 되면 가져오기를 거부해 prefix만 검사·재연결하는 경로를 막는다. 원본 다운로드/내보내기 바이트는 이 수정으로 변경하지 않는다.
- 기존 편집형 지식 문서의 `KnowledgeStore.Material`/스냅샷 경로는 별도 감사 대상이다. 대화의 로컬 조사 검색은 새 근거 포트를 사용하지만 이전 지식 편집 경로까지 동일한 스트림 계약으로 간주하지 않는다.

## 검증 상태와 남는 한계

전체 Java 회귀는1099통과·25 opt-in생략이다. 별도 opt-in 실행에서100 MiB 영속 저장·재열기·색인 교체를 확인했다. 독립 javac/java 검사로 100 MiB 스풀·검색 창 순회를 `-Xmx64m`에서 수행했고 최종 문자 위치·행/오프셋 일치·명시적 파일 삭제를 확인했다. 이는 Tika 파서·JDBC·원본 BLOB·실제 모델을 포함하는 전체 프로세스 메모리 측정이 아니다.

회귀 테스트: `AnalyzerTest`, `ExtractedTextWriterTest`, `StreamingTextChunksTest`, `StreamingCollectionTest`, `LargeFileIngestionTest`, `MigrationTest`. `LargeFileIngestionTest`는 기본 4 MiB의 저장·체크포인트·DB/색인 재열기·50개 경쟁 문서·반복 색인·교체·삭제를 검사한다. `-Dforge.acceptance.large=true`는 같은 경로를 100 MiB와 1/50/99 MiB 표식으로 검사한다. `FileAcceptanceTest`의 기존 case ID와 표식 조건은 유지하며 전체 파트를 검사하도록 바꾼다. 이 파일 인수 테스트 자체의 UI·실제 앱 재시작·의미 검색·답변 한계 표시는 유지한다.

수동 재분석의 `LibraryStore.content()`와 업로드/Source 원본 BLOB 저장에는 여전히 원본 전체 byte 배열이 있다. 저장 포트에는 기존 스트림 API가 없다. Tika의 개별 PDF/Office 파서 내부 메모리도 이 변경만으로 제한되지 않는다. 따라서 추출문→파트 저장→색인의 제한된 메모리 처리를 전체 수집 경로의 일정 메모리 보장으로 확대하지 않는다. T0161–T0165는 검사한 계층에서 PASS지만 UI/답변 전체 인수 판정은 PARTIAL이다.
