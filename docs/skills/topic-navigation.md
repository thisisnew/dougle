# 필요한 설명부터 찾아 읽기

목차에서 토픽을 찾고 토픽의 안내로 읽을 항목을 좁힙니다. 답변에는 안내가 가리키는 설명뿐 아니라 연결된 조건·예외·근거도 필요합니다. [지식 저장 구조](architecture.md)

## 저장 방식

새로 저장하거나 실제로 갱신하는 토픽 앞에 짧은 안내를 둡니다. 다음은 가상 예시입니다.

```text
주제: 입하 확정
범위: receiving
찾을 표현: 입고 확정, confirmReceipt
다루는 내용: 확정 조건·기록 위치·취소 처리

저장 위치 → C01
제외 조건 → C02
취소 처리 → C03
주의: C01의 설명에는 C02 조건도 함께 확인
```

실제 항목에는 원본 위치·확인 시각·확인 상태를 함께 기록합니다. 안내는 위치를 찾는 용도이며 그 자체를 사실의 근거로 쓰지 않습니다.

## 질문할 때

1. 공통 목차에서 확인된 테넌트·서비스 범위와 토픽을 찾습니다. 기존 하위 목차가 있으면 사용하되 공통 자료와 허용된 교차 서비스 의존 관계를 놓치지 않습니다.
2. 제목·용어·코드 식별자를 검색해 읽을 위치를 좁힙니다.
3. 해당 항목과 연결된 조건·예외·충돌·출처를 읽습니다.
4. 근거가 부족하거나 오래됐다면 다른 항목과 원본으로 범위를 넓힙니다.

제목과 항목 목록이 같아도 같은 제목 아래 예외·정정이 추가됐을 수 있습니다. `complete` 표시만으로 다른 구간을 읽지 않아도 된다고 판단하지 않습니다. 안내는 검증 당시의 본문 식별값 또는 안내와 본문을 함께 검증한 불변 스냅샷 기록과 맞아야 합니다. 호스트가 이를 확실히 확인하지 못하면 관련 후보 노트 전체와 연결된 조건·예외를 읽습니다.

확인은 현재 질문의 후보에 한정하며 전체 지식의 해시 계산·일괄 변환·추가 실행기를 요구하지 않습니다. “전부 알려 주세요”라는 요청이나 잘린 결과, 부족한 근거는 다른 후보와 원본까지 범위를 넓힐 이유입니다. 실제 코드 동작은 코드 조사로, 현재 상태는 새 조회로 확인합니다.

## 갱신할 때

바뀐 설명과 영향을 받는 항목만 수정합니다. 먼저 안내를 보완 대기로 표시하고 설명·조건·근거의 연결을 확인한 뒤 안내를 완성합니다. 연결 대상의 이동·삭제·정정·범위 변경은 참조하는 노트의 본문이 그대로여도 재검사해야 합니다. 중간에 끊기거나 검증 기록이 맞지 않으면 관련 노트 전체를 읽습니다. 원본을 읽지 않고 형식만 정리한 기록은 새로 검증한 지식이 아닙니다.

여러 호스트가 같은 기록을 쓸 때는 실제 조건부 쓰기(CAS), 모든 작성자가 따르는 잠금, 또는 확인된 단일 작성자 경로가 필요합니다. 저장 직전 다시 읽는 것만으로 경합을 막을 수는 없습니다. 보호 수단이 없거나 소유권을 잃으면 후속 저장을 멈추고 정정·충돌과 미완료 작업을 보존합니다. 파일별 CAS도 여러 파일 전체를 한 번에 반영하는 트랜잭션은 아닙니다.

긴 토픽은 목차·항목별 읽기를 우선합니다. 실제 업무가 나뉘고 기존 링크를 보존할 수 있을 때만 분리합니다. 공유할 때도 설명에 필요한 조건·예외를 포함하되 허용한 공유 범위를 넘지 않습니다.

## 기존 사용자

스킬 업데이트는 지식 파일을 일괄 변경하지 않습니다. 기존 형식을 검색하고 읽을 수 있으며 쓰기가 금지돼도 확인한 근거로 답할 수 있습니다. 새로 저장하거나 실제로 갱신하는 토픽부터 안내를 보완하며 기존 소스·주장 ID·상대 링크·정정·공유 이력을 유지합니다.
