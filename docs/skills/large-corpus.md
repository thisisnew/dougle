# 자료가 많을 때는 어떻게 처리하나요?

**Markdown을 유지하고, 바뀐 부분을 먼저 찾습니다.** 지식용 SQLite는 도입하지 않았습니다.

| 작업 | 읽고 처리할 범위 | 하지 않는 일 |
|---|---|---|
| Connect | 처음에는 요청한 범위를 나눠 읽고, 재연결은 변경분부터 확인 | 전체 원본을 한 번에 요약 |
| 질문 중 갱신 | 질문에 필요한 원본과 관련 조건·근거 | 모든 자료가 최신이 될 때까지 대기 |
| Fetch | 팀 저장소의 변경 파일과 연결된 지식 | 기존 지식 덮어쓰기·원본 서비스 재수집 |
| Publish | 내 변경분과 팀 변경분을 합친 공유 패키지 | 모든 토픽 재작성·자동 원본 갱신 |

별도 Reload 명령은 없습니다. 질문할 때 필요한 갱신을 수행하며, 갱신했다고 자동 Publish하지는 않습니다.

## 예: 자료가 1만 개이고 10개만 바뀌었다면

먼저 파일 목록·내용 지문을 비교합니다. 검증한 비교 기록이 있다면 바뀐10개와 그 영향을 받는 조건·근거를 확인합니다. 나머지 문서를 AI가 다시 정리하지 않습니다. 목록 비교 자체는 전체 파일 수에 따라 시간이 들 수 있습니다.

처음 가져오거나 믿을 수 있는 비교 기록이 없으면 전체 범위를 나눠 확인해야 합니다. 파일명·수정 시각만 같다고 내용을 같다고 판단하지 않습니다. 기존 기준점이 손상됐다면 복구하거나 중단하며, 첫 가져오기로 간주해 덮어쓰지 않습니다.

**공유할 변경이 있다면 민감정보 검사는 최종 패키지 전체에 실행합니다.** 이 단계는 변경된 파일만 검사하는 방식으로 줄이지 않았습니다. 실제 변경이 없다면 중복 커밋을 만들지 않습니다.

## 바뀐 자료도 아주 많다면

한 번에 처리할 분량을 나누고 완료·미완료 항목을 로컬에 남깁니다. 다시 실행하면 원격 버전과 로컬 변경을 확인한 뒤 이어갑니다. 일부만 끝났을 때 전체 갱신·병합 완료로 표시하지 않습니다.

동료가 같은 지식을 고쳤다면 양쪽 주장과 근거를 보존합니다. 게시 직전 팀 저장소가 바뀌면 다시 비교하며, 계속 바뀌면 중단합니다. 마지막 작성자가 앞사람의 내용을 덮어쓰는 방식이 아닙니다.

이 절차는 호스트 AI가 기존 파일·Git 도구로 수행합니다. 별도 동기화 엔진이나 자동 백그라운드 작업은 아닙니다.

## Slack 답변이 느릴 때

봇의 **2. 상태 확인**에서 최근 문의의 `recent_timings`를 확인할 수 있습니다.

- 큐 대기와 실제 처리 시간을 구분합니다.
- 자료 탐색·원본 조회·답변 규칙 적용 등 관측된 단계 시간을 남깁니다.
- 근거 보완인지, 말투 보완인지 재시도 이유를 구분합니다.

단계 시간은 진행 신호 사이의 시간입니다. 모델의 순수 추론 시간이나 각 도구의 정확한 실행 시간은 아니며, 입력·출력 문자 수도 실제 과금 토큰 수와 다릅니다.

같은 문의에서 근거 검증을 마치고 존댓말·출처 배치만 고칠 때는 조사 결과를 재사용합니다. 운영 현재값·미확인 근거·새 질문·세션 유실에는 적용하지 않습니다. i-have-adhd·plain-language 실행과 승인자의 게시 검토는 유지합니다.

## 무엇을 측정했나요?

[측정 결과](large-corpus-benchmark.json)는 가상 Markdown 파일에 실제 민감정보 검사 스크립트를 실행한 결과입니다. 변경 전후 최종 파일 지문과 검사 파일 수를 비교합니다. 이 수치는 검색·답변 전체 속도나 실제 회사 지식의 병합 품질을 뜻하지 않습니다.

같은 개발 Mac에서 파일당4 KiB, 크기별 전후1회씩 측정했습니다. 검사 파일 수와 최종 패키지 지문이 모두 일치했습니다.

| 파일 수 | 변경 전 | 변경 후 |
|---|---:|---:|
| 100개 | 8.8초 | 4.8초 |
| 1,000개 | 100.5초 | 57.1초 |
| 5,000개 | 474.3초 | 338.3초 |

5,000개에서는 약29% 단축됐지만 여전히 약5분38초가 걸렸습니다. **전체 검사 비용이 사라진 것은 아닙니다.** 개발 중 다른 검사도 병행한 단일 측정이며 M Mac에서의 동일 성능이나 모든 자료의 처리 시간을 보장하지 않습니다.

기존 검사 규칙을 유지하면서 파일마다 반복하던 외부 명령 실행을 줄였습니다. 실제 회사 Slack의 답변 지연은 새 계측 기록으로 원인을 확인해야 합니다. 많은 실제 변경·최초 가져오기·전체 민감정보 검토 비용까지 없어지지는 않습니다.

개발 환경에서 재측정하려면 다음을 실행합니다. 스킬 사용자가 실행할 명령은 아닙니다.

```sh
python3 scripts/benchmark-publish-sensitive.py --counts 100 1000 5000 --output benchmark.json
```

[5,000개 파일 Git 검사](large-corpus-git-verification.json)에서는 변경10개·그대로인4,993개를 구분하고 캐시 변조·고정한 버전의 일관성을 확인했습니다. 호스트 AI가 실제로 해당 병합을 수행했다는 결과는 아닙니다.

이전 검사 스크립트를 `--baseline /path/to/old-check-sensitive.sh`로 지정하면 같은 파일에서 전후 비교합니다.
