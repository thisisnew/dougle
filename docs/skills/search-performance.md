# 검색 속도를 높이는 방법

더글은 Markdown 목차로 읽을 범위를 좁히고 호스트의 검색·조회 도구를 사용합니다. 지식용 SQLite나 Lucene 색인은 사용하지 않습니다.

## 검색 절차

| 단계 | 처리 |
|---|---|
| 목차 탐색 | 업무 주제·한영 동의어·코드 식별자로 토픽과 출처 위치 확인 |
| 부분 읽기 | 관련 항목과 정확한 원본 위치부터 읽고 조건·예외까지 확인 |
| 조회 묶기 | 호스트가 지원하면 독립 조회를 병렬 처리. 기억 저장은 순서대로 실행 |
| 근거 재사용 | 현재 문맥의 유효한 근거 재사용. 기한 경과·변경·충돌은 재확인. 구현은 코드 조사, 현재 상태는 새 조회 |
| 검색 확대 | 근거가 부족하거나 전체 목록이 필요하면 다른 후보와 원본으로 확대 |

기존 지식을 일괄 재정리하지 않고 필요한 토픽의 목차부터 보완합니다. 끊기거나 오래된 안내는 원래 자료 범위에서 다시 검색합니다. [토픽 안내와 호환](topic-navigation.md) · [탐색 비교 평가](retrieval-evaluation/README.md)

## Lucene을 붙이면 빨라지나요?

[Apache Lucene](https://lucene.apache.org/core/index.html)은 전문 검색·순위 검색·증분 색인을 지원하는 Java 라이브러리입니다. 아래는 도입 선택지의 비교이며 현재 구현에 포함되지는 않습니다.

| 방식 | 기대 이점 | 추가 비용·한계 |
|---|---|---|
| 현재 목차 + 호스트 조회 도구 | 기존 설치 방식 유지, 불필요한 읽기 감소 | 모델·도구의 검색 품질에 영향받음 |
| Lucene 로컬 실행기 | 많은 문서에서 후보 검색·순위화 | Java 환경, 색인 생성·갱신·삭제·권한 처리와 연결 코드 필요 |
| 회사의 기존 검색 도구 | 이미 구축한 색인 사용 | 제공 도구·검색 권한·최신성에 의존 |

Lucene은 서버 제품이 아니므로 별도 서버가 반드시 필요한 것은 아닙니다. 다만 스킬에서 호출할 실행 계층은 필요합니다. 로그인·원격 다운로드·갱신·답변 생성이 병목이면 색인만으로 전체 대기 시간을 크게 줄이기 어렵습니다.

## 실제로 측정할 것

같은 자료와 질문으로 아래 단계를 나눠 비교합니다.

| 단계 | 확인할 항목 |
|---|---|
| 자료 탐색 | 목차·파일 검색 시간, 후보 수, 읽은 파일 수 |
| 원본 확인·갱신 | 원격 조회 시간, 권한 대기, 실제 읽은 범위 |
| 답변 생성 | 첫 응답·완료 시간, 불필요한 반복 |

새 주제·반복 질문·원본 변경 후 질문·동의어 질문을 구분하고 출처 누락·오답·변경 반영도 확인합니다. 봇의 단계별 관측 시간과 재시도 종류는 [대용량 처리와 계측](large-corpus.md)에서 설명합니다.

기존 평가만으로 실제 회사 문의의 배속이나 지연 절감률을 제시할 수는 없습니다. 로컬 텍스트 검색이 병목으로 확인된 뒤에 선택적 색인을 검토합니다. [문맥 사용량과 정확도 평가](context-optimization.md)
