# 03. 근거 연결 복구와 좁은 재조사

## 이유
#77은 첫 시도 source_mismatch, 재시도 unknown_receipt로 실패했습니다. 실제 자료가 없어 실패한 것인지, 읽은 자료의 번호를 잘못 연결했는지 구분해야 합니다.

## 구현
- 성공한 도구 결과에 긴 영수증 ID와 함께 r_로 시작하는 짧은 별칭을 제공합니다.
- 현재 실행에 실제 존재하는 영수증만 연결합니다. 잘못 적은 ID나 잘못 연결한 ID는 출처 대상·버전·관측된 행 범위를 만족하는 후보가 정확히 하나일 때만 복구합니다.
- 여러 후보, 읽지 않은 행, 다른 파일/커밋, SQL live 근거는 자동 복구하지 않습니다.
- 형식/표현 보완에서 이전 실행 근거를 재사용하는 기존 경로는 이 자동 연결의 대상에서 제외합니다. 기존 보완 계약을 약화하지 않습니다.
- research 재시도에는 직전 읽기의 위치 힌트를 전달합니다. 원문을 복제하지 않으며 옛 영수증 ID를 새 실행 증거로 사용할 수 없습니다. 필요한 읽기를 다시 수행합니다.

## 기대효과
실제로 읽은 근거의 번호 연결 오류 때문에 전체 문의가 재실행되는 횟수를 줄입니다. 문장 내용이 원문에서 도출되는지는 별도 정확도 검증 대상입니다. 자료가 없거나 모호한 경우를 자동 정답 처리하지 않습니다.

## 회사 시험
#72/#76/#77 유형을 동일 지식 스냅숏으로 비교합니다. 질문별 시도 수, status.recent_retry_reasons와 recent_read_failures, 실행별 토큰을 기록합니다. 자동 연결이 있었다면 receipt_binding_repaired 감사 이벤트에 실행과 체크 번호만 남습니다. 성공만 보지 말고 원본과 결론/조건/예외를 대조합니다.

## 실패 시
unknown_receipt가 계속되면 새 호출에서 실제 읽기가 있었는지, source_mismatch면 원문 커밋/경로/행 범위가 맞는지 확인합니다. 근거 검사를 끄거나 과거 문의의 영수증을 끼워 넣지 마세요. 같은 파일을 여러 번 읽어 후보가 모호하면 자동 복구가 되지 않는 것이 정상입니다.

## 개발 검증
별칭/유일한 위치 복구, 다른 파일/미열람 행/다중 후보 거절, 기존 verification 보완 경계 검사 통과. 전체 검증은 09에 기록합니다.
