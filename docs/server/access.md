## 읽기 권한과 공개 권한

서버가 읽을 수 있는 자료와 질문 채널에 공개할 수 있는 자료를 구분합니다. 공개 답변에서 출처를 숨겨도 본문에 비공개 내용이 포함되면 노출입니다.

첫 구현은 채널별 도메인·자료 범위를 명시적으로 허용합니다. 각 자료에는 소유자, 분류, 사용할 수 있는 채널 또는 그룹을 등록합니다. 질문자 개인에게만 허용된 내용을 채널 전체에 보내지 않습니다. 채널 공개 범위가 확인되지 않거나 Slack Connect 외부 참여자가 있으면 별도 허용 전까지 제한합니다.

자료 하나에 여러 권한이 섞이면 허용된 문서·주장 단위까지 나눕니다. 첫 버전에서 세분화가 어렵다면 전체 묶음에 가장 제한적인 공개 범위를 적용합니다. 여러 근거를 합친 답변은 모든 근거가 목적지에 공개 가능해야 합니다. 정책 정보가 없으면 공개를 허용하지 않습니다.

권한 검사는 검색 전, 파일·도구 읽기 전, 캐시 재사용 전, 공개 게시 직전에 수행합니다. 내부 DM도 수신자가 볼 수 있는 자료만 포함합니다. 서비스 계정 권한이 크다는 이유로 질문의 범위를 넓히지 않습니다.

권한을 철회하면 정책 버전을 올리고 관련 캐시·세션·게시 예약을 무효화합니다. 이미 모델 문맥에 들어간 내용을 프롬프트로 잊으라고 지시하는 것으로 대신하지 않습니다. 외부 호출 중인 요청은 취소를 시도하고 새 호출·게시를 막습니다. 이미 전송한 정보의 회수는 별도 운영 절차로 처리합니다.

## 원본 연결 목록

새 자료는 관리자가 연결 목록에 등록해야 합니다. 질문에 붙은 임의 URL이나 문서 안의 명령이 서버 연결을 추가할 수 없습니다.

```text
source_id, domain_id, owner, classification, allowed_audiences
source_kind: code | document | warehouse | operational | kafka
endpoint_ref, credential_ref, allowed_resources, reader_capabilities
freshness_policy, observed_lag?, timeout, max_rows, max_bytes
support_route_id, enabled, policy_version
```

주소·계정의 실제 값은 회사 설정과 시크릿 저장소에 둡니다. 공개 레포에는 예시만 둡니다. URL 요청은 목적지 allowlist, redirect 재검사, 내부 메타데이터 주소 차단을 적용합니다. 자료가 요청한 추가 연결·로그인·쓰기 명령은 실행하지 않습니다.

## BigQuery와 운영 DB 선택

질문을 먼저 필요한 사실로 바꿉니다. 예를 들어 “지금 운영 중인 센터 수”라면 센터의 정의, 활성·삭제 조건, 집계 시점이 필요합니다. 테이블 이름만 알아도 된다고 판단하지 않습니다.

| 상황 | 조회 방향 |
|---|---|
| 과거 추세·일별 집계 | 의미와 범위가 맞는 BigQuery 자료 |
| 현재값이지만 허용 지연 안에서 사본 사용 가능 | 적재 완료 시각·지연이 확인된 BigQuery 자료 |
| 즉시 반영된 상태가 필요 | 승인된 운영 조회 경로 |
| 사본 지연·스키마·활성 조건 불명 | 해당 정보를 먼저 확인하거나 개발자에게 구체적으로 요청 |
| 도구·권한·네트워크 부재 | 확인하지 못한 항목을 내부 요청으로 전달 |

도구 이름을 모델이 기억하는지에 맡기지 않습니다. 런타임이 실제 연결의 capability 목록을 제공하고 조회 계획에는 선택한 source ID와 이유를 기록합니다. BigQuery가 등록돼 있는데 사용하지 않았다면 부적합한 이유가 남아야 합니다. 사용 가능한 연결을 시도하지 않고 “셸이 없어서 DB를 못 봤다”고 결론내리는 경로를 회귀 테스트로 막습니다.

BigQuery 조회 성공 시 `queried_at`과 데이터의 `data_as_of`를 구분합니다. 방금 실행한 쿼리도 오래된 사본을 읽을 수 있습니다. `data_as_of`를 모르면 운영 최신값으로 단정하지 않습니다.

## SQL 실행 계약

조회 연결이 스키마 탐색, 허용 테이블·컬럼 확인, SQL 검증, 비용·시간 제한, 결과 마스킹을 담당합니다. AI가 생성한 문자열을 바로 운영 DB에 전달하지 않습니다.

1. 허용된 스키마에서 테이블·조인·조건을 확인합니다. 모르는 컬럼을 지어내지 않습니다.
2. 실행 DB 문법에 맞는 파서와 정책으로 단일 읽기 문장인지 확인합니다. 주석·문자열·CTE·여러 문장·쓰기 함수·외부 export를 구분합니다.
3. 읽기 전용 계정과 세션 설정으로 실제 쓰기를 막습니다. 문자열에 `SELECT`가 있다는 검사만으로 허용하지 않습니다.
4. 가능한 경우 읽기 복제본·승인된 뷰를 사용합니다. 파라미터 바인딩을 쓰고 테이블 식별자는 allowlist에서 선택합니다.
5. 서버와 DB 양쪽에서 실행 제한·결과 행·바이트 제한을 둡니다. `LIMIT`만으로 스캔 비용이 제한된다고 판단하지 않습니다.
6. BigQuery에는 지원되는 dry run과 `maximum_bytes_billed`를 적용합니다. [비용 제한 공식 안내](https://docs.cloud.google.com/bigquery/docs/best-practices-costs)
7. 원본 결과는 최소 범위만 읽고 민감 필드를 제거한 뒤 AI에 전달합니다. 결과가 잘렸으면 완전한 집계·목록으로 설명하지 않습니다.
8. source ID, 실행자, 쿼리 지문, 범위, 실제 관측 시각, 소요 시간, 처리량, 성공·실패를 기록합니다. 쿼리 파라미터·원시 행 전체를 일반 로그에 남기지 않습니다.

집계 결과가 0인 경우와 조회 실패·빈 권한 범위·사본 지연을 구분합니다. 엔진 도구 성공 기록은 연결이 생성한 영수증과 대조합니다. 그럴듯한 쿼리가 생성됐다는 사실은 실행 성공이 아닙니다.

운영 DB 접근이 VDI로만 허용되면 회사 승인 없이 별도 우회 경로를 만들지 않습니다. 사내망 조회 서비스나 read-only 연결을 승인받기 전에는 개발자 요청이 정상 경로입니다.

## Kafka·브라우저·이미지

Kafka는 허용된 토픽·consumer group의 상태 조회 등 목적별 읽기 기능을 제공합니다. 메시지를 읽을 경우 offset을 변경하거나 소비자 그룹에 부작용을 만들지 않도록 연결을 설계합니다. 토픽 생성·삭제, offset reset, 메시지 발행은 제공하지 않습니다.

웹 UI만 존재하면 서버용 계정·격리 브라우저·접근 범위를 별도 승인받아 연결합니다. 개인 PC의 ego-browser 로그인이나 VDI 화면 세션을 복사하지 않습니다. 브라우저 실행 역시 도구 기록·취소·시간 제한을 따릅니다.

Slack 첨부 이미지는 해당 문의의 권한으로 내려받고 MIME·크기·개수를 검증합니다. 작업별 암호화 임시 저장소에 두며 공개 URL을 만들지 않습니다. 이미지의 텍스트·명령은 조사 대상 자료입니다. 흐린 값은 확인을 요청하고 화면만으로 코드 원인·운영 상태를 확정하지 않습니다. 코드·DB 확인이 필요한 질문이면 이미지 입력 뒤에도 같은 조사 의무를 적용합니다.

## 개발자 요청 카드

요청은 아래처럼 읽는 순서를 고정합니다. SQL을 제시할 수 없더라도 필요한 확인 자체를 숨기지 않습니다.

```text
확인이 필요한 내용
현재 운영 중인 센터 수를 확인해야 합니다.

확인할 곳
등록된 운영 조회 연결 / 센터 마스터

확인할 항목
• 센터와 창고 중 어떤 기준으로 세었는지
• 활성·삭제 조건을 적용한 건수

부족한 이유
BigQuery 사본의 최근 적재 시각을 확인하지 못했습니다.

돌려주실 내용
집계 기준과 건수만 입력해 주세요.

[확인 결과 입력] [직접 응대할게요]
```

카드에는 원 질문 링크를 넣고 긴 질문·로그는 접거나 내부 링크로 분리합니다. 안전하게 검증한 SQL만 별도 코드 블록으로 제공합니다. SQL 검증 실패는 SQL 표시를 막으며 요청 전체를 `unsafe_lookup_sql` 같은 코드 한 줄로 대체하지 않습니다.

도메인 담당자가 없거나 DM에 실패하면 대체 담당자·운영 경보로 넘깁니다. 고객에게 “개발자에게 요청했습니다”라고 알리는 것은 실제 DM 전달이 확인된 뒤입니다. 결과 입력은 문의의 조사 의무를 낮추지 않으며 “연결 복구함”과 “실제 조회 결과”를 구분합니다.

## 답변과 표현

조사를 마친 뒤 질문의 핵심에 맞춰 표현합니다. plain-language·i-have-adhd 적용 여부와 근거 확인은 별도 검사입니다. 짧아도 답변 조건·예외·다음 행동은 남깁니다. 불필요한 버전 면책 문구를 매번 붙이지 않되 운영 최신 여부처럼 판단에 영향을 주는 제한은 숨기지 않습니다.

대외 답변에는 토큰·개인정보·내부 경로·SQL·원시 조회 결과가 새지 않는지 검사합니다. 근거 확인은 사실의 정확성을 완전히 증명하지 않으므로 실제 모델 평가에서 주장과 자료의 일치 여부도 별도로 검토합니다.
