# 서버 구축과 배포 전략

[서버 설계 입구](README.md) · [추가 개발·변경 전략](development.md) · [실행·복구 운영](operations.md)

**CI가 만든 이미지를 시험 환경에서 검증하고, 같은 이미지를 운영에 배포합니다. 서버에서 `git pull`을 하거나 실행 중인 코드를 직접 고치는 방식은 사용하지 않습니다.**

상태: 구현 전 TO-BE, 2026-11-08. 현재 GitHub Actions는 스킬·로컬 봇 검사를 수행할 뿐입니다. 아래 서버 이미지 빌드·시험 배포·운영 배포는 아직 구현되지 않았습니다. 회사 자원·권한이 확정되면 이 계약에 맞춰 배포 파일과 파이프라인을 만듭니다.

## 배포 흐름

| 단계 | 하는 일 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 코드 변경 | 개발 브랜치에서 구현·테스트 | 계약·로컬 회귀·서버 검사가 통과함 |
| 이미지 생성 | 고정 커밋으로 이미지 한 번 빌드 | digest·출처·의존성·검사 결과를 기록함 |
| 시험 배포 | 격리 staging에 해당 digest 설치 | 실제 모델·Slack·자료 연결·마이그레이션 검증 |
| 운영 선택 | 검증된 릴리스와 환경 설정 선택 | 운영 책임자가 범위·검사·복귀 경로 확인 |
| 교체 | drain·역할 종료·DB 변경·새 버전 진단 | DB·원장·스키마·단일 역할 소유권 일치 |
| 운영 확인 | 시험 채널 확인 후 고객 처리 재개 | 관측 기준 충족, 불명 전송·오류 여부 확인 |

시험과 운영 사이에 이미지를 다시 빌드하지 않습니다. 환경별 차이는 외부 설정과 비밀 참조로 주입합니다. 이미지 digest로 특정 산출물을 고정할 수 있습니다. [Docker 공식 설명](https://docs.docker.com/reference/cli/docker/image/pull/)

## 첫 서버는 어디에 어떻게 만드나요?

회사에 관리형 컨테이너 실행 환경이 있으면 그 표준을 사용합니다. 없다면 사내망 접근이 승인된 Linux VM 1대에서 컨테이너 실행을 시작합니다. 이때 Docker Compose 같은 실행 명세와 OS 서비스 관리로 재시작을 관리합니다. Kubernetes 도입은 필수 조건이 아닙니다.

| 자원 | 첫 구축 기준 | 회사에서 정할 값 |
|---|---|---|
| 실행 환경 | 역할별 컨테이너, 조사 초기 동시 2건 | 플랫폼·CPU/RAM·Linux 아키텍처 |
| 상태 DB | 관리형 PostgreSQL 우선, 전용 DB·계정 | 버전·용량·백업·네트워크 |
| 레지스트리 | 회사 승인 비공개 컨테이너 저장소 | URL·push/pull 주체·보관 기간 |
| 파일 | 지식 스냅샷·복구 원장 영속 저장, 작업 파일 분리 | 볼륨/객체 저장소·암호화·백업 |
| 비밀 | 서비스 인증, 환경별 별도 참조 | 회사 비밀 저장소·회전 담당자 |
| 네트워크 | Slack·AI·Git·허용 자료의 목적지별 통신 | 프록시·방화벽·DB 승인 경로 |
| 관측 | 중앙 로그·지표·경보·관리 상태 조회 | 수집 위치·당번·보관·연락 경로 |

VM 1대는 장애 시 복구 시간이 생기는 구성이며 고가용성으로 표현하지 않습니다. PostgreSQL까지 같은 VM에 두는 것은 별도 결정입니다. 그렇게 시작한다면 외부 백업과 VM 소실 복원 연습을 필수로 하고 같은 디스크의 복사본만 백업으로 인정하지 않습니다.

인프라 정의는 회사 표준 도구로 코드화합니다. 환경·네트워크·볼륨·DB·비밀 참조·역할 권한·관측 설정의 선언을 보관하며 실제 비밀 값은 넣지 않습니다. 회사 표준이 정해지기 전에는 특정 클라우드·Terraform·Helm을 필수로 선택하지 않습니다.

## 한 이미지, 역할별 권한

이미지는 같아도 수신·게시·조사·갱신의 실행 설정과 자격은 다릅니다. 단일 VM에서도 역할별 컨테이너로 자격과 파일 접근을 분리합니다. 게시기는 Slack 쓰기 자격을 갖지만 조사 엔진에는 전달하지 않습니다. DB 마이그레이션 자격은 일회성 변경 작업에만 줍니다.

이미지에는 코드·고정된 의존성·스킬 묶음만 포함합니다. 회사 지식·대화·조회 결과·개인 CLI 홈·실제 인증 파일은 포함하지 않습니다. 파일은 필요한 범위만 마운트하고 작업 디렉터리는 문의별로 격리합니다. 스킬 호환 경로가 필요하면 서버 전용 홈에 읽기 전용 스냅샷을 연결합니다.

조사 작업의 OS·파일·메모리 격리를 실제로 구현해야 합니다. 컨테이너 하나 안에서 폴더 이름만 다르게 준 것을 보안 격리로 인정하지 않습니다. 엔진에 호스트 Docker 소켓이나 전체 볼륨을 넘기지 않습니다. 실행 플랫폼의 작업 격리 기능 또는 제한된 실행 감독자를 정하고 E07로 검증합니다.

## 개발·시험·운영 분리

| 환경 | 목적 | Slack·자료 | 자격·저장소 |
|---|---|---|---|
| 개발 | 개별 기능·디버깅 | fake Slack/AI, 합성 자료 기본 | 임시 DB·홈, 운영 자격 없음 |
| CI | 재현 가능한 자동 검사 | fake와 실제 프로토콜 fixture, 격리 PostgreSQL | 일회성 자원, 회사 망 접근 없음 |
| staging | 배포 후보의 실제 연동 | 별도 시험 앱·비공개 채널, 승인된 시험 자료 | 운영과 별도 DB·원장·자격·지원 대상 |
| production | 고객 질문 처리 | 운영 앱·허용 채널·등록 자료 | 운영 전용 상태·비밀·예산 |

같은 워크스페이스에 시험 앱을 둘 수 있지만 운영 앱 토큰을 재사용하지 않습니다. staging에 운영 DB 백업을 그대로 복제하지 않고 합성·마스킹 자료를 사용합니다. 직접 운영 읽기가 꼭 필요한 회사 수용 시험은 별도 승인 범위와 비용 한도를 기록합니다.

Socket Mode 연결이 여러 개면 이벤트가 연결 사이에 분배될 수 있으므로 서로 다른 DB를 가진 시험/운영 실행기에 같은 앱 토큰을 주면 안 됩니다. [Slack Socket Mode 안내](https://docs.slack.dev/apis/events-api/using-socket-mode/)

## 레포와 회사 설정의 위치

제품 코드는 기존 Dougle 레포에서 개발합니다. 회사 전용 배포 설정은 회사가 관리하는 비공개 구성 저장소 또는 플랫폼 설정에 둡니다. 제품 레포에는 템플릿·계약·합성 fixture만 둡니다. 업무 지식을 공유하는 저장소와도 구분합니다.

```text
제품 레포: skills/, dougle-bot/, tests/, deploy/ 템플릿
회사 구성: 환경별 릴리스 digest, 설정·정책 버전, 비밀 참조, 인프라 정의
지식 저장소: 승인된 정제 Markdown·출처·정정
비밀 저장소: Slack·AI·자료 조회 자격의 실제 값
```

제품 CI를 신뢰하지 못하는 회사 정책이라면 같은 검증된 소스 커밋을 사내 CI로 가져와 빌드·검사합니다. 이 경우 사내 빌드 digest를 staging과 운영에 동일하게 승격합니다. 공개 레포의 외부 기여 코드가 회사 배포 runner에서 실행되는 경로를 만들지 않습니다.

## CI/CD를 어떻게 구성하나요?

아래 이름은 구현할 파이프라인 역할입니다. 실제 `.github/workflows/` 파일이 이미 있다는 뜻은 아닙니다. 회사 표준 CI/CD에서도 동일한 계약을 구현할 수 있습니다.

| 파이프라인 | 입력·실행 조건 | 결과·권한 |
|---|---|---|
| verify | 변경 커밋, 전체 관련 의존 경로 | 로컬 회귀·계약·PG·정적 검사. 배포 자격 없음 |
| build-candidate | 신뢰한 main의 통과 커밋 | 고정 의존성으로 이미지, SBOM·출처·취약점 검사·digest. 레지스트리 push만 |
| deploy-staging | 후보 digest와 시험 구성 revision | 별도 환경 배포·연동·업그레이드/복귀 결과. 시험 자격만 |
| promote-production | 동일 digest·검증 증거·운영 구성 revision | 보호된 배포 작업, 배포 잠금·이력. 운영 전용 권한 |
| rollback | 마지막 호환 릴리스와 현재 상태 | 호환성 진단 후 교체 또는 게시 차단·운영자 확인 |

CI path filter에는 스킬·프롬프트·공통 검증기·의존성·스키마·배포 템플릿을 포함합니다. Python 파일이 바뀌지 않았다는 이유로 모델 행동 검사를 건너뛰지 않습니다. 필수 작업이 skip/취소/수집 0건이면 전체 성공으로 처리하지 않습니다.

Actions 및 빌드 기반 이미지는 확인한 버전·digest를 고정하고 갱신 절차를 둡니다. lockfile을 커밋하며 빌드마다 임의 최신 의존성을 설치하지 않습니다. SBOM·스캔 결과·구동 검사·대상 CPU 아키텍처를 릴리스에 연결합니다. 지원하지 않는 Linux/CLI 조합은 배포 전에 차단합니다.

운영 배포는 main push나 태그 생성만으로 즉시 실행하지 않습니다. 최초에는 운영 책임자가 검증된 릴리스를 선택해 승격합니다. 이는 향후 제품 운영 정책이며 이번 문서 반영에 추가 승인을 요청하는 절차는 아닙니다. GitHub environment 보호 기능을 사용할 수 있는지는 회사 플랜·레포 공개 범위로 확인합니다. 없으면 사내 배포 승인 시스템에 같은 경계를 둡니다. [GitHub 환경 보호 설명](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

회사 플랫폼이 지원하면 OIDC 같은 단기 인증을 사용합니다. 신뢰 조건은 제품 레포·워크플로·배포 환경·허용 ref로 제한합니다. 운영 비밀을 일반 PR/외부 기여 작업에 주지 않습니다. [GitHub OIDC 안내](https://docs.github.com/en/actions/concepts/security/openid-connect)

사내망 접근에는 전용 배포 runner 또는 사내 pull 방식 실행기를 사용합니다. 둘 다 검증된 digest와 허용한 배포 동작만 받습니다. 영속 배포 runner에서 임의 PR 테스트를 실행하지 않습니다. CI에는 배포 권한이 필요할 뿐, 운영 DB 조회 결과나 AI에 주입하는 자격 전체가 필요하지 않습니다.

## 릴리스에 무엇을 기록하나요?

[릴리스 기록 템플릿](release-template.json)을 복사해 후보별로 작성합니다. 필수 항목이 비어 있으면 운영 배포를 막습니다. backfill처럼 해당하지 않는 항목은 빈 값의 이유를 남깁니다. 배포 시각·결과는 실행 중 채웁니다. 템플릿은 실행 결과나 현재 배포 설정이 아닙니다.

필수 항목은 소스 커밋, 이미지 digest, 런타임·스킬·엔진·프롬프트 버전, 지원 DB 스키마 범위, migration 목록, 환경 구성·정책 revision, 테스트 결과 참조, 변경 요약, 호환 가능한 복귀 digest입니다. 배포 시점에는 이전/신규 릴리스, 지식 snapshot, 실행자, 시작/종료·결과, 역할 소유권 epoch도 기록합니다.

같은 버전의 이미지 내용을 덮어쓰지 않습니다. `latest`나 움직이는 태그를 운영 기준으로 쓰지 않고 digest로 고정합니다. 런타임 이미지와 스킬 묶음은 호환성을 시험한 조합이며 운영에서 자동 플러그인 업데이트를 하지 않습니다. 모델 이름을 고정해도 제공자 동작 변화 가능성은 남으므로 실제 모델 식별자와 행동 평가를 기록합니다.

## 최초 구축 순서

1. 회사 운영 책임자와 실행 플랫폼·계정·네트워크·예산·복구 목표를 확정합니다.
2. 환경별 인프라·자격·DB·원장·볼륨·관측 경로를 구성 코드로 만듭니다.
3. 제품 이미지를 만들고 Linux 구동·실제 PostgreSQL·격리·로컬 회귀를 검증합니다.
4. staging에 시험 앱을 연결하고 122개 명세 중 해당 자동·실연동·성능·배포 사례를 수행합니다. 선택 기능 제외는 기록합니다.
5. 운영에 접수/게시를 열지 않은 상태로 설치하고 설정·자료·권한·마이그레이션·복귀를 진단합니다.
6. 기존 로컬 봇에서 이관한다면 [운영 문서의 10단계](operations.md)를 적용합니다. 과거 문의·전송 원장은 임의 폐기하지 않습니다.
7. 제한된 운영 시험 채널만 먼저 열어 실제 답변·보충·직접 응대·상태 조회를 확인합니다.
8. 정한 관측 기간과 성공 기준을 충족하면 허용 채널을 넓힙니다. 확대도 정책 변경으로 기록합니다.

## 이후 정기 배포 순서

첫 버전은 **짧은 교체 구간을 허용하는 단일 활성 버전 방식**입니다. 무중단 배포를 보장하지 않습니다. 서버 안의 역할을 순서대로 교체할 수 있어도 신구 버전의 조사·게시를 동시에 활성화하지 않습니다.

1. 배포 잠금을 획득하고 이전/후보 digest·구성·스키마 호환성·가용 저장소·백업·원장을 확인합니다. 실행 중인 다른 배포가 있으면 시작하지 않습니다.
2. `draining`으로 바꿔 새 작업 선점을 멈춥니다. 수신기가 살아 있는 동안 새 질문은 DB에 보관합니다. 진행 중 조사·전송은 정한 기한 안에 마칩니다.
3. 기한을 넘긴 조사는 취소·소유권 만료로 처리합니다. 전송 시작 후 결과를 모르면 unknown으로 남깁니다. 완료된 답변을 배포 편의상 삭제하지 않습니다.
4. 수신기를 종료하고 옛 worker·게시기·갱신기·복구기의 종료 또는 소유권 상실을 확인합니다. 새 역할을 열기 전에 fencing을 확정합니다. 이 구간의 미수신 Slack 이벤트는 무손실 보장 밖이며 중단 시간을 기록합니다.
5. migration 전용 작업 하나가 배포 잠금 아래에서 스키마를 변경합니다. 실패하면 게시를 닫은 채 중단하고 진단합니다. 모든 replica 시작 때 DDL을 실행하지 않습니다.
6. 새 버전을 `recovering`으로 시작합니다. DB·원장·정책·snapshot·lease·설정 호환성을 확인합니다. 사전 진단에 live 고객 게시를 사용하지 않습니다.
7. 검증 후 수신을 연결하고 배포 확인용 채널에만 조사·게시를 제한적으로 허용합니다. 다른 접수는 큐에 남깁니다. 이 배포 게이트는 환경 상태에 기록하며 일반 권한·예산·근거 검사를 우회하지 않습니다.
8. 시험 질문·결과 입력·직접 응대·관측을 확인한 뒤 게이트를 풀고 `running`으로 전환합니다. 대기열을 한꺼번에 무제한 실행하지 않습니다.
9. 정한 관측 기간 동안 오류·대기·근거 차단·DM 실패·비용을 비교합니다. 책임자가 배포 완료를 기록하고 잠금을 해제합니다.

배포 잠금과 게이트는 DB 또는 회사 배포 제어 저장소에 영속화하고 배포 ID·owner·epoch·단계를 남깁니다. CI 실행 취소로 잠금이 사라지거나 자동으로 게시가 열리지 않습니다. 복구 실행은 현재 단계를 확인해 이어가며 lease 만료만으로 migration이나 외부 전송을 재실행하지 않습니다. 전체 배포 기한 초과는 경보와 복귀 판단으로 이어집니다.

`paused`는 사용자의 의도적 중지이므로 배포 때 대신 사용하지 않습니다. 배포 도중 액션으로 접수한 개발자 결과도 DB에 보존하고 구세대 결과를 거절해야 합니다. staging의 확대 시험을 통과하기 전에는 운영 수신/게시 이중화나 퍼센트 기반 카나리 배포를 구현했다고 부르지 않습니다.

## 되돌리기와 긴급 수정

| 문제 | 먼저 할 일 | 복귀 방식 |
|---|---|---|
| 새 코드·스킬이 잘못 답함 | 해당 자동 게시·작업 선점 차단 | 현 DB와 호환되는 이전 이미지·설정으로 교체, 새 세션·후보 재검증 |
| DB 확장 migration 후 앱 실패 | 현재 데이터 보존, 호환 범위 확인 | 확장 스키마를 읽는 이전 앱으로 복귀 |
| 비호환 schema·새 상태가 이미 저장됨 | 구버전 시작 차단 | 수정 버전으로 전진하거나 명시적 복구 절차 수행 |
| 잘못된 지식 활성화 | 해당 자료 사용/게시 차단 | 검증된 이전 snapshot 선택, 진행 후보·세션 무효화 |
| 비밀 유출·자료 권한 변경 | 자격 회수·정책 차단 | 새 자격·정책 적용; 옛 권한을 되살리는 복귀 금지 |
| 전송 결과 불명·원장 불일치 | 게시기 차단 | 외부 기록 대조 후 조정; 일괄 재송신 금지 |

코드 rollback은 DB backup restore와 다릅니다. 일반 배포 실패 때 DB를 과거로 되돌리면 그사이 접수한 질문·개발자 보충·게시 기록을 잃을 수 있습니다. DB 복원은 재난 복구로 분리하고 독립 전송 원장·삭제 정책까지 대조합니다.

긴급 수정도 소스 커밋→회귀 검사→새 이미지→staging 최소 재현→운영 승격을 거칩니다. 서버 파일 직접 수정·검사 생략을 기본 긴급 경로로 두지 않습니다. 이미 고객에게 나간 잘못된 답변은 이미지 복귀로 사라지지 않으므로 해당 문의를 추적해 담당자가 정정 여부를 결정합니다.

## 나중에 서버가 커지면

첫 병목이 조사라면 worker만 늘립니다. 전역 예산·연결 제한·스레드 직렬성은 유지합니다. VM 소실 복구 시간으로 운영 목표를 충족하지 못하면 다중 노드·외부 스냅샷 저장·자동 역할 인계를 추가합니다. 플랫폼 변경은 앱/저장 계약을 유지한 별도 배포 변경으로 시험합니다.

그때 rolling/canary를 도입하려면 신구 job·schema·세션·카드 계약의 동시 호환, 스레드별 버전 고정, 중복 게시 방지, 채널별 노출 범위가 먼저 검증되어야 합니다. 단순히 replica를 늘리는 것으로 무중단이나 정확히 한 번 게시가 달성되지는 않습니다.
