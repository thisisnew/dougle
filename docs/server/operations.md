# 배포·운영

[서버 설계 입구](README.md) · 다음: [구현·수용 기준](implementation.md)

이 문서는 실행 중 관리·중지·이전·복구 절차입니다. 서버를 처음 만들고 이후 버전을 올리는 전체 과정은 [구축·배포 전략](delivery.md), 기능을 계속 개발하는 규칙은 [개발·변경 전략](development.md)을 따릅니다. CI/CD·환경 분리·이미지 승격·DB 호환성·긴급 수정은 그 문서에서 정의합니다.

## 배포 전제

회사에서 허용한 Linux 실행 환경, PostgreSQL, 시크릿 저장소, 지속 저장소, 로그 수집 경로가 필요합니다. DB·코드·문서·AI·Slack에 대한 네트워크 접근도 각각 확인합니다. 서버 생성만으로 자료 접근 권한이 생기지는 않습니다.

| 자원 | 첫 배포 구성 |
|---|---|
| 프로그램 | 버전이 고정된 컨테이너 이미지, 비root 실행 |
| 수신·게시 | Socket Mode 수신기 1개, 게시기 1개 |
| 조사 | 동시 2건, 개별 작업 디렉터리·프로세스 제한 |
| 상태 | PostgreSQL, 마이그레이션 계정과 일반 실행 계정 분리 |
| 파일 | 읽기 전용 지식 버전, 작업 임시 파일, 복구 가능한 전송 원장 |
| 비밀 | 회사 시크릿 저장소의 서비스 계정 자격 |
| 관측 | 구조화 로그·지표·상태 조회·운영 경보 |

초기에는 영속 볼륨으로 지식 버전을 보관할 수 있습니다. 여러 노드로 늘리면 내용 해시로 객체 저장소에서 내려받아 각 노드의 읽기 전용 캐시에 둡니다. 세션 파일을 여러 작업자가 동시에 쓰는 공유 디렉터리는 사용하지 않습니다.

Socket Mode는 서버에서 Slack으로 연결하므로 공개 이벤트 수신 URL 없이 운영할 수 있습니다. Git webhook 수신 URL을 열 수 없다면 등록 ref의 주기적 비교로 시작합니다. webhook을 쓰면 서명 검증·중복 제거·실제 원격 확인을 구현합니다. [Slack Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/)

## 목표 설정 예시

아래는 서버 설정의 제안 형식입니다. 현재 `config.toml`에 붙여 넣어 실행할 수 있는 설정이 아닙니다. 실제 자격 값은 포함하지 않습니다.

```toml
[runtime]
mode = "server"
roles = ["intake", "worker", "dispatcher", "knowledge", "recovery"]
max_parallel = 2
lease_seconds = 60
heartbeat_seconds = 10
research_timeout_seconds = 900
queue_capacity = 100

[state]
backend = "postgres"
credential_ref = "dougle/state-database"

[slack]
workspace_id = "WORKSPACE_ID"
bot_token_ref = "dougle/slack-bot"
app_token_ref = "dougle/slack-app"
require_approval = false
identity_reaction = "dougle"
working_reaction = "loadingg"
completed_reaction = "처리완료"

[engine]
adapter = "claude_cli"
credential_ref = "dougle/ai-service"
skill_bundle_version = "PINNED_VERSION"
max_budget_usd_per_call = 3.0
daily_budget_usd = 30.0

[knowledge]
auto_fetch = true
reconcile_seconds = 300
auto_publish = false
write_mode = "proposal"

[[knowledge.repositories]]
id = "team-knowledge"
url = "https://github.com/ORG/REPOSITORY.git"
ref = "dougle-knowledge"
paths = ["knowledge/example-domain/"]
domain_id = "example-domain"

[[channels]]
id = "CHANNEL_ID"
domains = ["example-domain"]
support_route = "example-support"
external_members_allowed = false
```

예시 ID·미해결 비밀 참조·빈 공개 범위에서는 시작 진단을 실패시킵니다. 설정의 숫자는 범위와 상호 관계를 검증합니다. 토큰, 접속 문자열의 비밀번호, SQL 파라미터는 로그에 출력하지 않습니다. 설정 변경도 버전과 감사 기록을 남기며 권한 축소는 진행 중인 작업에 적용합니다.

## 시작과 종료

시작 시 설정·비밀 참조·DB 버전·스킬 묶음·유효한 지식 버전을 검사합니다. 모든 원본을 다시 읽지는 않습니다. 필요한 자료가 없는 도메인은 사용 불가로 표시하고 다른 도메인의 중단 여부는 의존 관계로 판단합니다.

| 모드 | 새로운 질문 | 연결·기존 작업 |
|---|---|---|
| `running` | 접수합니다. | 정상 처리 |
| `draining` | 수신기가 살아 있으면 DB에 접수해 기다리게 합니다. | 새 작업 선점을 멈추고 진행 중인 작업을 제한 시간 안에 마칩니다. |
| `paused` | 중지 구간의 이벤트를 무시합니다. | 기존 작업은 보존하며 새 조사·공개 전송을 멈춥니다. |
| `recovering` | 설정에 따라 DB 대기열에 접수합니다. | 원장·DB·권한 검사가 끝날 때까지 게시를 막습니다. |

이용자에게는 “실행 중”, “업데이트 중”, “중지”, “복구 중”으로 표시합니다. 이미 시작된 외부 전송은 회수할 수 없으므로 중지 후에도 그 결과를 대조합니다.

중지 구간은 DB에 저장합니다. 재개 후 늦게 도착한 이벤트도 Slack 생성 시각으로 제외합니다. 중지 전에 접수한 문의는 보존합니다. 프로세스 장애·배포를 의도적 중지로 기록하지 않습니다. 중지 기간의 채널 이력을 뒤져 새 문의를 만드는 처리도 추가하지 않습니다.

Slack 재전송·연결에 의존하는 미수신 이벤트까지 무손실을 보장하지 않습니다. 복구 보장의 경계는 DB에 접수한 문의입니다. 전환 시 수신 중단 시간을 줄이고 실제 이벤트 전달·재전송을 별도로 시험합니다.

## 관측과 상태 확인

고객은 Slack의 반응과 필요한 진행 안내를 봅니다. 관리자는 기존 스킬의 “상태 확인”에서도 서버 상황을 조회할 수 있게 합니다. 별도 터미널의 `tail` 명령을 필수로 요구하지 않습니다. 관리 연결에는 인증을 붙이며 공개 관리 웹 화면은 첫 범위에 포함하지 않습니다.

| 관측 항목 | 확인할 내용 |
|---|---|
| 대기열 길이·가장 오래 기다린 시간 | 문의가 밀리고 있는지 |
| 단계·경과 시간·마지막 신호 | 조사가 진행 중인지, 어디에서 멈췄는지 |
| 연결별 지연·오류 코드 | DB·문서·코드 연결 장애 |
| AI 입력·출력 토큰·비용 | 조사·표현·재시도의 비용 |
| 소유권 만료·오래된 결과 거절 | 작업자 장애와 안전한 인계 |
| 전송 불명·게시 차단 | 중복 위험·권한 변경 |
| 지식 갱신 지연·충돌 수 | 공유 자료 수신 상태 |
| 개발자 대기 시간·DM 실패 | 내부 확인이 방치됐는지 |

로그에는 문의·작업·실행 ID, 단계, 소요 시간, 이유 코드를 남깁니다. 원문 질문·첨부·SQL 결과·모델 내부 추론을 일반 로그에 출력하지 않습니다. 상세 내용을 보는 저장소에는 별도 권한을 적용합니다.

Liveness는 프로세스 응답을, readiness는 DB·역할 소유권·수신 연결 등을 역할별로 확인합니다. BigQuery 장애만으로 전체 프로세스를 계속 재시작하지 않습니다. 해당 연결의 새 요청을 잠시 제한하고 필요한 문의만 내부 확인으로 넘깁니다.

## 보관과 백업

보관 기간은 회사 승인 사항입니다. 초기 제안은 작업 첨부 24시간, 대화·조회 결과 30일, 원문 없는 감사·전송 기록 90일입니다. 실제 보관 정책을 확정하기 전에는 운영 자료로 공개 서비스를 시작하지 않습니다. 미해결 문의의 자료가 만료되면 담당자에게 알리고 필요한 최소 요약만 허용 범위에서 유지합니다.

DB 백업, 지식 버전, 전송 원장, 암호화·비밀 참조의 복구 방법을 함께 관리합니다. 초기 복구 목표안은 RPO 15분, RTO 60분이며 아직 측정하지 않았습니다. 실제 백업과 복원 연습으로 달성 여부를 기록합니다.

중복 방지 기록을 삭제하려면 그보다 오래된 이벤트를 자동 접수하지 않는 정책도 필요합니다. 대화 본문과 최소 전송 ID·해시·종료 상태를 분리해 필요한 기간만 보관합니다. 백업에서 삭제된 자료가 되살아나지 않도록 삭제 이력도 재적용합니다.

## 로컬에서 서버로 전환

1. 별도 개발용 Slack 앱과 합성 지식으로 서버를 검증합니다. 운영 앱에 로컬 시험 실행기를 동시에 연결하지 않습니다.
2. 서비스 인증·채널·지식·담당자를 서버에 설정하고 게시를 닫은 상태에서 시작 진단을 합니다.
3. 공유된 지식을 가져와 검증합니다. 개인 홈 전체나 로그인 파일은 복사하지 않습니다.
4. 기존 로컬 실행을 멈추고 DB·`post-intents.log`·필요한 관련 파일을 같은 중지 시점에 보존합니다.
5. 기존 ID와 새 UUID의 대응표를 만들고 워크스페이스를 추가합니다. 시각은 UTC로 변환하며 Slack ts는 문자열로 유지합니다. 행 수·FK·해시·전송 상태를 대조합니다.
6. 완료·거절·취소는 종료 상태를 보존합니다. 직접 응대 감사 기록이 있는 취소는 `human_owned`로 변환합니다. 승인 대기는 그대로 두고 `posting/post_unknown`은 확인 전까지 보내지 않습니다.
7. 중단된 조사는 기존 소유권을 만료시키고 새 실행으로 재개합니다. 과거 CLI 세션 복원을 필수로 삼지 않으며 허용된 대화에서 문맥을 복원합니다.
8. 기존 DM 카드의 옛 ID를 문의로 연결하는 대응표를 두거나 옛 카드를 무효화하고 새 카드로 갱신합니다. 오래된 버튼을 다른 문의에 연결해서는 안 됩니다.
9. 로컬 Socket 연결 종료를 확인한 뒤 서버 수신을 시작합니다. 같은 앱이라면 이전 자체가 토큰 재발급 사유는 아니지만 비밀 보관 위치는 서버로 옮깁니다.
10. 제한된 채널에서 질문·개발자 보충·직접 응대·재시작을 확인하고 범위를 넓힙니다.

과거 기록을 옮길 권한·필요가 없다면 이전 문의의 종료 방침을 정하고 서버를 새 기록으로 시작합니다. 이때도 옛 카드·불명 전송·중지 구간을 먼저 정리합니다. 방치된 문의가 자동 완료됐다고 표시하지 않습니다.

## 업데이트·되돌리기·장애 복구

앱 업데이트, 공유 지식 수신, 원본 확인은 별도 작업입니다. 앱 업데이트 때문에 지식을 전부 다시 만들지 않습니다. DB 변경은 추가부터 시작하고 신구 버전의 호환 기간을 정합니다. 새 스키마를 이해하지 못하는 구버전은 시작을 막습니다.

배포 순서는 drain, 진행 중 작업 종료 확인, 필요한 마이그레이션, 새 버전 시작 진단, 수신·게시 재개입니다. 종료 기한을 넘긴 작업은 취소·소유권 만료를 기록하며 옛 프로세스가 돌아와도 결과를 채택하지 않습니다.

장애 복구 시 게시를 닫고 DB·원장·지식을 복원합니다. 외부 Slack 기록과 대조해 모순된 전송은 `post_unknown`으로 둡니다. 백업 시점 이후의 게시가 불분명하면 오래된 대기 메시지를 일괄 재전송하지 않습니다. 대조 완료와 운영자 확인을 기록한 뒤 게시를 다시 엽니다.
