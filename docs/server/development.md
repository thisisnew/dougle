# 서버 운영 이후의 개발·변경 전략

[서버 설계 입구](README.md) · [서버 구축·배포](delivery.md) · [테스트 명세](testing/README.md)

**개발은 기존 레포에서 계속합니다. 기능별로 작게 변경하고, 로컬·서버 공통 계약과 실제 답변을 검증한 버전만 배포합니다.**

상태: 구현 전 TO-BE, 2026-11-08. 기존 로컬 사용자에게 서버 설치를 요구하지 않으며 운영 서버의 자동 업데이트 정책도 이번 문서 작성으로 활성화되지 않습니다.

## 무엇이 바뀌는지 먼저 구분합니다

| 변경 | 수정 위치 | 반영 방법 | 필수 검증 |
|---|---|---|---|
| 봇 기능·상태 전이 | 제품 코드·계약 | 새 런타임 릴리스·이미지 | 해당 수용 기준·PG 경합·로컬 회귀 |
| 답변 스킬·프롬프트·모델 | 고정된 엔진/스킬 묶음 | 새 호환 릴리스 또는 검증된 실행 구성 | 실제 모델·근거 기록·표현·비용 회귀 |
| 정제 업무 지식 | 선택 지식 저장소 | publish→서버 fetch→검증된 snapshot | 충돌·출처·민감정보·권한·관련 답변 |
| 채널·담당자·읽기 범위 | 회사 구성·정책 | 검증한 구성 revision 적용 | 권한 확대/축소·기존 문의·카드 처리 |
| 비밀 회전 | 회사 비밀 저장소 | 자격 참조 갱신·연결 재설정 | 누출 방지·실연결·실패 경보 |
| DB 구조 | migration·저장 계약 | 배포 전용 migration 작업 | 신구 호환·경합·실데이터 규모·복귀 |
| OS·플랫폼·의존성 | 인프라/이미지 정의 | 새 이미지 또는 인프라 배포 | 아키텍처·격리·장애·부하·복원 |

지식의 publish는 제품 코드 배포가 아닙니다. 서버 코드를 올렸다고 모든 지식을 다시 내재화하지 않습니다. 지식 정정으로 고칠 수 있는 내용을 배포 때마다 앱에 하드코딩하지 않습니다.

## 한 기능의 개발 흐름

1. 문제를 한 문장으로 적고 실제 문의 예시·현재 동작·원하는 결과를 남깁니다. 회사 자료는 공개 이슈에 붙이지 않고 합성 사례로 바꿉니다.
2. 영향 범위를 정합니다. 로컬 스킬·로컬 봇·서버·DB·권한·스킬/모델·배포 중 어디가 달라지는지 표시합니다.
3. 실패 재현을 만들고 기존 테스트 ID를 연결합니다. 새 계약이면 명세 ID·변형·합격 증거를 먼저 추가합니다.
4. 짧은 기능 브랜치에서 구현합니다. 큰 변경은 호환 인터페이스→미사용 구현→시험 연결→기존 호출자 전환→옛 구현 제거 순으로 나눕니다.
5. 관련 자동 검사와 로컬 회귀를 실행합니다. 실제 모델·자료 경로를 바꾸면 합성 모델 평가와 staging 실연동도 수행합니다.
6. 검토 가능한 작은 변경으로 main에 반영합니다. 팀 공동 개발에서는 PR 리뷰를 기본 제안으로 하되 최종 리뷰 정책은 팀이 정합니다. 어떤 방식으로 합치든 운영 배포는 별도 승격 절차입니다.
7. 검증된 후보를 릴리스하고 staging→운영으로 올립니다. 배포 후 오류·지연·토큰·내부 인계 비율을 확인해 완료합니다.

main은 배포 가능한 상태를 유지하되 모든 main 변경을 즉시 운영에 반영하지 않습니다. 미완성 기능은 명시적 기본 꺼짐 설정 뒤에 두고 허용되지 않은 경로로 실행할 수 없게 합니다. 장기 develop 브랜치와 운영 서버만의 비공개 수정본은 만들지 않습니다.

현재 지식 publish의 직접 반영 정책은 그대로입니다. 제품 코드 리뷰 정책을 도입한다고 지식 공유를 PR 필수로 바꾸지 않습니다. 회사 운영 설정 검토는 자료 공유와 별개입니다.

## 공통 코드와 서버 코드의 경계

근거 검증·답변 표현·업무 판단·개발자 인계 규칙은 공통 application/contract에 둡니다. SQLite/PostgreSQL, Keychain/회사 비밀 저장소, 로컬/서버 실행은 어댑터로 나눕니다. 서버와 로컬에 같은 정책을 복사해 따로 수정하지 않습니다.

새 기능의 완료 조건에는 “서버 전용 의존성이 로컬 지식 스킬 사용자에게 강제되지 않음”을 포함합니다. 스킬 정본과 배포 사본은 기존 방식대로 동일하게 생성·검증합니다. 사용하지 않는 서버 실험 패키지나 옛 경로는 전환이 끝난 뒤 제거하되 지원 중인 로컬 경로를 일괄 삭제하지 않습니다.

신규 자료 연결은 `SourceReader` 계약으로 추가합니다. capability·권한·스키마·관측 시각·잘림·취소·영수증을 구현하며 모델 프롬프트에 도구 이름 하나만 적는 것으로 완료하지 않습니다. 연결이 없는 환경에서도 나머지 기능이 동작해야 합니다.

## 버전과 호환성

| 대상 | 관리 규칙 |
|---|---|
| 스킬 패키지 | 기존 스킬 버전 유지. 동작 변경 시 증가, 정본/사본 일치 |
| 봇 런타임 | 로컬·서버가 공유하는 패키지 버전. 서버 전용 변경도 릴리스 노트에 범위 표시 |
| 서버 이미지 | 런타임·스킬·엔진·의존성 조합을 digest로 고정 |
| DB 스키마 | 단조 증가 migration ID와 지원 최소/최대 또는 명시적 호환 집합 |
| 설정·정책 | schema version과 환경별 revision. 권한 축소는 즉시 적용 |
| 지식 | Git commit·snapshot ID. 앱 릴리스 번호와 독립 |
| 실행·세션·근거 | engine/skill/prompt/policy/snapshot 계약 버전을 함께 기록 |

첫 서버 릴리스에서 기존 스킬·봇 번호를 임의로 같게 만들지 않습니다. 무엇이 바뀌었는지에 따라 버전을 올리고, 호환되는 조합을 릴리스 기록으로 고정합니다. 코드가 같더라도 이미지 기반 의존성이나 스킬이 바뀌면 새 digest와 검증 결과가 필요합니다.

앱은 모르는 schema/config/job payload 버전을 시작 시 또는 처리 전에 차단합니다. 새 enum을 구버전이 실패 없이 무시하게 만드는 것으로 호환성을 인정하지 않습니다. 대기 문의와 옛 DM 카드도 버전 계약의 일부입니다.

## DB는 추가→전환→제거 순서로 바꿉니다

예를 들어 `developer_requests`에 새 분류 필드를 추가할 때는 다음 순서를 따릅니다.

| 릴리스 | 작업 | 되돌릴 수 있는 조건 |
|---|---|---|
| N | nullable 필드/새 테이블 추가, 기존 읽기 유지 | N-1이 확장 스키마와 새 행을 처리할 수 있음 |
| N+1 | 새 쓰기·호환 읽기, 필요 데이터 배치 보충 | 중복 쓰기 정합성·옛 의미 보존을 검증함 |
| N+2 이후 | 완전성 검사 후 새 읽기 기본값 전환 | 이전 앱이 여전히 이해하는 값만 남아 있음 |
| 제거 릴리스 | 복귀 기간 종료·옛 실행/카드 영향 확인 후 삭제·제약 강화 | 이후에는 옛 앱으로 복귀 불가함을 명시 |

릴리스 번호는 설명용이며 실제 기간은 운영 담당자가 정합니다. 장기 backfill은 DDL 트랜잭션 안에 넣지 않습니다. 기본 키 범위·체크포인트·배치 크기·재시도·중단 조건을 기록하고 같은 배치를 반복해도 결과가 중복되지 않아야 합니다.

migration은 단일 실행 잠금과 ID·checksum을 사용합니다. 적용한 migration 파일을 수정하지 않고 새 migration으로 고칩니다. 잠금/문장 제한시간을 정하며 운영 데이터 규모로 지연을 측정합니다. 앱 시작이 대량 backfill 완료를 무기한 기다리는 구조는 피합니다.

추가 migration이라도 새 상태·의미를 저장하면 이전 앱이 읽지 못할 수 있습니다. “컬럼 추가니까 rollback 가능”으로 판단하지 않고 실제 이전 버전으로 읽기·처리·게시 검사를 수행합니다. 일반적인 down migration으로 고객 데이터와 전송 기록을 지우지 않습니다.

## 질문 처리 중 버전이 바뀌면

첫 배포 전략은 drain으로 신구 동시 실행을 피합니다. 그래도 큐·개발자 대기·승인 대기 문의는 배포를 넘어서 존재합니다. 문의에는 접수 당시 reply mode, generation, job payload version, 마지막 검증 계약을 보관합니다.

새 worker는 이전 job을 명시적 변환기로 읽거나 지원하지 않는 상태로 보류합니다. 완료 후보를 게시하려면 현재 정책과 검증 계약으로 다시 판단합니다. 코드·스킬·모델·정책 변화가 기존 영수증 의미를 바꾸면 재조사합니다. 조사 의무를 낮추지 않습니다.

진행 중이던 모델 프로세스는 종료·취소하고 늦은 결과는 epoch/generation으로 거절합니다. 기존 세션을 임의 resume하지 않습니다. 개발자 보충·실제 게시본을 보존한 허용 문맥으로 복원합니다. 검토 모드의 옛 후보를 새 자동 모드로 일괄 전환하지 않습니다.

운영 설정은 적용 방식도 선언합니다. 채널 공개 권한 축소는 즉시 새 읽기·게시를 막습니다. 병렬도·모델·실행 경로처럼 시작 계약에 영향을 주는 값은 drain 후 재시작합니다. 담당자 변경은 열린 요청의 수신자·권한·카드를 함께 바꿉니다.

## AI 답변 변경은 일반 코드 검사만으로 끝내지 않습니다

프롬프트 한 줄도 제품 동작 변경입니다. 스킬의 표현 규칙을 바꿀 때 실제 근거 조사를 줄이거나 보완 호출을 과도하게 늘리는지 같이 측정합니다.

고정 합성 평가 세트에는 업무·코드·현재 DB·적재 지연·이미지·권한 거부·자료 없음·후속·개발자 보충을 포함합니다. 후보와 기준 버전에 같은 질문과 자료를 제공하고 주장 정확도·필수 조회·존댓말·간결성·입력 토큰·시간·비용을 비교합니다. 문장 일치율로 답변 품질을 판정하지 않습니다.

실제 고객 질문을 두 엔진에 몰래 보내는 shadow 운영은 첫 범위에 없습니다. 비교 평가가 필요하면 승인된 비민감 자료로 격리 실행하고 출력·도구 쓰기를 막습니다. 비용과 자료 전송 범위를 먼저 정합니다.

모델 제공자가 동작을 바꾸거나 예정된 버전이 종료되면 새 모델로 조용히 바꾸지 않습니다. 허용 후보를 평가하고 호환 릴리스로 배포합니다. 실행 불가 시 명시적 오류·내부 인계로 처리하고, 평가하지 않은 모델 자동 fallback은 하지 않습니다.

## 결함과 추가 기능의 운영

| 종류 | 처리 |
|---|---|
| 자료 노출·근거 없는 자동 게시·중복 답변 | 해당 경로 게시를 먼저 막고 원인·영향 문의 확인, 회귀 fixture와 긴급 릴리스 |
| 특정 자료 연결 실패 | 해당 연결 격리·개발자 인계, 다른 도메인 유지, 실제 연결 복구 검증 |
| 느린 답변·과도한 비용 | 대기/검색/원본/AI/게시 단계를 분리 측정하고 병목 수정 |
| 표현·사용성 개선 | 실제 질문 예시와 이해도 기준 고정, 필수 근거 유지 검증 |
| 신규 기능·채널·도메인 | 권한·지원 범위·최소 수용 기준을 정한 뒤 제한 환경부터 확대 |

결함 기록은 문의 correlation ID, 릴리스·정책·snapshot, 비민감 재현, 기대/실제 결과, 영향 범위, 수정·재검증을 연결합니다. 운영 대화 원문을 공개 이슈나 테스트 fixture로 자동 복사하지 않습니다.

긴급 수정 브랜치는 운영 중인 릴리스 커밋에서 만들고 main에도 동일 수정을 반영합니다. 아직 배포되지 않은 무관한 기능을 긴급 패치에 섞지 않습니다. 두 갈래 수정의 누락을 릴리스 검사로 확인합니다. 자세한 배포·복귀는 [배포 전략](delivery.md)을 따릅니다.

## 지원 범위와 운영 책임

첫 운영은 현재 서버 릴리스와 실제 복귀 검증한 직전 호환 릴리스까지 유지하는 것을 기본안으로 둡니다. 이는 스킬·로컬 봇의 기존 지원을 중단한다는 뜻이 아닙니다. 로컬 설치·설정·공유 형식 변경은 별도 호환 안내와 L01~L03 검증을 거칩니다.

새 코드·새 schema가 직전 버전 복귀를 막으면 배포 전에 복귀 대신 수정 배포 또는 복구 방법을 명시합니다. 배포 이미지·설정·검사·migration·원장은 정한 복귀 기간 동안 보관합니다. 자동 cleanup이 마지막 복귀 이미지를 지우지 못하게 합니다.

| 책임 | 맡을 일 |
|---|---|
| 제품 개발 담당 | 계약·코드·스킬·테스트·릴리스 노트 |
| 도메인 담당 | 업무 정답·자료 연결·공개 범위·미확인 문의 |
| 배포/운영 담당 | 인프라·승격·관측·장애·백업·복구·비용 |
| 보안/플랫폼 담당 | 서비스 인증·망·DB 읽기 승인·접근 정책 |

처음에는 같은 사람이 여러 책임을 맡을 수 있지만 담당자와 부재 시 대체자를 기록합니다. 운영 권한을 가진 사람이 없거나 복구를 수행할 사람이 없으면 상시 서비스로 열지 않습니다.

## 기능 완료 체크

- 문제·범위·합격 기준과 실제 실패 재현이 있습니다.
- 코드·계약·설정·스키마·스킬 변경과 호환 범위가 설명돼 있습니다.
- 관련 자동 검사·실제 모델/회사 검사·기존 로컬 회귀가 증거와 연결됩니다.
- 비밀 없는 로그·진행 상태·내부 지원 경로·비용 제한이 있습니다.
- 배포·복귀·data migration·기존 문의/카드 처리가 검증됩니다.
- 사용자 문서·운영 절차·테스트 ID·릴리스 기록이 최종 구현과 일치합니다.

이 조건을 충족하지 않은 기능은 “코드 작성 완료”와 “운영 제공 가능”을 구분해 표시합니다.
