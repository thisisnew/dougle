# 구현 순서와 수용 기준

[서버 설계 입구](README.md)

이 문서는 앞으로 실행할 개발·검증 계획입니다. 아래 테스트는 모두 `NOT_RUN`으로 시작합니다. 기존 로컬 봇의 통과 결과나 이번 문서의 링크·그림 검사로 서버 동작을 통과 처리하지 않습니다.

## 구현 순서

| 단계 | 작업과 산출물 | 종료 조건 |
|---|---|---|
| M0 범위 고정 | 회사 자원·계정·자료 전송·공개 범위·보관·담당자 결정, 현재 로컬 회귀 기준 보존 | [입구 문서](README.md)의 회사 확인 항목과 변경 결정 기록 |
| M1 계약 추출 | Engine·Store·Knowledge·SourceReader·Authorization 계약, 로컬 어댑터 연결 | 기존 로컬 기능·설치·스킬 사본 검사 통과, 서버가 없어도 로컬 실행 가능 |
| M2 서버 기반 | Linux 실행, 시크릿 연결, PostgreSQL 마이그레이션, 역할 시작·종료·진단 | 실제 PostgreSQL로 접수·ack·단일 작업·복구 검사 |
| M3 지식 수신 | 등록 저장소 수신, 증분 목록, 3방향 병합, 스냅샷·수정 제안 | K01~K12, 자료량별 측정, 개인 저장소 미변경 |
| M4 병렬 조사 | 스레드 소유권·세대·예산 예약·엔진 격리·세션 복원 | J01~J12, C01~C06, E01~E07 |
| M5 자료 접근 | 읽기·공개 정책, 실제 capability, BigQuery·운영 조회·이미지 | A01~A12, Q01~Q10; 권한 없는 조회·공개 0건 |
| M6 게시·내부 지원 | outbox, 전송 원장, 개발자 인계·보충·직접 응대·안내 | D01~D12, H01~H09, 실제 Slack 제한 채널 검증 |
| M7 운영·이전 | 관측, 중지·drain, 백업·복원, ID·카드 마이그레이션 | O01~O10, 실제 복원 연습, 전환·되돌리기 기록 |
| M8 제한 운영 | 한 도메인·제한 채널에서 운영, 지연·정확도·비용 관찰 | 아래 회사 수용 검증과 운영 책임자 승인 |

M1 이후 인터페이스가 고정되면 지식·조회 어댑터 개발을 병행할 수 있습니다. M4~M6 통합 완료 전에는 자동 게시를 열지 않습니다. 모델 엔진 교체는 M4의 별도 변경으로 진행하고 기존 실행기를 비교 기준으로 남깁니다.

## 테스트 층

| 층 | 도구·환경 | 증명하는 범위 |
|---|---|---|
| 계약·정책 | fake Slack·AI·원본, 가짜 시계, 임시 파일 | 상태 전이, 입력 검증, 권한·근거 규칙 |
| 저장·경합 | 실제 PostgreSQL, 서로 다른 프로세스, 격리 테스트 DB | 잠금·트랜잭션·유일 제약·소유권 |
| 장애 주입 | 프로세스 종료, 지연·단절·429·불명 응답, 시각 제어 | 복구, 중복 방지, 비용 보류 |
| 모델 행동 | 실제 허용 모델 + 합성 업무 자료·가짜 조회 | 조사 선택, 자료 충실성, 스킬·영수증 계약, 쉬운 존댓말 |
| 회사 연동 | 허용된 제한 Slack 채널·서비스 계정·읽기 자료 | 실제 API·인증·네트워크·모델·UI 동작 |
| 부하·복원 | 명시한 장비·모델·자료량·동시성·백업 | 측정한 환경의 처리량·복구 시간 |

PostgreSQL 잠금 검사를 SQLite fake로 대신하지 않습니다. 모델의 도구 반환과 영수증을 미리 정답 ID로 맞춰 넣는 테스트만 작성하지 않습니다. 실제 어댑터가 만드는 ID·stream·성공 기록을 연결하는 검사도 포함합니다. 외부 모델 호출 수·실패·비용과 회사 연동 여부를 별도로 남깁니다.

## 테스트 목록

각 행은 독립된 실패 원인과 기대 결과를 갖습니다. 경합은 barrier로 같은 시점을 맞추고 여러 번 실행합니다. sleep 시간에 우연히 의존하는 검사로 끝내지 않습니다.

## 성능 시험 설계

자료량과 변경량을 따로 늘립니다. 지식 1천·1만·10만 파일에서 변경 0개·10개·1%·전체를 측정합니다. 같은 크기뿐 아니라 긴 파일·작은 파일·연결이 많은 토픽을 섞습니다. 최초 수신, 반복 수신, 실패 후 재개를 분리합니다.

질문은 업무 설명·코드·현재 DB·이미지·후속 질문·개발자 보충으로 나눕니다. 동시성 1·2·4·8에서 같은 스레드 집중과 여러 스레드 분산을 각각 실행합니다. API 비용·운영 DB 허용량 안에서 점진적으로 올립니다.

기록에는 장비·컨테이너 제한, 코드·스킬·모델 버전, 자료 목록 해시, 캐시 유무, 반복 수, 오류 수, 토큰·비용, p50/p95/p99를 남깁니다. 적은 표본의 p99는 신뢰 한계를 함께 표시합니다. 접수 대기·검색·원본 읽기·AI 작성·게시 시간을 분리합니다.

초기 합격 기준은 다음과 같습니다.

- 합성 접수 부하에서 저장 후 ack가 1초 이내 p95이며 Slack 제한을 넘는 사례를 따로 보고합니다.
- 동일 커밋 재수신에서 의미 병합·본문 재작성 횟수는 0입니다.
- 다른 스레드 2건이 실제로 겹쳐 실행되고 같은 스레드는 겹치지 않습니다.
- 설정된 메모리·비용·조회 제한을 넘기면 안전하게 대기·중단하며 조용한 유실은 없습니다.
- 기준 버전보다 검색·갱신·응답 시간이 나빠지면 원인을 설명하고 출시 판단을 남깁니다. AI 호출까지 포함한 속도 향상을 파일 검사만으로 주장하지 않습니다.

고객 답변 완료 시간의 목표는 회사 자료·모델로 첫 측정한 뒤 확정합니다. 서버로 이전했다는 이유만으로 10초 응답 같은 수치를 약속하지 않습니다.

## 회사 수용 검증

실제 담당자와 질문별 기대 결과를 먼저 정하고 제한 채널에서 실행합니다. 최소 항목은 일반 업무, 명시적 코드 확인, BigQuery 집계, 사본 지연, 운영 DB 접근 불가, 이미지+코드 조사, 같은 스레드 후속, 개발자 보충, 직접 응대, 권한 거부, 토큰 회전, 재시작입니다.

자료를 실제로 읽었는지, 설명이 자료와 맞는지, 비전문가가 이해할 수 있는지, 불필요한 세부가 많은지를 따로 평가합니다. 고객에게 보낸 문장과 내부 근거를 함께 보되 민감 자료는 공개 레포에 올리지 않습니다.
