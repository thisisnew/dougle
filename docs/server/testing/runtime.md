# 접수·병렬 작업·비용·엔진 테스트

[공통 준비·출시 기준](README.md) · [수용 기준 색인](../implementation.md)

모든 사례는 구현 후 실행할 `NOT_RUN` 명세입니다. 공통 증거에 각 사례의 증거를 추가합니다. 한 사례에 나열된 변형은 모두 필수입니다.

## J01 · 동일 이벤트 여러 번 도착

- **환경:** PG·수신 어댑터
- **준비:** 수신기 2개와 같은 이벤트 E 준비
- **절차:** 동일 E를 20회 동시에 보냅니다. 다른 envelope_id, 다른 event_id지만 같은 trigger인 변형도 보냅니다.
- **합격:** 유효 문의·초기 작업은 각각 1개입니다. 중복 ack는 허용되나 AI·접수 부수 효과의 중복을 만들지 않습니다.
- **증거:** processed_events·inquiry·job 카운트, 외부 호출 원장

## J02 · DB 커밋 실패

- **환경:** PG·수신 어댑터
- **준비:** 아직 접수되지 않은 E
- **절차:** 문의 INSERT 후 커밋 실패를 주입하고 같은 E를 재전송합니다.
- **합격:** 실패 시 성공 ack와 부분 문의가 없습니다. 재전송 시 정확히 한 문의를 접수합니다.
- **증거:** TX 결과와 ack 순서, 행 카운트

## J03 · 커밋 후 ack 직전 종료

- **환경:** PG·kill
- **준비:** E 접수 커밋 완료, ack barrier
- **절차:** ack 전에 프로세스를 종료하고 재시작 후 E를 재전송합니다.
- **합격:** 기존 문의를 재사용하고 초기 작업을 추가하지 않습니다. 문의는 최종 처리 또는 명시적 대기 상태로 남습니다.
- **증거:** 커밋/kill/ack 타임라인, job 카운트

## J04 · 실제 어댑터의 이벤트 ack

- **환경:** 실제 선택한 Slack 어댑터·PG
- **준비:** SDK 자동 ack 설정까지 운영과 동일, 네트워크 transport만 fake
- **절차:** DB 커밋 barrier를 잡고 실제 envelope를 어댑터로 주입합니다. 성공·실패 두 경로를 실행합니다.
- **합격:** 커밋 전 ack가 없고 성공 후 ack됩니다. AI·원본·DM 호출은 ack 경로 밖입니다. SDK가 선 ack하면 구현 실패로 판정합니다.
- **증거:** transport 송신 시각과 TX·엔진 시작 순서

## J05 · 같은 스레드 동시 질문

- **환경:** PG·독립 worker
- **준비:** T1에 접수 순서가 다른 질문 3개
- **절차:** worker 2개로 동시 선점합니다. 첫 문의를 needs_developer로 전환한 뒤 후속을 진행합니다.
- **합격:** T1 활성 조사는 최대 1개이고 접수 순서를 지킵니다. 내부 확인 대기는 소유권을 반환해 후속을 막지 않습니다.
- **증거:** job 시작/종료 구간·thread lease

## J06 · 다른 스레드 다수 질문

- **환경:** PG·독립 worker
- **준비:** max_parallel=2, T1~T8에 지연 가능한 작업
- **절차:** 8개를 접수하고 worker를 여러 개 띄웁니다. 하나씩 완료시킵니다.
- **합격:** 전체 활성 AI는 최대 2개이며 다른 스레드 2개는 실제 겹칩니다. 실행기 수 증가로 전역 한도를 우회하지 않습니다.
- **증거:** 동시 실행 최대값, 대기·선점 순서

## J07 · 소유권 만료 후 새 작업자 선점

- **환경:** PG·barrier
- **준비:** worker A의 epoch 1 작업을 중단하고 lease 만료, B가 epoch 2 선점
- **절차:** B 결과 전후에 A의 완료·비용 보고·제안·outbox 생성을 시도합니다.
- **합격:** A는 새 결과·제안·게시를 확정하지 못합니다. 늦은 실제 비용은 기존 실행과 연결해 별도 정산하되 답변은 되살리지 않습니다.
- **증거:** 영향 행 수, epoch·generation·예산·outbox

## J08 · 작업자 추가 시작

- **환경:** PG·독립 프로세스
- **준비:** A가 정상 heartbeat 중
- **절차:** B와 복구기를 추가 시작하고 A의 장기 작업을 유지합니다.
- **합격:** A는 running으로 유지되며 초기화·중복 선점하지 않습니다. 만료 작업만 복구 대상입니다.
- **증거:** 시작 전후 job/lease, engine 호출 수

## J09 · 결과 저장 중 실패

- **환경:** PG·실패 주입
- **준비:** 검증된 결과와 비용·제안 준비
- **절차:** draft, job 완료, 비용, outbox, audit 저장 사이마다 오류를 주입합니다.
- **합격:** 각 실패에서 전체 결과 TX가 롤백됩니다. 재실행 후 revision·정산·outbox는 한 번만 확정됩니다.
- **증거:** 각 지점 DB diff, 외부 Slack 호출 0건

## J10 · 대기열 한도 초과

- **환경:** PG·fake Slack
- **준비:** queue_capacity=2, 작업 선점 정지
- **절차:** 서로 다른 이벤트 3개와 세 번째 재전송을 넣습니다. 자동/검토 모드를 각각 실행합니다.
- **합격:** 3번째는 overloaded 기록과 자동 모드 안내 최대 1개, AI job 0개입니다. 검토 모드는 공개 안내가 없습니다. 최소 기록 실패 시 ack하지 않습니다.
- **증거:** event 결정, nullable inquiry outbox 제약, 큐·안내 수

## J11 · 일부 연결이 오래 지연

- **환경:** PG·fake 원본
- **준비:** 연결 A만 느리고 B는 정상, 전체 병렬 여유 있음
- **절차:** A 문의를 시작한 뒤 B 문의를 넣고 A 제한시간을 넘깁니다.
- **합격:** B는 A 종료를 기다리지 않습니다. A는 제한 내 중단·내부 확인되고 다른 연결을 재시작하지 않습니다.
- **증거:** 연결별 호출·단계 시간, 활성 제한

## J12 · 작업자 강제 종료·시계 차이

- **환경:** PG·kill·가짜 앱 시계
- **준비:** worker별 앱 시각에 큰 차이, 외부 조회는 취소 무시
- **절차:** worker를 강제 종료하고 DB 기준 lease 만료 후 복구합니다.
- **합격:** 소유권 판단은 DB 시각입니다. 오래된 완료를 거절하고 취소되지 않은 조회의 연결·비용을 추적합니다.
- **증거:** DB now·lease, provider job ID와 비용 보류

## C01 · 마지막 예산을 두 작업자가 동시 예약

- **환경:** PG·barrier
- **준비:** 남은 예산은 한 호출만 수용 가능
- **절차:** 두 worker가 동시에 같은 UTC 계정에서 예약합니다.
- **합격:** 하나만 시작하고 spent+reserved+uncertain은 한도를 넘지 않습니다. 예산 부족 경로는 AI 미호출입니다.
- **증거:** 계정 전후, engine 호출·예약 행

## C02 · 엔진 비용 미반환·비정상 종료

- **환경:** PG·fake 엔진
- **준비:** 예산 예약 후 호출 시작
- **절차:** 비용 필드 누락, timeout, 프로세스 종료를 각각 주입하고 다음 문의를 접수합니다.
- **합격:** 예약이 무료로 반환되지 않고 uncertain으로 보류됩니다. 제공자 대조 후에만 확정하며 후속 예약에 반영합니다.
- **증거:** 예약→보류→정산 이력

## C03 · 완료 응답 중복 도착

- **환경:** PG·barrier
- **준비:** 한 run의 비용 확정 결과 준비
- **절차:** 같은 완료를 동시에·재시작 후 반복 전달합니다.
- **합격:** run별 한 번 정산하고 음수 예약·중복 spent 증가가 없습니다.
- **증거:** 계정 합계·정산 유일 제약

## C04 · UTC 날짜 경계에서 실행 종료

- **환경:** PG·제어 시계
- **준비:** UTC 23:59 시작 계정과 다음 날짜 계정
- **절차:** 날짜를 넘겨 완료하고 비용을 정산합니다. KST 날짜도 함께 비교합니다.
- **합격:** 시작 시 예약한 UTC 계정에 대응해 정산합니다. 새 날 예산에 중복 청구하거나 예약이 남지 않습니다.
- **증거:** 시작/완료 UTC, 계정 날짜와 합계

## C05 · BigQuery 비용 한도 초과

- **환경:** BQ 어댑터·PG
- **준비:** AI 예산 충분, dry run 추정값이 BQ 한도 초과
- **절차:** 조회 계획을 실행하고 한도 이내 변형도 실행합니다.
- **합격:** 초과는 실제 query 미실행, 이내는 maximum_bytes_billed 등 설정 전달 확인. LIMIT으로 비용 검사를 대체하지 않습니다.
- **증거:** dry run·실행 호출 수, 제한 파라미터·각 예산

## C06 · 알려진 확정 실패·재시도

- **환경:** PG·fake 엔진
- **준비:** 첫 시도는 비용이 확정된 일시 실패, 두 번째 성공
- **절차:** 읽기 재시도 2회 상한, 형식 보완 1회, 전체 기한 초과를 별도 변형으로 실행합니다.
- **합격:** 시도별 실제 비용과 예약이 일치합니다. 상한·기한 뒤 추가 호출이 없고 확정된 미사용분만 반환합니다.
- **증거:** attempt별 예약/정산/오류·호출 시간

## E01 · 세션 파일 없음

- **환경:** 실제 엔진 어댑터·합성 대화
- **준비:** 세션 파일 삭제, 실제 게시된 수정 답변과 미게시 후보 존재
- **절차:** 같은 스레드 후속을 실행해 세션 없음 응답을 주고 복원합니다.
- **합격:** 허용 대화·실제 게시본을 복원하며 미게시 후보를 고객에게 말한 것으로 취급하지 않습니다. 코드·현재값 근거를 새로 읽습니다.
- **증거:** 복원 context digest, 원본 호출·신규 session

## E02 · 권한 축소 후 동일 스레드 질문

- **환경:** 엔진·PG
- **준비:** 기존 세션이 제한 자료를 읽은 상태
- **절차:** 정책 축소 후 같은 스레드에서 후속 질문합니다.
- **합격:** 기존 세션·캐시는 사용하지 않고 허용된 대화로 새 문맥을 구성합니다. 제한 내용이 응답·DM에 재등장하지 않습니다.
- **증거:** session ID 변경, 정책 버전·출력 canary

## E03 · 지식 버전·스킬 계약 변경

- **환경:** 엔진·PG
- **준비:** S0·스킬 v1·엔진 v1의 세션
- **절차:** snapshot, skill bundle, engine 계약을 각각 변경하고 후속을 실행합니다.
- **합격:** 새 문맥과 계약을 사용합니다. 과거 영수증을 최신 실행의 직접 확인으로 표시하지 않습니다.
- **증거:** 실행 버전·근거 관측 시각·복원 메타데이터

## E04 · 필수 스킬 누락·실패

- **환경:** 실제 stream/receipt 파서
- **준비:** 정상 근거가 있는 합성 엔진 stream
- **절차:** dougle-ask/i-have-adhd/plain-language 각각 누락·실패·중복 ID를 주입합니다. 보완 호출도 검사합니다.
- **합격:** 필수 스킬 성공이 없으면 게시 차단, 조사 요구는 유지합니다. 보완 허용을 운영 조회 생략에 사용하지 않습니다.
- **증거:** 스킬 기록·검증 사유·게시 0건

## E05 · 모델의 근거 ID와 실제 도구 기록 불일치

- **환경:** 실제 stream/receipt 파서
- **준비:** 운영 어댑터가 만든 ID를 쓰는 정상 fixture
- **절차:** 잘못된 ID·다른 run·실패 도구·범위/버전 불일치·모델 verified=true를 변형으로 제출합니다.
- **합격:** 정상 fixture는 통과하고 불일치는 차단합니다. 어떤 연결이 부족한지 내부 진단을 남기며 권한 오류로 단정하지 않습니다.
- **증거:** raw fixture 해시, 실제 생성 ID 대조·진단

## E06 · 질문이 짧거나 “간단히” 요청

- **환경:** 실제 모델·합성 도구
- **준비:** 업무 설명/현재 코드/현재 DB/이미지 질문의 정답과 필수 도구 정의
- **절차:** 보통 표현과 '한 줄로 간단히'를 각각 질문합니다.
- **합격:** 표현은 짧아져도 필수 코드·DB 근거가 유지됩니다. 모르는 조건을 단정하지 않고 핵심·조건·다음 행동을 남깁니다.
- **증거:** 질문쌍 출력, 실제 tool trace·정답 평가

## E07 · 작업별 파일·환경에 다른 문의 정보 삽입

- **환경:** 격리 엔진 프로세스
- **준비:** A/B의 별도 디렉터리·인증 범위·가짜 canary
- **절차:** A가 B의 절대/상대 경로·환경·세션을 읽도록 유도하고 두 작업을 동시 실행합니다.
- **합격:** OS/도구 경계에서 접근 차단되고 출력·로그에 B canary가 없습니다. 종료 후 임시 파일도 보관 정책대로 정리합니다.
- **증거:** 접근 거부·출력 스캔·마운트/권한 설정
