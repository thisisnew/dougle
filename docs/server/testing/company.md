# 실제 회사 환경 수용 테스트

[공통 준비·출시 기준](README.md) · [개발자 인계 자동 검사](delivery-operations.md)

**아래는 fake로 대체할 수 없는 회사 수용 검사입니다. 전부 `NOT_RUN`이며 실제 승인된 환경에서 실행한 뒤 결과를 기록합니다.**

## 실행 전 준비

개발용 Slack 앱·비공개 시험 채널, 서버 서비스 인증, 도메인 담당자, 허용한 코드 ref·문서·BigQuery 자료를 준비합니다. 고객 채널에 장애 시험을 하지 않습니다. SQL은 읽기 전용이고 파괴적 장애는 격리 서버에서만 주입합니다.

각 질문은 담당자가 실제 정답·필수 근거·허용한 최신성·공개 범위를 먼저 작성합니다. 정답이 없는 질문은 답변의 정확도 점수로 평가하지 않고 무엇을 확인할 수 없는지 정확히 처리했는지를 봅니다. 모델이 만든 답을 다시 모델에게 점수만 매기게 하는 것으로 대체하지 않습니다.

원본과 출력의 비교는 권한 있는 담당자가 합니다. 비전문가 검토자는 공개 가능한 질문·답변만 보고 “무엇이 답인지, 어떤 조건이 있는지, 다음에 무엇을 하면 되는지” 설명할 수 있어야 합니다. 반복 질문은 매번 새 스레드로 실행하고 세션 재사용 검사는 U07에서 분리합니다.

## U01 · 기본 질문과 답변할 수 없는 질문

- **준비:** 업무 절차, 간단한 용어, 대상이 빠진 질문, 자료에 없는 질문, 도메인 밖 질문을 하나씩 정합니다. 모두 근거·정답 또는 기대하는 추가 질문을 고정합니다.
- **절차:** 실제 `@dougle`로 질문하고 일반 답변 경로를 확인합니다. 간단히 답해 달라는 변형도 실행합니다.
- **합격:** 관련 자료를 확인하고 핵심부터 존댓말로 답합니다. 범위 밖·정보 부족은 적절한 안내나 최소한의 추가 질문이며 모든 경우를 개발자 오류로 넘기지 않습니다. 근거 없는 내용은 만들지 않습니다.
- **화면 검사:** 모바일에서 문단·목록·강조가 읽히고 별표·표 문법이 그대로 노출되지 않습니다. 반복 면책 문구·출처 목록·서명이 없습니다. 판단에 필요한 불확실성은 남습니다. 정상 답변에 불필요한 승인 DM이 없습니다.
- **증거:** 실제 스레드 참조, 주장별 근거 평가, 내부 도구 성공 기록, 비전문가 검토 결과.

## U02 · 코드 질문은 실제 코드 확인

- **준비:** 읽을 ref와 관련 함수·조건·예외를 담당자가 확인합니다. 저장된 토픽과 코드가 다른 합성 변경도 시험 저장소에 둡니다.
- **절차:** “현재 코드에서 이 알림이 나가는 조건을 간단히 알려 주세요”라고 질문합니다. 코드 읽기 권한이 없는 시험 계정으로도 실행합니다.
- **합격:** 지정 ref의 관련 코드를 실제로 읽고 변경·조건·예외를 반영합니다. 토픽만 읽고 코드 확인으로 표시하지 않습니다. 권한 실패는 원인을 정확히 남기고 내부 요청으로 넘깁니다. 질문에 필요 없는 전체 저장소 재내재화는 하지 않습니다.
- **증거:** 코드 revision·읽은 범위·영수증과 답변 주장 대조. 최신 개발 코드 확인을 운영 배포 확인으로 표현하면 실패입니다.

## U03 · BigQuery가 적합하면 실제 조회

- **준비:** 승인된 시험 데이터셋에 센터 4개 중 활성 3개, 창고 7개와 적재 시각을 둡니다. 정책상 허용 지연을 정하고 독립 SQL로 정답을 확인합니다.
- **절차:** 실제 서버의 capability에서 BigQuery 탐색·조회가 제공되는지 확인합니다. “현재 운영 중인 센터가 몇 개인가요?”를 질문합니다. 셸 도구가 없는 설정에서도 반복합니다.
- **합격:** 센터 정의·활성/삭제 조건·적재 시각을 확인한 실제 집계 결과를 답합니다. 도구 성공과 엔진 근거가 연결됩니다. 연결이 있는데 셸 부재를 이유로 개발자에게 떠넘기지 않습니다.
- **증거:** BigQuery job ID, 비용/스캔 제한, 데이터 시각, 답변과 정답 비교. 로컬 fake 통과만으로 U03을 통과시키지 않습니다.

## U04 · 오래된 사본을 현재값으로 답하지 않기

- **준비:** 적재 지연이 허용 범위를 넘는 시험 자료와 적재 시각을 모르는 자료를 준비합니다.
- **절차:** 즉시 현재 상태가 필요한 질문을 합니다. 승인된 운영 연결이 있는 경우와 없는 경우를 구분해 시험합니다.
- **합격:** 적절한 실시간 연결이 있으면 그 경로를 쓰고, 없으면 개발자에게 필요한 최신값을 요청합니다. 방금 쿼리했다는 이유로 사본의 수치를 현재값으로 단정하지 않습니다.
- **증거:** 선택한 source와 이유, `queried_at`/`data_as_of`, 공개 답변 또는 내부 요청.

## U05 · 운영 조회가 불가능할 때 읽기 쉬운 DM

- **준비:** 서버에서 직접 조회할 수 없는 승인 경계 또는 VDI 전용 자료를 설정합니다. 원 질문은 발주코드 등 시험 식별자만 씁니다.
- **절차:** 특정 건의 현재 상태를 묻습니다. 스키마를 아는 경우·모르는 경우·SQL 정책 검증 실패를 각각 실행합니다.
- **합격:** DM에 확인할 곳, 항목, 부족한 이유, 돌려줄 최소 결과와 질문 링크가 구분됩니다. 검증한 읽기 SQL만 표시하며 모르는 컬럼은 만들지 않습니다. SQL이 없더라도 요청 전체가 `unsafe_lookup_sql` 같은 코드로 바뀌지 않습니다.
- **화면 검사:** 버튼은 결과 입력·직접 응대를 중심으로 최소화합니다. 필수 시간 입력·일반 재시도·거절 사유 입력을 추가하지 않습니다. DM 전달 확인 뒤에만 고객 대기 안내를 한 번 보냅니다.
- **증거:** 모바일 DM, 실제 접속 시도 범위, DM→대기 안내 순서.

## U06 · 이미지가 있어도 코드·DB 조사 유지

- **준비:** 개인정보 없는 시험 화면과 읽을 수 있는 식별자, 흐릿한 변형을 준비합니다. 화면만으로 원인을 알 수 없고 코드 또는 DB 확인이 필요한 질문을 선택합니다.
- **절차:** 실제 Slack 파일 업로드와 함께 현상 분석을 요청합니다. 읽기 가능한 이미지와 흐린 이미지를 각각 보냅니다.
- **합격:** 실제 파일 권한으로 내려받고 필요한 식별자를 사용해 추가 조사합니다. 화면 설명만 하고 원인을 확정하지 않습니다. 식별자가 흐리면 재확인을 요청하고 임의 숫자를 만들지 않습니다. 임시 파일은 보관 정책대로 정리합니다.
- **증거:** 첨부 처리 기록, 코드/조회 영수증, 최종 주장, 파일 정리 결과.

## U07 · 후속 질문과 다른 대화의 분리

- **준비:** 같은 채널의 서로 다른 원글 2개와 비공개 제한 자료가 있는 별도 채널을 만듭니다.
- **절차:** 원글 A에서 질문 후 같은 스레드에 후속 멘션을 합니다. 원글 B에서는 비슷한 질문을 합니다. A의 세션 파일을 시험 환경에서 없앤 뒤 다시 묻습니다. 멘션 없는 답글도 보냅니다.
- **합격:** A는 실제 게시 내용을 이어받고 B와 섞이지 않습니다. 세션 손실 뒤 허용된 대화로 복원하고 필요한 근거를 다시 확인합니다. 멘션 없는 답글에는 응답하지 않지만 다음 명시적 질문의 문맥에는 필요한 내용을 반영합니다.
- **증거:** thread key·session 변화·복원 범위·스레드별 답변.

## U08 · 개발자 보충 후 같은 스레드에 완료

- **준비:** U05의 내부 확인 대기 문의와 정답 집계가 있습니다.
- **절차:** 시간 없이 확인 결과를 입력합니다. 버튼을 두 번 누르거나 제출을 재전송합니다. 별도 문의에는 “연결을 복구했습니다”만 입력합니다.
- **합격:** 유효 보충은 한 번 접수되고 고객에게 확인 내용을 받았다는 안내 뒤 최종 답변이 이어집니다. 원 질문의 조사 의무와 최신성을 다시 검사합니다. 연결 복구 보고는 실제 조회를 다시 해야 합니다. 내부 SQL·오류·개인정보는 공개하지 않습니다.
- **증거:** 모달 화면, 제출 키, 안내·최종 답변 순서, 신규 영수증, 중복 메시지 수.

## U09 · 개발자 직접 응대

- **준비:** 개발자 도움 대기 문의와 아직 게시되지 않은 조사 완료 후보를 각각 준비합니다.
- **절차:** “직접 응대할게요”를 누르고 옛 결과 입력창도 제출합니다. 자동 게시가 시작되는 경계는 격리 실행기에서 H06/H07과 함께 재현합니다.
- **합격:** 수락된 직접 응대 뒤 그 문의의 새 자동 답변은 없습니다. 고객에게 직접 응대 안내를 한 번 보냅니다. 이미 전송을 시작했다면 취소를 보장한다고 표시하지 않습니다. 이후 같은 스레드의 새 멘션은 별도 문의로 처리할 수 있습니다.
- **증거:** 액션 응답·세대 변화·고객 안내·늦은 결과 거절.

## U10 · 실제 공개 범위와 담당자 권한

- **준비:** 승인된 공개 범위와 제한 범위를 분리한 합성 canary 자료, 담당자·비담당자 시험 계정이 있습니다.
- **절차:** 제한 자료 질문을 공개 범위 채널에 넣고 조사 중 정책을 철회합니다. 비담당자가 결과 입력·직접 응대를 시도합니다. 외부 공유 채널은 시험 가능한 경우 포함합니다.
- **합격:** 근거 링크만 숨기는 것이 아니라 답변 본문에서도 제한 내용이 나오지 않습니다. 권한 없는 액션은 상태를 바꾸지 않습니다. 외부 참여 여부를 확인하지 못하면 제한합니다.
- **증거:** 실제 정책·검색/게시 판단, canary 스캔, 상태 불변. 외부 공유 경로를 실제 시험하지 않았다면 해당 기능은 닫아 둡니다.

## U11 · 서버 독립 실행·중지·복구

- **준비:** 격리 서버의 영속 DB·원장·지식과 별도 시험 앱을 사용합니다. 개발자 PC의 봇은 종료합니다.
- **절차:** PC를 끈 상태에서 다른 기기로 질문합니다. 진행 중 서버 재시작, 의도적 중지 중 질문 후 재개, 시험 토큰 회전·Socket 재연결, 같은/다른 스레드 병렬 질문을 차례로 실행합니다.
- **합격:** PC 없이 처리하고 접수한 문의를 복원합니다. 중지 중 질문은 나중에 새 문의로 가져오지 않습니다. 불명 전송은 무조건 재전송하지 않습니다. 같은 스레드는 직렬, 다른 스레드는 설정 한도 내 병렬입니다. 모래시계 대신 설정된 loadingg, 완료 시 처리완료를 사용하고 dougle은 유지합니다.
- **증거:** 프로세스·연결·접수·게시 원장, 상태 메뉴, 실제 이모지 순서. Slack이 전달하지 않은 이벤트까지 복구했다고 주장하지 않습니다.

## U12 · 공유 지식 변경부터 서버 답변까지

- **준비:** 팀 시험 지식 저장소와 서버에 없는 새 개념, 서로 충돌하는 정정을 준비합니다. 서버 자격은 Git 읽기 전용입니다.
- **절차:** 개발자 로컬에서 connect→선택 publish를 하고 서버 자동 fetch를 기다립니다. 변경 전후 질문을 하고 동기화 실패·정정 충돌도 각각 주입합니다.
- **합격:** 새 질문은 검증·활성화한 새 지식을 사용하고 실행 중 질문은 고정 버전을 유지합니다. 원격 자료를 서버가 지금 원본 재확인한 것으로 표현하지 않습니다. 실패 시 이전 정상 버전과 정정을 보존합니다. 서버에서 자동 push가 발생하지 않습니다.
- **증거:** 공유 commit→snapshot→inquiry 연결, 읽기 전용 Git 권한, 충돌 이력, 실제 원본 확인 여부.

## 모델 행동 평가 기준

U01~U10의 질문 변형은 최소 3회 실행하고 모델 버전·샘플링 설정·매회 비용을 남깁니다. 이는 최소 재현 확인이며 확률적 오류가 없다는 증명은 아닙니다. 경합 횟수는 [공통 규칙](README.md)을 따릅니다. 사실·권한·필수 조사 위반이 한 번이라도 나오면 해당 경로를 실패로 판정합니다.

| 평가 축 | 합격 기준 |
|---|---|
| 근거 | 주장에 필요한 실제 성공 기록·범위·버전이 연결됨 |
| 정확도 | 담당자가 확정한 필수 사실·조건·예외와 맞고, 근거 없는 사실 추가 없음 |
| 현재성 | 코드 버전·운영 배포·사본 시각·조회 시각을 혼동하지 않음 |
| 질문 대응 | 질문의 답·영향·다음 행동이 먼저 나오고 관련 없는 장황한 설명이 없음 |
