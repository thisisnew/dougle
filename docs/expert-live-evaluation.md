## 2026-10-25 추가: 프로세스 I/O 스케줄러 고갈 재현과 수정

위 30회 제한과 재평가 미실행 문구는 최초 평가 당시 기록이다. 이후 사용자가 합성 자료의 실제 AI 추가 평가를 승인해 총량 제한을 해제했다. 실행은 여전히 유한한 배치별 상한·요청 직전 호출 수 기록·실패 시 자동 재전송 금지를 유지한다. [후속 실제 평가](evaluations/investigation-live-v3-20261025-review.md)와 [배치 실행 방법](evaluations/investigation-live-method.md)을 별도로 본다.

### 확인된 재현 경로

`CodexAppServerTest.optInRoutesCodexAnswerThroughIsolatedStreamAndReleasesProcessAndLock`가 통합 검사에서 실패했다. 최초 검사는 부분 출력 대기 5초 뒤 실패해 실행 오류를 가렸고, 부분 출력을 받은 뒤 완료 전임을 검사하는 조건도 fixture의 1.8초 지연에 의존했다. 부분 출력 관측을 명시적 latch로 동기화하고 실패 future도 함께 관측하도록 변경했다. 부분 대기는 기존 실행 제한인 8초에 맞췄으며 실제 생성의 8초 제한은 늘리지 않았다. 이후에는 가상 제공자에서도 `답변 생성` 단계의 실행 시간 초과가 드러났다. 따라서 단순히 테스트 대기 시간만 늘리는 것으로 해결했다고 보지 않는다.

같은 단일 검사는 일반 JVM에서 통과했지만, 별도 JVM에서 `-Djdk.virtualThreadScheduler.parallelism=1 -Djdk.virtualThreadScheduler.maxPoolSize=1`로 carrier를 하나로 제한하면 실패했다. 수정 전 재현 로그는 `/tmp/dougle-provider-carrier-repro.log`이며 1개 검사에서 `TimeoutException`이 발생했다. 해당 합성 테스트 JVM의 스레드 덤프만 확인했으며 실제 제공자 메시지·인증 내용은 덤프하지 않았다. 재현 중 남은 가상 Node 자식 프로세스도 확인 후 종료했다.

확인한 구조적 원인은 **Java 21의 블로킹 subprocess pipe I/O를 virtual-thread executor에 올려 carrier를 점유할 수 있는 경로**다. app-server는 stdout 프로토콜 처리와 stderr 읽기를, exec 계획/생성은 stdout·stderr 읽기와 stdin 쓰기를 같은 종류의 executor에 제출했다. 제한된 carrier에서 읽기가 먼저 막히면 프로토콜 처리·입력 쓰기·감시 작업이 진행하지 못할 수 있다. 특히 exec에서 두 읽기 작업 때문에 세 번째 stdin 쓰기가 실행되지 않는 위험이 있다. 한 carrier 재현의 실패와 아래 수정 후 같은 제약에서의 통과가 이 스케줄러 의존성을 검증한다. 이것이 과거 실제 서비스 시간 초과의 유일한 원인이었다는 증거는 아니다.

### 수정과 가상 회귀 결과

- `CodexAppServer`: stdout/stderr용 전용 platform-thread pool 2개.
- `CliCuratorModel`: stdout/stderr/stdin용 전용 platform-thread pool 3개. 계획은 `generatePlan → generateInternal → Codex exec` 경로이며 app-server 답변 경로와 구별한다.

- 새 `ProviderProcessIoTest`는 별도 JVM의 carrier를 **1개로 제한한 채** 기존 스트리밍 출력·최종 답변·임시 폴더/프로세스 정리·프로필 잠금 재사용 검사와 CODEX/CLAUDE exec 계획 schema 검사를 실행한다. 전부 가상 실행 파일이며 외부 AI 호출은 0회다.

수정 후 `/tmp/dougle-provider-platform-io-targeted.log` 실행은 **exit 0, 37개 통과, 실패/오류/skip 0개**다. 세부는 app-server 15, 계획 전송 7, 프로필 5, 연결 확인 5, 로그인 4, 제한 carrier 회귀 1개다. 기존 시간 초과·취소·프로세스 정리·출력 제한 검사도 유지했다. 코드 변경 이후 실제 제공자 성공으로 이 숫자를 합산하지 않는다.

### 아직 확인하지 못한 실제 제공자 원인

수정 전 실제 JAR `7fe16e3f7637a5b536702d12059d462117b9d46037e0f6c04813a8b2b8fd680e`에서는 빈 근거 → 실제 PlanModel SEARCH → 로컬 검색 → 새 근거 고정 → 새 승인 → 답변과 후속 질문이 성공했다. 그러나 충분한 근거가 있는 질문의 app-server 답변 제한 시간 초과와, 서로 다른 두 시나리오에서 첫 exec 계획 요청의 90초 제한 시간 초과도 발생했다. 따라서 실패가 항상 세 번째 턴에만 발생한다는 가설은 성립하지 않는다. 이 배치는 8회 전송 시도(계획 5/답변 3)이며 전체 성공으로 표시하지 않는다.

**Platform-thread 수정 후 실제 AI 시간 초과 해결 여부는 아직 미검증이다.** 새 JAR의 해시를 고정하고 유한한 배치로 재평가해야 한다. 답변의 안전한 단계 이름은 INITIALIZE/CONFIG/THREAD/TURN/WAIT_RESPONSE로만 기록하고 원문 stderr·인증·프로토콜 본문을 수집하지 않는다. exec 계획의 90초 감시 제한은 app-server 단계와 관계없으므로 관측하지 못한 내부 단계를 추정하지 않는다. 제공자 기본 모델을 요청했으며 실제 모델 ID도 여전히 미관측이다. 실제 재평가 전에는 이 수정을 실서비스 시간 초과 해결 또는 E01–E50 전체 통과로 보고하지 않는다.

다음 우선 배치는 E01의 서로 다른 표현 3가지 × 실제 2턴(최대 12회: 계획 6/답변 6)이며, 각 trial은 별도 thread에서 후속 문맥을 확인한다. 다음 E03 업무 주제 전환/E02 호출·저장 경로는 별도 최대 8회 배치로 실행한다. 기존 인수 handoff의 E01 PASS 권고는 구 artifact의 짧은 trial 1개에 한정되며, **3표현 반복 규칙을 충족한 최종 인수로 확대하면 안 된다.** 새 artifact 반복 실행과 수동 근거 대조를 마친 뒤 판정을 갱신한다. 준비 자체는 실행 증거가 아니며 시간 초과 시 자동 재시도하지 않는다.

### 같은 날 새 JAR 실제 재평가: 시간 초과 잔존

Platform-thread 수정이 포함된 JAR `1ddab26fc24c41a1a25ab8cc351d98659cccefdace8a0b697f54048a20f8afe0`로 E01 3표현 평가를 시작했다. 첫 trial의 두 답변은 수동 근거 대조에서 적합했지만, 두 번째 trial 첫 답변이 `Codex 답변 생성 단계에서 제한 시간을 초과했습니다.`로 실패해 6회 전송(계획 3/답변 3) 뒤 중단했다. 계획 3회는 exec 경로에서 모두 STOP으로 성공했다. 답변 실패의 안전한 단계는 **CODEX_APP_SERVER / WAIT_RESPONSE**다. turn/start 응답 이후 유효한 완료 답변을 받지 못했다는 범위만 알 수 있으며, 원격 모델·전송·이벤트 처리 중 어디가 원인인지는 확정할 수 없다. 초기화/설정/대화 준비 단계 실패라고 보고하지 않는다.

따라서 **가상 carrier 고갈 회귀 수정은 확인됐지만 실제 AI 시간 초과 전체 해결은 확인되지 않았고, 이번 새 실행에서 재발했다.** E01 3표현 인수도 아직 미충족이다. 시간 제한 증가·자동 재시도·자격 증명/원문 stderr 덤프는 하지 않았다. [새 JAR 원본/수동 대조](evaluations/investigation-live-platform-io-20261025-review.md)에 실제 답변·근거·단계·실패를 보존한다.
