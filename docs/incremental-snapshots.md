# 변경 파일만 다시 분석하기

후속 구현: GitHub의 [같은 SHA 수집 생략·변경 blob만 가져오기](git-incremental.md)를 추가했습니다. 최종 반영은 이 문서의 전체 스냅샷 비교/부분 분석 경로를 그대로 사용합니다.

Source를 다시 동기화할 때 전체 파일을 지우고 다시 넣던 동작을 바꿨습니다.
이제 **경로와 내용 해시가 같은 파일은 그대로 두고, 추가·변경 파일만 분석**합니다.

## 작동 원리

1. 동기화 실행권을 얻은 뒤 현재 파일 해시 목록을 읽습니다.
2. 수집한 새 목록과 비교합니다.
3. 추가·변경 파일만 Tika/JavaParser로 분석합니다.
4. 한 DB 트랜잭션에서 파일별 추가/수정/삭제, 분석·심볼·색인 큐, Source revision을 반영합니다.

| 상황 | 처리 |
|---|---|
| 다른 파일만 변경 | 그대로인 파일 ID·본문·분석·심볼 유지 |
| 같은 경로의 본문 변경 | ID 유지, 내용/해시/분석 교체 |
| 파일 삭제 | 해당 항목 삭제, 검색 큐로 제거 전파 |
| 이름 변경 | 현재는 이전 경로 삭제 + 새 경로 추가 |
| 파일 ↔ 폴더 | 충돌 항목을 정리한 뒤 새 구조 구성 |
| 분석/DB 실패 | 이전 게시 스냅샷 유지, Source 오류 표시 |

실제 경로는 `SourceService → SnapshotPlanner → JdbcSourceStore`입니다.
기존 `AnalysisStore`와 검색 outbox를 사용하며 새 DB 스키마는 필요하지 않습니다.
수집 도중 Source를 삭제하면 되살리지 않습니다.

지식 원문/게시본은 수정하지 않습니다. 근거 해시가 그대로면 CURRENT, 바뀌면 STALE,
경로가 없어지면 MISSING으로 기존 최신성 검사에 반영됩니다. CURRENT는 사실 검증이 아닙니다.

## 아직 하지 않는 일

- Git 네트워크 다운로드는 아직 전체 스냅샷입니다. 실제 Git diff 기반 변경 blob 수집과는 다릅니다.
- URL 조건부 요청, Source 자동 폴링은 별도 작업입니다.
- 전체 원본의 과거 revision을 영구 보관하는 기능은 아닙니다.
- 수집·파일 크기·SSRF·읽기 전용 제한은 그대로입니다.

## 검증

- Source/계획기 대상 테스트 19개 통과: 보존, 변경/삭제, 구조 전환, 실패 롤백 등.
- 통합 실행 중 기존 3개 테스트가 “다른 파일이 바뀌면 ID가 교체된다”는 이전 정책을 기대해 실패했습니다.
  새 보존 정책으로 기대값을 바꾸고 지식/묶음 최신성 관련 29개 테스트를 다시 통과했습니다.
- 전체 빌드 UI 185개/백엔드 316개 통과, 실제 AI opt-in 1개 skip. 실제 JAR 수집·검색·최신성·재시작 smoke도 통과했습니다.
