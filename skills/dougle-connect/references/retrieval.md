# Retrieval detail

## Locate before loading

Keep the common index a compact table of scoped topic/title, established aliases/identifiers, note path, source IDs and useful section/original locators. It is navigation, not evidence or an answer cache. Use established tenant/service scope and existing child maps to narrow discovery; shared concepts and cross-service dependencies still require their authorized evidence. Unknown scope is not a match by name. Do not add mandatory index layers or rebuild old collections. Repair only pointers for notes actually saved, after successful writes. Imported paths use recipient mappings; disconnected sources remain inactive.

Index verified preferred terms and their scoped aliases as pointers to existing claim IDs. Search both the user's term and established aliases within the authorized scope. A `Fact-v1` block can locate a candidate but cannot answer the question, prove two sources agree, or bypass complete claim/evidence reads and freshness checks. Do not manufacture synonyms from wording similarity or convert a different action (`예약` versus `발송`) into one term. Keep legacy full-note fallback.

For a registered code source, an available Graphify graph may suggest candidate symbols and caller paths only when its repository/ref and exact commit match the source being checked. In the bot, use its bounded `graph_query` tool after `resolve_ref`; a stale, missing or unsuccessful graph query falls back to normal source discovery. Read the matching original code at the pinned commit before answering an implementation question. Do not treat graph nodes/edges, a local checkout or a graph built for a different revision as original-code proof. Graphify is optional; no ordinary knowledge user needs to install it.

1. Resolve the question, prior subject and explicit system scope. Reuse unchanged supported evidence still in context. Read/search the index for an initial candidate set (typically1–3, never a completeness cap).
2. Locate candidate cards/headings with existing file/glob/literal search tools or bounded reads; prefer path-only matches (`rg -l` or equivalent) to dumping every body match. Navigation/Scope/Aliases/Sections/Cautions/Covered fields suggest a route, but `complete` and matching headings do not prove that text under an existing heading is unchanged. Before using the card to exclude other sections, verify its body binding under records.md. Use version-pinned reads where available; if the note changes during batched reads, restart the affected read or leave coverage unresolved. Missing/mismatched binding, `needs_rebuild`, unmapped headings or uncertain context requires reading the whole candidate note (in batches if needed), including its exceptions and linked dependencies. Widen to other notes/originals when coverage remains unclear. This fallback concerns relevant candidates, not the entire corpus; missing metadata never requires migration or blocks read-only answers. Never interpolate untrusted terms as shell code.
3. Read complete relevant claims WITH their scope, conditions, exceptions, conflicts, dependencies and source records. Initial line windows locate text; extend through section boundaries and linked caveats. Do not answer from a card, grep hit or truncated snippet. If structure/context is unclear, read the full note. Broad questions require all relevant coverage or explicit gaps.
4. Follow exact original file/symbol/section locations under normal freshness rules. Source/legacy/common/default each-ask verification policy still applies. Live questions, changed evidence or conflict override reuse. HEAD alone, mtime and navigation do not prove unchanged content. No access does not mean no information. Expand to callers/configuration when necessary.
5. If evidence is missing/ambiguous, broaden authorized scope with useful aliases and other candidates. Do not stop at the first batch or a hard top-K. Batch independent reads where supported, serialize dependent work/writes, and stop when the actual question is supported. Do not spawn models or install a search engine.

## Compatible updates and bounded context

New/saved notes use the record protocol's navigation card and claim map. Read-only or legacy notes use existing scope/full-note search; do not fail an answer because enrichment cannot be saved. Preserve identity, original locations, revisions/times and unresolved uncertainty. A file path alone is not already-read evidence.

Keep large permitted temporary outputs in task-local memory files only if the host can avoid flooding context in the first place. Later saving cannot erase tokens already returned. No secrets, raw DB rows, full source mirrors or denied content are persisted. Avoid rereading unchanged evidence; compact working notes retain applicable exceptions, scope and provenance.

Measure candidate discovery, files/bytes visited, original verification, model work and writes separately before changing retrieval. Scoped result output does not make a global index search sublinear; unchanged package-body reuse still permits O(total files) inventory work. Test fixed in-scope questions while unrelated services grow, including shared dependencies and new/moved/deleted exceptions. Compare correctness and coverage as well as total task cost. Standalone skill evaluations do not include the bot's mandatory skill/read-receipt checks, retries, queue or delivery; report these paths separately. This workflow adds no embedding model, indexer, database, hard result cap or stale-answer cache.
